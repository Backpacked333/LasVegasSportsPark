# Outage and offline runbook

Status legend: **Verified** = implemented and tested in this repository today (file cited). **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval. **Pending decision** = needs an operator answer; the owner is named from specification §6.6. "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23).

This is one of the "Operational runbooks" handoff artifacts (§6.7) and the "Outage procedure" staff acceptance task of §6.3. It implements §4.15 (Offline behavior) and the pickup rule of SPK-ENTRY-007, and it is the operating-side counterpart of acceptance journey SPK-AT-018 ("Device works offline then reconnects": observations synchronize once; stale authority is not asserted) and SPK-AT-016 ("Adult may pay but may not collect"). Companion documents: [`cutover.md`](cutover.md), [`recovery.md`](recovery.md), `../package-a/acceptance-fixtures.md` (SPK-AT-016, SPK-AT-018), `../package-a/decision-register.md` (DEC-005, DEC-032, DEC-033, DEC-034), `../package-a/policy-register.md` (POL-019, POL-020).

## 2. Offline behaviour of approved staff devices (§4.15)

### 2.1 What an approved device may queue offline

| Observation kind (SPK-ENTRY-001 record)     | May be queued offline?                                                                   | Basis                                                                                         | Status                                     |
| ------------------------------------------- | ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------ |
| Facility arrival                            | Yes                                                                                      | §4.15 "queue arrival and attendance observations"                                             | **Proposed** (DEC-032)                     |
| Session check-in                            | Yes, for sessions inside the device's roster snapshot                                    | §4.15 "attendance observations"; SPK-ENTRY-003 (staff select the people and sessions)         | **Proposed** (DEC-032)                     |
| Observed attendance (present, absent, late) | Yes, for people inside the roster snapshot                                               | §4.15                                                                                         | **Proposed** (DEC-032)                     |
| Departure                                   | Not named in §4.15; treated as an observation of the same kind until decided             | SPK-ENTRY-001 lists departure separately; SPK-ENTRY-008 (arrivals are not verified occupancy) | **Pending decision** (DEC-032, Operations) |

| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |

| New capacity commitments  | Server-owned holds and database-enforced capacity (SPK-REG-005, SPK-REG-006, §4.7 invariant 3)                                       | Same                                                                    | Rejects the row; creates no hold                                                                                                                | **Proposed**                                                   |

### 2.5 Reconnection and conflict review (§4.15 "Reconnection must preserve conflicting observations for review")

| Step | Behaviour                                                                                                                                                                                                                                           | Status                                                                                                                                                |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | The device uploads its queue as one batch (`entry.sync_offline_observations`, fixture SPK-AT-018) with the snapshot reference and the sync age (now minus snapshot instant) for §5.11 "Offline synchronization age".                                | **Proposed**                                                                                                                                          |
| 2    | The server returns one outcome per observation: `accepted`, `accepted_with_conflict`, `rejected` (with reason), `held_for_review`. Row outcomes are independent; one bad row does not fail the batch.                                               | **Proposed**                                                                                                                                          |
| 3    | Re-uploading the same batch (lost acknowledgement) returns identical outcomes and creates no rows (unique client identifier).                                                                                                                       | **Proposed**; the unique-violation pattern is **Verified** elsewhere (`core-schema.spec.ts` "idempotency keys are unique per organization and scope") |
| 4    | A conflicting online observation (another device recorded the same person absent) is preserved: both rows stay, neither overwrites the other, and an operational exception `entry.observation_conflict` (owner queue `program_manager`) lists both. | **Proposed**; the exception mechanism is **Verified** (`OperationalExceptions.raise`)                                                                 |
| 5    | A program manager resolves the conflict by recording a correction observation naming the effective one with a reason; nothing is deleted (SPK-ENTRY-005). Observation tables are append-only (`forbid_mutation`).                                   | **Proposed**; the trigger pattern is **Verified** (`0001_core_schema.sql`)                                                                            |
| 6    | A batch whose snapshot is older than the maximum age is accepted into review only (`held_for_review`, reason `snapshot_older_than_maximum`); no attendance becomes effective until confirmed row by row.                                            | **Proposed**; maximum age **Pending decision** (DEC-033)                                                                                              |
| 7    | A release attempted offline is never applied from the batch: authority is re-checked online at sync time and the attempt is recorded with its outcome (`denied` when the authority was revoked after the snapshot).                                 | **Proposed**; live authority check **Verified** (identity module)                                                                                     |
| 8    | Rows for sessions outside the snapshot scope, or from a device of another organization, are rejected (`outside_snapshot_scope`; `NOT_FOUND` across organizations, **Verified** error rendering).                                                    | **Proposed**                                                                                                                                          |
| 9    | Sync age and held batches are visible in the Today workspace (SPK-UX-006) under the owner named in [`recovery.md`](recovery.md) section 9.                                                                                                          | **Pending decision** (DEC-015)                                                                                                                        |

### 2.6 Staff checklist while a device is offline

**Proposed**. Print with the device.

- [ ] Check the cached-data age on the screen. If it exceeds the approved maximum ([two hours, Proposed]), stop queueing and switch to paper under section 4 until reconnected.
- [ ] Record arrivals and attendance only for people and sessions shown in the cached roster. Select the people and sessions actually attending; never mark a whole household present (SPK-ENTRY-003).
- [ ] Do not take payments, promise places, change guardians or move rosters. Write the request down for later (keep the customer's input; SPK-UX-008).
- [ ] Do not release a child from a supervised program on the basis of the cached roster. Follow section 3 if an approved manual procedure exists; otherwise the release waits for connectivity or an online check by phone to a staff member with access.
- [ ] On reconnection, let the device upload, then read every row outcome. Report `accepted_with_conflict` and `held_for_review` rows to the program manager the same day.
- [ ] Tell the support lead if the device stayed offline longer than the maximum age or if any observation was rejected.

### 3.3 Rules that apply to any procedure Operations approves (Proposed)

- A cached authority list is evidence of what was true at the snapshot instant, never of what is true now. The record must say which snapshot was used.
- Every release attempt during the outage is recorded, including denials and escalations, and is entered into Sportspark after reconnection as a release record (fixture SPK-AT-016 step 1 records denials too).
- After reconnection, each manual release is re-checked against the authority in force at the recorded time (**Verified** live check: the identity module evaluates grants "at the clock on every call"). A release that would have been denied online is listed for review by the program manager with the guardian informed under the approved communication policy (**Pending decision** DEC-012).
- Payment permission, schedule visibility and household membership never substitute for `collect` (SPK-ENTRY-007; **Verified**: `Person.householdId` is never consulted by any authority check, identity README; the kernel never lets a child principal `pay` or `collect` for themselves even on an `allowSelf` action, **Verified** in `apps/api/src/kernel/__tests__/authorization.spec.ts`; the identity README still lists an older kernel self short-circuit limitation that this test shows is closed, so the README needs updating, which is outside the scope of this document).
- Child details on paper forms are handled under the privacy policy (§4.14; retention **Pending decision** DEC-060).
