Status legend: **Verified** = implemented and tested in this repository today (file cited). **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval. **Pending decision** = needs an operator answer; the owner is named from specification §6.6. Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23). Statements about the code found stale on 2026-10-31 are corrected in place, marked **Verified 2026-10-31 (correction)**, and say what the earlier text claimed.

It implements §4.15 (Offline behavior) and the pickup rule of SPK-ENTRY-007, and it is the operating-side counterpart of acceptance journey SPK-AT-018 ("Device works offline then reconnects": observations synchronize once; stale authority is not asserted) and SPK-AT-016 ("Adult may pay but may not collect"). ### 2.6 Staff checklist while a device is offline

**Proposed**. Print with the device.

- [ ] Check the cached-data age on the screen. If it exceeds the approved maximum ([two hours, Proposed]), stop queueing and switch to paper under section 4 until reconnected.
- [ ] Record arrivals and attendance only for people and sessions shown in the cached roster. Select the people and sessions actually attending; never mark a whole household present (SPK-ENTRY-003).
- [ ] Do not take payments, promise places, change guardians or move rosters. Write the request down for later (keep the customer's input; SPK-UX-008).
- [ ] Do not release a child from a supervised program on the basis of the cached roster. Follow section 3 if an approved manual procedure exists; otherwise the release waits for connectivity or an online check by phone to a staff member with access.
- [ ] On reconnection, let the device upload, then read every item outcome. Report `accepted_with_conflict` items and items flagged `stale_snapshot` to the program manager the same day; each also raises an exception for review (`entry.attendance_conflict` for a conflicting observation, `entry.offline_release_unverified` for a release whose collector lacked authority, `entry.stale_offline_snapshot` for a stale snapshot). **Verified 2026-10-31 (correction)**: the 2026-10-24 checklist named a `held_for_review` outcome, which does not exist (section 2.5 step 2).
- [ ] Tell the support lead if the device stayed offline longer than the maximum age or if any observation was rejected.

## 3. Supervised-pickup outage procedure

**Pending decision: Operations** (DEC-005 "Pickup and outage procedure", DEC-034 "§4.15 supervised pickup during an outage"; POL-019). This section is intentionally empty of procedure. ### 3.3 Rules that apply to any procedure Operations approves (Proposed)

- A cached authority list is evidence of what was true at the snapshot instant, never of what is true now. The record must say which snapshot was used.
- Every release attempt during the outage is recorded, including denials and escalations, and is entered into Sportspark after reconnection as a release record (fixture SPK-AT-016 step 1 records denials too).
- After reconnection, each manual release is re-checked against the authority in force at the recorded time (**Verified**: at synchronization the entry module requires `collect` both now and at the recorded handover time, through identity's `hasPermissionAt` as-of check over the grant, relationship and suspension history; a release without it is recorded `not_held` with a critical `entry.offline_release_unverified` exception — `apps/api/src/modules/entry/__tests__/offline-reconciliation.spec.ts`). A queued release the server cannot record (no approved procedure, outside the device's authority) raises a critical `entry.offline_release_unrecorded` exception (**Verified**, `offline-sync.spec.ts`). A release that would have been denied online is listed for review by the program manager with the guardian informed under the approved communication policy (**Pending decision** DEC-012).
- Payment permission, schedule visibility and household membership never substitute for `collect` (SPK-ENTRY-007; **Verified**: `Person.householdId` is never consulted by any authority check, identity README; the kernel never lets a child principal `pay` or `collect` for themselves even on an `allowSelf` action, **Verified** in `apps/api/src/kernel/__tests__/authorization.spec.ts`; the identity README still lists an older kernel self short-circuit limitation that this test shows is closed, so the README needs updating, which is outside the scope of this document).
- Child details on paper forms are handled under the privacy policy (§4.14; retention **Pending decision** DEC-060).

## 6. Monitoring signal for this runbook
