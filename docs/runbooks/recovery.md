## 2. The four kinds of recovery (§5.8)

The first step of every incident is to classify it. The classification decides who may order the recovery and what must be reconciled afterwards.

| Kind                             | When it applies                                                                                                                           | What is restored                                                                                       | What it cannot undo                                                                                     | Authority effect (authority matrix section 6)                                                                                                                     | Decision owner                                                                           | Status       |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------ |
| Prelaunch abort                  | Before any customer activation, payment or publication in Sportspark for the affected scope                                               | Legacy writes for the scope; Sportspark state for the scope is discarded or kept as a rehearsal import | Nothing needs undoing: no external fact was created                                                     | Every assignment for the scope reverts to legacy (new assignment records, effective now)                                                                          | Cutover decision owner (**Pending decision** DEC-068)                                    | **Proposed** |
| Software rollback                | A Sportspark release must be reverted and no data is lost                                                                                 | The previous application build                                                                         | Schema migrations already applied (they are forward-only, section 4)                                    | None. Assignments are data, not code                                                                                                                              | Technical lead (**Pending decision** DEC-015)                                            | **Proposed** |
| Data restoration                 | The database must be restored to an earlier point                                                                                         | Local records as of the restore point                                                                  | Payments, deliveries, provider events and valid customer activity that happened after the restore point | None by itself; assignments made after the restore point are re-recorded from the decision log                                                                    | Technical lead with Finance; lifting recovery mode needs the general manager (section 5) | **Proposed** |
| Recovery after real transactions | Sportspark has accepted payments, published schedules or activated customers for the scope, and the scope must be repaired or handed back | Journals preserved; external facts reconciled; authority handed back explicitly if needed              | Money already received stays recorded in the Sportspark journal; refunds follow the original payment    | A new assignment record names legacy as writer from a stated instant; Sportspark disables the workflow first; records created meanwhile are exported under review | Cutover decision owner with Finance (**Pending decision** DEC-068, DEC-067)              | **Proposed** |

Principle (§5.8, reproduced): "Restoring an older database cannot undo payments or valid customer activity." A restore moves Sportspark's memory backwards; it does not move the payment processor, the messaging provider, the customers or the staff backwards. Everything they did after the restore point is a fact that Sportspark must learn again before it resumes normal operation (section 7).

## 4. Software rollback

Owner: Technical lead. No authority change.

- [ ] Confirm no data loss is involved; otherwise this is data restoration (section 5).
- [ ] Choose the build to roll back to. It must be compatible with the schema currently applied: migrations are forward-only and immutable once applied. **Verified**: `packages/db/src/migrate.ts` refuses to run when an applied migration's checksum changed and applies each migration in its own transaction; `packages/db/src/migrate.spec.ts` "refuses to run when an applied migration changed on disk", "rolls back a failing migration file as a unit". No down-migration mechanism exists in `packages/db/migrations` (**Verified** by listing).
- [ ] If the rollback target predates a migration, do not roll back the code alone: treat the change as a new forward migration or a data restoration decided with Finance.
- [ ] Order the rollback so that no event is consumed by a build that lacks one of its handlers: stop or roll back the API processes first, let the current (newer) workers drain the outbox and the inbox (no pending event due now), then stop the workers and deploy the previous build to them. On a roll-forward, deploy the workers before the APIs. The order is **Proposed**. The guard behind it is **Verified** (R3-OPERATIONS-01): each event records the handlers its producing build registers (`outbox_events.expected_handlers`, `inbox_events.expected_handlers`, migration `0013_core_event_expected_handlers.sql`); a worker whose build lacks one runs the handlers it has and leaves the event pending, `last_error` "waiting for handler(s) ...", retried every `OUTBOX_MISSING_HANDLER_RETRY_SECONDS` (default 300) without counting an attempt, so the handler runs once a build that has it is back (`outbox.spec.ts`, `inbox.spec.ts` "R3-OPERATIONS-01: ..."). A build that removes a handler on purpose declares it with `EventHandlerRegistry.retire` (inbox: `Inbox.retire`), or such events wait for it; the committed handler manifest fails such a build in CI (`apps/api/src/__tests__/event-handler-manifest.spec.ts`, **Verified**). A wait is not silent: once an event has waited `OUTBOX_MISSING_HANDLER_ESCALATE_AFTER_SECONDS` (default 3600) the worker opens `reliability.outbox_waiting_for_handler` (inbox: `reliability.inbox_waiting_for_handler`) in the `system_administrator` queue naming the missing handlers, and resolves it when the event settles; it cannot be resolved by hand before that, only closed with a reason (**Verified**, migration `0015_core_event_handler_wait.sql`; `outbox.spec.ts`, `inbox.spec.ts` "§5.11 / R3-OPERATIONS-01: ...").
- [ ] Stop workers cleanly: `SIGTERM` (or `SIGINT`) makes the worker claim nothing more, waits for the work in flight (the outbox and inbox event in hand, a periodic job pass, an idempotency sweep) to finish and record its outcome, hands claimed events it has not started back at once, then closes the application and its database and exits; the whole stop, the database close included, is bounded by `WORKER_SHUTDOWN_TIMEOUT_MS` (default 20,000; keep it under the host's grace period) (**Verified 2026-10-31 (correction)**, R3-OPERATIONS-10: `apps/api/src/worker.ts`, `kernel/workers/graceful-stop.ts`, `kernel/__tests__/worker-shutdown.spec.ts`; the earlier text called the stop clean while it only cleared timers and exited mid-pass, and the close was not bounded: ending the database pool waits for every connection still inside a transaction). When the budget runs out first, the worker exits with those connections open and the database rolls their transactions back. Work still running when the timeout ends is retried once its lease lapses: `OUTBOX_LOCK_LEASE_SECONDS` (default 60) for outbox and inbox events, `PERIODIC_JOBS_LEASE_SECONDS` (default 300) for a periodic job (**Verified**: `outbox.spec.ts` "reclaims events whose worker died (expired lease)"). The communications delivery worker and the finance provider worker also claim nothing more and their `stop()` resolves only once the batch or pass in flight has recorded its outcomes, so the bounded stop waits for a delivery hand-off or provider call instead of cutting it off (**Verified**, R3-OPERATIONS-10: `modules/communications/__tests__/worker-stop.spec.ts`, `modules/finance/__tests__/worker-stop.spec.ts`).
- [ ] Deploy the previous build; `DB_AUTO_MIGRATE` does not run against PostgreSQL in production (**Verified**: `apps/api/src/kernel/database/database.provider.ts` applies migrations only when `NODE_ENV !== 'production'`), so the schema stays as it is.
- [ ] Verify `GET /v1/health` reports `database: ok` (**Verified**: `apps/api/src/kernel/health/health.controller.ts`; `kernel/__tests__/auth-and-operations.spec.ts` "serves health publicly and echoes correlation ids") and `GET /v1/ready` returns 200 (**Verified**: `health.controller.ts`; `kernel/__tests__/health-ready.spec.ts` asserts 503 for an unreachable database, for a pending, changed or missing migration and for a draining process, `degraded` (200) for an outbox or inbox backlog and for a stale periodic job, and that dead letters are counted without changing readiness; **Verified 2026-11-09 (correction)**: the earlier text said readiness was not asserted by a test). Every route, health and readiness included, is served under the global `v1` prefix (`apps/api/src/kernel/app-setup.ts`), so `GET /health` and `GET /ready` answer 404. **Verified 2026-10-31 (correction)**: the 2026-10-24 text gave the unprefixed paths and called readiness **Verified**.
- [ ] Confirm which build is running: the `version` that `GET /v1/health` and `GET /v1/ready` report is the commit the image was built from (**Verified**: `config.ts` `buildVersion` derives `APP_VERSION` from `SOURCE_COMMIT`, which the Dockerfile exports and the CI and deploy workflows set to the commit, or from `VERCEL_GIT_COMMIT_SHA` on the staging host; an explicit `APP_VERSION` names a release instead; `kernel/__tests__/config.spec.ts` "§5.8 / §6.8 item 11: APP_VERSION names the build ...", `health-ready.spec.ts` "liveness and readiness name the build", and the CI job "Container image" asserts that the running image reports `github.sha`). Compare it with the build identifier in the deployment tooling and the ledger row; `0.1.0` means a developer build. **Verified 2026-11-09 (correction)**: the earlier text said `APP_VERSION` was set by no build or deployment step. Where the image runs is still **Pending decision** DEC-021.
- [ ] Restart workers; confirm the outbox drains (pending count falls) and no new `reliability.outbox_dead_letter` or `reliability.inbox_dead_letter` exceptions appear. An outbox dead letter is raised to the queue of the failing handler's failure owner, else the producer's, and to `system_administrator` only when neither names one; almost every module handler names one (`finance_operator`, `program_manager`, `league_manager`, `scheduler`, `front_desk`, `support_operator`, `facilities_operator`). An inbox dead letter always goes to `system_administrator` (**Verified**: `outbox-dispatcher.ts`, `kernel/__tests__/outbox.spec.ts` "dead-letters to the failing handler failure owner (§4.12, SPK-UX-006)", "uses the producer failure owner when the failing handler declares none", "falls back to system_administrator when nobody declares an owner"; `inbox.ts`, `inbox.spec.ts` "§4.12: retries failed events with backoff and dead-letters with an owned exception after max attempts"). Look across every queue: list `GET /v1/exceptions?status=open` as a general manager, system administrator or support operator, who see every queue (`modules/support/services/exception-queues.service.ts`, oversight roles), and pick out both categories; `GET /v1/exceptions?queue=system_administrator` alone misses most outbox dead letters, and the list has no category filter (**Proposed**: add one). **Verified 2026-10-31 (correction)**: the 2026-10-24 text said every outbox dead letter goes to `system_administrator`. Events still pending with `last_error` "waiting for handler(s) ..." were produced by the newer build and wait for its handlers: they run after the next roll-forward, or the newer build must retire those handlers (**Verified**, R3-OPERATIONS-01); a rollback that lasts longer than `OUTBOX_MISSING_HANDLER_ESCALATE_AFTER_SECONDS` shows them as `reliability.outbox_waiting_for_handler` exceptions in the `system_administrator` queue, resolved by the worker after the roll-forward (**Verified**).
- [ ] Record the rollback with build identifiers in the release evidence ledger.
- [ ] Assignments are data: a rollback must not reinterpret them (authority matrix section 6).

## 5. Data restoration

Owner: Technical lead, with Finance for every step involving money; recovery mode is lifted by the general manager. The backup and restore tooling is **Pending decision** (DEC-021); this section states what must be true regardless of tooling.

### 5.1 Before restoring

- [ ] Classify: is this truly data restoration, or can the damage be repaired forward with corrections (append-only journals and audit mean most mistakes are corrected by new rows, not by restores; SPK-PAY-010; **Verified** `forbid_mutation` on `audit_records`, `core-schema.spec.ts` "audit records are append-only")?
- [ ] Identify the restore point (instant, UTC) and write it in the decision log with the evidence (backup identifier, reason).
- [ ] Estimate what will be lost locally between the restore point and now: payments received, refunds executed, schedules published, households activated, observations synced, notices sent. Each becomes a reconciliation item (section 7).
- [ ] Confirm the decision log and the migration snapshot files are intact outside the database ([`cutover.md`](cutover.md) sections 4 and 13).
- [ ] Declare recovery mode before touching the database (section 5.2).

### 5.2 Recovery mode

**Verified** gate (review stage 2; `apps/api/src/kernel/recovery/`, test `apps/api/src/__tests__/journeys/spk-at-028.spec.ts`). The staff dashboard view of it is Pending.

- [ ] Choose a restore reference (the ticket or backup id) and set `RECOVERY_RESTORE_REFERENCE` to it on every API and worker process **before** they start on the restored database. At boot each organization gets one critical `reliability.recovery_mode` exception (owner queue `general_manager`; `details` carry the reference and the `database_restores` record of the restore, or `missing`; audit action `operations.recovery_entered` with the same details and, when recorded, the restore instant and operator in its reason; section 5.3). A restart with the same reference does not re-enter a recovery that was already resumed. **Verified**.
- [ ] While recovery mode is active, the HTTP routes of finance's money commands (quotes, checkouts and their payments, obligations and contribution payments, credits, installments, cash tenders, refunds) answer 503 `INTEGRATION_UNAVAILABLE`, next action `retry_later`, `details.reason = recovery_mode`, before any idempotency key is claimed; reads, provider webhooks, `POST /v1/payments/{id}/reconcile`, `POST /v1/refunds/{id}/reconcile` and `POST /v1/settlement-reconciliations` stay available. **Verified**. The same refusal covers point-of-sale setup and sales (products, registers, opening and closing register sessions, sales, lines, tenders, voids, returns) and accounting mappings and export batches: every command of `PosSetupController`, `PosSalesController` and `AccountingController` (`@RefusedDuringRecovery()` in `modules/finance/controllers/pos.controller.ts` and `accounting.controller.ts`; the published contract documents the 503, `modules/finance/__tests__/recovery-contract.spec.ts`; a POS or accounting request during recovery is not exercised by a test). **Verified 2026-10-31 (correction)**: the 2026-10-24 list left out point of sale and accounting. So the desk cannot ring a sale or close a drawer session until recovery is lifted (section 5.4). Refusing other modules' customer commands too is **Proposed**.
- [ ] The refusal also holds for in-process callers: `RefundsService.request`, `CreditsService.issue`, `ObligationsService.create` and `ObligationsService.pay` check recovery mode for the organization themselves and answer the same 503 `INTEGRATION_UNAVAILABLE` `recovery_mode` before anything is reserved, recorded or sent to the provider (`refuseDuringRecovery` in `apps/api/src/modules/finance/finance.shared.ts`). So `POST /v1/recommendations/{id}/apply` for a refund recommendation is refused and recorded as a failed apply that may be retried after resuming (automation `__tests__/recovery-apply.spec.ts`); `POST /v1/import-batches/{id}/apply` stops at its first `credit` or `open_obligation` row and is resumed by applying again after recovery (the apply treats a 5xx refusal as a stop, not a row exception; the finance refusal is `finance/__tests__/recovery-in-process.spec.ts`); and support's `POST /v1/cases/{id}/request-refund` is `@RefusedDuringRecovery()` and also checks recovery mode itself (support `__tests__/case-actions.spec.ts` "SPK-AT-028 / §5.8 ..."). The assembled application shows the direct, case and assistant refund paths refused together with no refund recorded, reserved or sent (journey `apps/api/src/__tests__/journeys/spk-at-028.spec.ts` "SPK-AT-028 / R3-OPERATIONS-02: during recovery a refund requested from a support case or applied from an approved assistant proposal is refused ..."). **Verified 2026-11-01 (correction)**, R3-OPERATIONS-02 / R3-DOCS-TRUTH-3-07: the earlier 2026-11-01 text said these commands were not refused. An import-apply request during recovery is not exercised end to end by a test.
- [ ] The finance worker keeps reconciling payment and refund attempts by their existing idempotency keys but starts no new charge (no installment collection) while recovery mode is active. **Verified**. The outbox dispatcher and the inbox keep running so provider evidence is applied and checkouts finalize (section 7 steps 2 to 5). Message delivery is held back per organization: while its recovery mode is active the delivery worker claims none of its queued delivery attempts, so nothing is handed to a messaging provider, and the attempts wait until `POST /v1/recovery/resume`; other organizations keep receiving their messages (**Verified**, R3-OPERATIONS-05: `apps/api/src/modules/communications/services/delivery-worker.ts`, `modules/communications/__tests__/delivery-recovery.spec.ts`). Section 7 step 9 is therefore a review of the notices waiting to be sent, done before resuming; notices re-created by re-dispatched events wait with them. **Verified 2026-11-01 (correction)**: the earlier text said the delivery worker could not be held back and that queued notices reached the provider as soon as the worker started.
- [ ] `GET /v1/recovery` shows whether recovery is active and what still blocks resuming. **Verified**.
- [ ] Tell staff: what is unavailable, the restore instant, the next permitted action (SPK-UX-006).

### 5.3 Restore

- [ ] Restore the database to the restore point with the tooling of the selected environment (**Pending decision** DEC-021).
- [ ] Verify `schema_migrations` in the restored database matches the migration files on disk; the migration runner refuses to start otherwise (**Verified**: `migrate.ts` "migration ... is applied in the database but missing from disk" and checksum mismatch errors). If the restored schema is older than the deployed code, deploy the matching build first (section 4) or apply the pending migrations forward.
- [ ] Start the processes with `RECOVERY_RESTORE_REFERENCE` set (section 5.2); confirm `GET /v1/ready` is 200 (**Verified**, section 4) and `GET /v1/recovery` reports `active: true`.
- [ ] Re-record every authority assignment and decision-log entry made after the restore point (authority matrix section 6, "Data restoration").
- [ ] Audit the restore. **Verified**: `pnpm db:restore --in <file> --operator <name>` (or `RESTORE_OPERATOR`) writes a `database_restores` row in the restored database once the restored rows and applied migrations equal the manifest's: the backup id and the instant it was taken, the restore instant, the operator, the build (`APP_VERSION` or `SOURCE_COMMIT` of the image), whether the schema is current for this build, and the verification (migration `0020_core_database_restores.sql`, append-only; `packages/db/src/backup.ts` `recordRestore`; `packages/db/src/backup.spec.ts` "SPK-AT-028 / runbook §5.3: a faithful restore is recorded in database_restores ...", "a restore that does not match its backup is never recorded", "a restored schema older than migration 0020 cannot hold the record and says so"). At boot the processes look `RECOVERY_RESTORE_REFERENCE` up in it, and the `operations.recovery_entered` audit record and the `reliability.recovery_mode` exception carry the record, or `missing` (`apps/api/src/kernel/__tests__/recovery-restore-record.spec.ts`). The row is platform-wide (no organization: a restore is a fact about the whole database, like `schema_migrations`), so the per-organization audit record references it instead of repeating it; the `recovery.database_restored` audit action proposed earlier is superseded. Two gaps remain: a backup taken before migration 0020 has no ledger table in its dump, so the CLI says so and the restore instant and backup id go in the decision log ([`cutover.md`](cutover.md) section 13) and the release evidence ledger; and `pg_restore` itself is exercised by rehearsal (ledger row L-024), not by a test. **Verified 2026-11-09 (correction)**: the earlier text said no command or endpoint writes such a record.

### 5.4 After restoring

- [ ] Run the external-fact reconciliation of section 7 to completion and obtain Finance acceptance.
- [ ] Only then lift recovery mode: the general manager calls `POST /v1/recovery/resume` with a reason (`operations.resume_after_recovery`; the named recovery owner is **Pending decision** DEC-068). It is refused with 409 `RESOURCE_CONFLICT` `details.code = recovery_reconciliation_incomplete` and the blockers while any payment attempt is `created`, `action_required`, `processing` or `unknown`, any refund is `requested`, `processing` or `unknown`, or the latest processor settlement reconciliation recorded since recovery began is missing or shows a discrepancy; the generic exception commands cannot resolve the recovery exception (`recovery_resume_required`). **Verified**. Requiring an accepted reconciliation report entity (step 11) is **Proposed** (DEC-067).
- [ ] Where point of sale is enabled, close the register sessions left open across recovery and count their drawers once recovery is lifted (closing a session is refused while recovery is active, section 5.2); the end-of-day variance review (SPK-PAY-012) waits for it. **Proposed** step.
- [ ] Remove `RECOVERY_RESTORE_REFERENCE` from the configuration at the next deployment (keeping it is harmless: a resumed restore is not re-entered).
- [ ] Restart workers. Outbox events present in the restored database that were already dispatched before the restore will be dispatched again, because the restored `event_consumptions` rows are gone with the restore. Handlers must therefore be idempotent against the external world (section 7, item 9); handlers are idempotent against the database only within one database (**Verified** consumption rule, `outbox.spec.ts` "dispatches each event to every handler exactly once, even when redelivered").
- [ ] File the evidence (section 10).

## 6. Recovery after real transactions

Owner: Cutover decision owner with Finance; technical lead executes. Applies when Sportspark has accepted payments, published schedules or activated customers for the scope and the scope must be repaired or handed back (§5.8).

- [ ] Preserve journals: no journal entry, audit record or observation is deleted or rewritten; corrections are new rows referencing what they correct (SPK-PAY-010; **Verified** pattern: `forbid_mutation` trigger, `0001_core_schema.sql`).
- [ ] Reconcile external facts (section 7) and obtain Finance acceptance.
- [ ] Decide per category and scope whether Sportspark continues or authority is handed back to legacy.
- [ ] Handback, if ordered: (1) Sportspark disables the workflow for the scope first; (2) a new authority assignment names legacy as writer from a stated instant (`authority_assignments`, **Verified**, section 3); (3) legacy writes are re-enabled; (4) records created in Sportspark meanwhile are exported to legacy under the migration owner's review; (5) staff and customers are told (SPK-UX-006 "Next permitted action"; [`cutover.md`](cutover.md) sections 10 and 11). The handback is never implied by a restore or a rollback; it is always an explicit record (authority matrix rule 10).
- [ ] Money already received stays recorded in Sportspark's journal. Refunds of Sportspark payments are executed through Sportspark against the original payment (SPK-PAY-008 reservation rule; **Verified** `RefundMachine` keeps `unknown` until provider evidence).
