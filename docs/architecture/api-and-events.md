# API and event schemas

Status legend: **Verified** = implemented and tested in this repository today (file cited). **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval. **Pending decision** = needs an operator answer; the owner is named from specification §6.6. "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23).

This is the "API and event schemas" artifact required by §6.7. It covers the versioned, command-oriented API contract (§4.8), command behaviour (§4.9), the error contract (§4.10) and background work: the domain event envelope, the transactional outbox and the provider inbox (§4.12), plus an event catalogue. The exact request and response schemas are generated into `docs/api/openapi.json` (`pnpm build && pnpm openapi`, `CLAUDE.md`); this document explains the conventions those schemas follow and marks what exists. The entities the commands act on are in `docs/architecture/domain-model.md`.

## 2. API conventions (§4.8)

| Convention           | Behaviour today                                                                                                                                                                                                                                                                                                                                                                  | Status                                                                                                                                                                                          |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Version prefix       | Every route is served under `/v1` (`API_PREFIX` in `apps/api/src/kernel/app-setup.ts`; `servers: [{ url: '/v1' }]` in `packages/contracts/src/openapi.ts`; OpenAPI `info.version` is `0.1.0`).                                                                                                                                                                                   | **Verified** (`auth-and-operations.spec.ts` requests `/v1/health`, `/v1/operations/{id}`)                                                                                                       |
| Versioning rule      | Additive changes (new optional fields, new paths, new error codes) stay in `/v1`. A change that removes or re-types a field, changes a lifecycle or changes an error code's meaning is served under a new prefix, and the old one is kept for the API compatibility window that §4.13 requires the mobile release to define.                                                     | **Proposed**; the window and the minimum supported app version are **Pending decision**: Technical lead/operator (§4.13, SPK-AT-027)                                                            |
| Command orientation  | Consequential actions are `POST` to a verb sub-resource (`/closures/{id}/apply`, `/access-grants/{id}/revoke`, `/schedule-drafts/{id}/publish`) or `POST` to a collection that creates a record (`/relationships`, `/event-series`); revisioned edits are `PATCH` with `expectedRevision`; reads are `GET` with scoped query parameters.                                         | **Verified** pattern (every path in `docs/api/openapi.json`)                                                                                                                                    |
| Authentication       | Bearer token on every route unless the handler is marked `@Public()` (`/v1/health`, `/v1/dev/tokens`). The token is verified through `IdentityProviderPort` and resolved to a `Principal` through `PrincipalResolverPort`; a token that resolves to no active account is `AUTHENTICATION_REQUIRED` (401).                                                                        | **Verified** (`apps/api/src/kernel/auth/auth.guard.ts`; `auth-and-operations.spec.ts` "rejects missing, malformed, expired and unknown tokens")                                                 |
| Organization context | "Organization context must be derived from authenticated authorization, even when identifiers appear in requests" (§4.8): `Principal.organizationId` comes from the resolver (the account row), never from a header, path or body. Facility ids in bodies are validated against the principal's organization.                                                                    | **Verified** (`packages/contracts/src/principal.ts`; `principal-resolver.spec.ts` "cross-organization: a token from another organization never sees this organization's people")                |
| Authorization        | Every service calls `AuthorizationService.require(principal, action, target)` with an action declared once by `defineActions({ id: '<module>.<verb>', staffRoles, allowSelf?, subjectPermission?, teamRole?, requirements })` and the real target (organization, facility, subject persons, team entry, `protected`). A denial on a protected target is rendered as `NOT_FOUND`. | **Verified** (`apps/api/src/kernel/authorization/*`; `authorization.spec.ts`)                                                                                                                   |
| Request validation   | Bodies, query strings and path parameters are parsed by zod schemas (`@ZodBody`, `@ZodQuery`, `@ZodParams`); failures are `VALIDATION_FAILED` (400) with `details[]` of `{ path, message, code }`.                                                                                                                                                                               | **Verified** (`apps/api/src/kernel/http/zod-validation.pipe.ts`; `auth-and-operations.spec.ts` "validates path parameters with the error contract")                                             |
| Identifiers          | Every id is an application-generated time-ordered UUID v7 (`newId()`); clients never choose ids.                                                                                                                                                                                                                                                                                 | **Verified** (`packages/contracts/src/ids.ts`, `ids.spec.ts`)                                                                                                                                   |
| Time on the wire     | `Instant` is an ISO-8601 string with offset (stored as `timestamptz`); `Interval` is half-open `[start, end)`; facility-local inputs (`LocalTime` `HH:MM`, `LocalDate` `YYYY-MM-DD`) are interpreted in the facility's IANA zone (SPK-SCHED-008).                                                                                                                                | **Verified** (`packages/contracts/src/time.ts`, `time.spec.ts`; `event-series.spec.ts` SPK-SCHED-008)                                                                                           |
| Money on the wire    | `Money` is `{ amountMinor: integer, currency: ISO 4217 }` (SPK-PAY-001); a client-submitted price is never authoritative.                                                                                                                                                                                                                                                        | **Verified** contract (`packages/contracts/src/money.ts`, `money.spec.ts`); no endpoint carries money yet, so every finance body is **Proposed**                                                |
| Pagination           | List queries accept `limit` (1 to 200, default 50) and an opaque `cursor`; responses are `{ items, nextCursor }`. Global bootstrap responses are not offered (§4.5).                                                                                                                                                                                                             | **Verified** (`packages/contracts/src/pagination.ts`; `events.spec.ts` "lists events ... with cursor pagination")                                                                               |
| Success status codes | `POST` that creates returns 201 with the created record; `POST` that transitions or `PATCH` returns 200 with the current record; `DELETE` returns 200 with `{ id }`. An asynchronous command returns 202 with the `OperationAccepted` envelope (section 4).                                                                                                                      | **Verified** for 200/201 (`packages/contracts/src/api/identity.ts` `status`, `scheduling.ts` `command(...)`); 202 with `OperationAccepted` is **Proposed** (schema exists, no endpoint uses it) |
| Content type         | `application/json` request and response bodies only; uploads and downloads are restricted object-storage flows (§4.14), not API bodies.                                                                                                                                                                                                                                          | **Verified** for JSON (every registered path); object storage **Proposed** (no storage adapter exists)                                                                                          |
| Rate limiting        | `RATE_LIMITED` (429) is reserved in the error contract for rate-limited recovery and abuse protection (§4.14 "Rate-limited recovery").                                                                                                                                                                                                                                           | **Verified** code; limiter **Proposed** (no limiter exists in `apps/api/src/kernel`)                                                                                                            |
| Schema publication   | `packages/contracts/src/api/<module>.ts` registers each path and component with the single `openApiRegistry`; `pnpm build && pnpm openapi` writes `docs/api/openapi.json` (OpenAPI 3.1.0, `bearerAuth` security scheme). "Publish exact schemas in OpenAPI before client integration" (§4.8) is a Package E gate.                                                                | **Verified** generation (`docs/api/openapi.json` present with 60 operations); the client-integration gate is **Proposed** (no client exists, §6.5 Package E)                                    |

### 2.1 Headers

| Header                | Direction | Rule                                                                                                                                                                                                                                                                                                                                      | Status                                                                                                                                                 |
| --------------------- | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Authorization`       | request   | `Bearer <token>`; absent on `@Public()` routes gives the anonymous principal.                                                                                                                                                                                                                                                             | **Verified** (`auth.guard.ts`)                                                                                                                         |
| `Idempotency-Key`     | request   | Required on every handler marked `@Idempotent()` (all consequential `POST`, `PATCH`, `DELETE`); 8 to 128 characters (`IdempotencyKey` in `packages/contracts/src/commands.ts`, constant `IDEMPOTENCY_KEY_HEADER = 'idempotency-key'`); missing or malformed is `VALIDATION_FAILED` (400). Semantics in section 3.                         | **Verified** (`apps/api/src/kernel/http/idempotency.interceptor.ts`; `idempotency.spec.ts` "requires an Idempotency-Key header")                       |
| `X-Correlation-Id`    | both      | Honoured when the incoming value matches `^[A-Za-z0-9._:-]{8,128}$`, otherwise a new UUID v7 is assigned (`CORRELATION_ID_HEADER = 'x-correlation-id'`); always echoed on the response; stored on `audit_records`, `operations`, `outbox_events`, `job_attempts` and every error body as `correlationId` (§4.10 "correlation reference"). | **Verified** (`apps/api/src/kernel/http/correlation.middleware.ts`; `auth-and-operations.spec.ts` "serves health publicly and echoes correlation ids") |
| `Idempotent-Replayed` | response  | `true` when the response is a stored replay for the same key and payload.                                                                                                                                                                                                                                                                 | **Verified** (`idempotency.spec.ts` "replays the same key + payload without re-executing")                                                             |

### 2.2 Command meta (§4.9 "Expected revision", "Policy references", "Reason")

Every command body may carry these fields; modules mix them in with `withCommandMeta(shape)` and tighten them where the specification requires.

| Field              | Type and bounds                                               | Rule                                                                                                                                                                                                                                                                                                                                                                   | Status                                                                                                                                                                                                                              |
| ------------------ | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `expectedRevision` | integer >= 1, optional                                        | When present, the write runs `where revision = expectedRevision` and bumps it; a mismatch is `STALE_REVISION` (409) with `details { expectedRevision, currentRevision }`. Required (not optional) for sensitive edits: `PATCH /people/{id}`, `PATCH /staff-memberships/{id}`, `PATCH /schedule-drafts/{id}`.                                                           | **Verified** (`CommandMetaSchema`; `UpdatePersonBody.extend({ expectedRevision: Revision })`; `people.spec.ts` "§4.9: PATCH ... requires the current revision"; `schedule-drafts.spec.ts` "autosave guarded by the draft revision") |
| `reason`           | string, 1 to 2000 characters, optional                        | Stored on the audit record. Required for overrides, corrections and revocations: `POST /access-grants/{id}/revoke`, `/invitations/{id}/revoke`, `/staff-memberships/{id}/end`, `/accounts/{id}/relink`, `/duplicate-candidates/{id}/merge`, `/duplicate-candidates/{id}/dismiss`, `POST /access-reviews`, and `reason` on `POST /closures` (the closure's own reason). | **Verified** (`packages/contracts/src/api/identity.ts` `.extend({ reason: Reason })`; `scheduling.ts` `CreateClosureBody`; `unit-of-work.spec.ts` audit `reason`)                                                                   |
| `policyReferences` | array of up to 20 strings, each 1 to 200 characters, optional | Identifies the policy versions the actor relied on (§4.9 "Policy references"); carried into the audit record and, for finance commands, the quote.                                                                                                                                                                                                                     | **Verified** field; no command interprets it yet, so its vocabulary (policy ids of `docs/package-a/policy-register.md`) is **Proposed**                                                                                             |

## 3. Idempotency semantics (§4.9)

| Rule                                                                                              | Mechanism                                                                                                                                                                                                                                         | Status                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A replay with the same key and payload returns the same operation (§4.9).                         | The key is stored with a SHA-256 hash of the canonical JSON of `{ method, path, body }` (key order ignored, `undefined` dropped); the stored status and body are replayed with `Idempotent-Replayed: true` and the handler is not executed again. | **Verified** (`idempotency.spec.ts` "replays the same key + payload without re-executing"; `people.spec.ts` "§4.9: POST /v1/people replays ... without creating a second person"; `resources.spec.ts` "idempotent replay creates one resource") |
| The same key with different contents returns a conflict (§4.9).                                   | Hash mismatch is `IDEMPOTENCY_CONFLICT` (409, next action `use_new_idempotency_key`).                                                                                                                                                             | **Verified** (`idempotency.spec.ts`)                                                                                                                                                                                                            |
| A key still executing cannot be raced.                                                            | The claim is an insert with `on conflict do nothing` inside a transaction; a second request while the first is `in_progress` is `IDEMPOTENCY_IN_PROGRESS` (409, `retry_later_with_same_key`).                                                     | **Verified** (`idempotency.interceptor.ts` `claim`); the race itself is exercised only under serialized PGlite, so the true-concurrency proof depends on the CI PostgreSQL job (`docs/architecture/overview.md` "Testing strategy")             |
| Keys are scoped so one customer cannot replay another's command.                                  | Primary key `(organization_id, scope_key, idempotency_key)` where `scope_key` is `account:<accountId>` or `<kind>:<actorLabel>` for principals without an account.                                                                                | **Verified** (`idempotency.spec.ts` "keys are scoped per account"; `core-schema.spec.ts` "idempotency keys are unique per organization and scope")                                                                                              |
| Domain outcomes are replayed; infrastructure failures are retryable.                              | A `DomainError` with status < 500 is stored and replayed (with a fresh `correlationId`); any 5xx or unexpected error releases the key so the client may retry with the same key.                                                                  | **Verified** (`idempotency.spec.ts` "stores domain (4xx) failures" and "releases the key after an unexpected (5xx) failure")                                                                                                                    |
| Keys expire.                                                                                      | `expires_at = now + IDEMPOTENCY_TTL_HOURS` (configuration default 24); expired keys are deleted on the next claim and may be reused.                                                                                                              | **Verified** (`idempotency.spec.ts` "expired keys can be reused"; `apps/api/src/kernel/config.ts`)                                                                                                                                              |
| An asynchronous command's key points at its operation so a replay returns the same `operationId`. | `idempotency_keys.operation_id` exists (`0001_core_schema.sql`); the interceptor stores `null` today and nothing sets it. The checkout coordinator (§4.11 step 4) and every 202 command should set it.                                            | **Proposed** (column **Verified**, population not implemented)                                                                                                                                                                                  |
| Replay never re-executes a provider call.                                                         | Provider calls happen outside the database transaction and their outcome is recorded as a fact (payment attempt, delivery attempt); a replayed command returns the recorded outcome.                                                              | **Proposed** rule (`CLAUDE.md` "Command pattern" step 4); no provider adapter exists (§5.2, **Pending decision**: Technical lead/account owners, DEC-018, DEC-019, DEC-020)                                                                     |

## 4. The operations resource (§4.8 `GET /v1/operations/{id}`)

| Element                       | Definition                                                                                                                                                                                                                                                                                                                                                                                                          | Status                                                                                                                                                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Operation` schema            | `{ id: uuid, kind: string, status, correlationId: string \| null, result: unknown \| null, error: { code, message, details? } \| null, createdAt, updatedAt, completedAt: instant \| null }` (`OperationSchema`, component `Operation`).                                                                                                                                                                            | **Verified** (`packages/contracts/src/commands.ts`; `docs/api/openapi.json` `components.schemas.Operation`)                                                                                              |
| `status` values               | `pending`, `running`, `succeeded`, `failed`, `recovery_required`, `compensated`. Anyone else, including staff of another organization, receives `NOT_FOUND` (404). | **Verified** (`operations.service.ts` `OperationActions.read`, `find`; `auth-and-operations.spec.ts` "shows an operation to its requester and to staff, and hides it across accounts and organizations") |

Producers today: `scheduling.publish_schedule` (`publications.operation_id`) and the identity merge (`person_merges.operation_id`).                                                | **Verified** (`schedule-drafts.spec.ts` "SPK-SCHED-006: publication commits ... and an operation"; `0100_identity_core.sql`, `0300_scheduling_core.sql`)                                                 |
| `OperationAccepted` envelope  | `{ operationId: uuid, status, href: string }` returned with 202 by commands that complete asynchronously (registration checkout, refund, bulk notice send).                                                                                                                                                                                                                                                         | **Verified** schema (`OperationAcceptedSchema`); **Proposed** usage (no endpoint returns it; `POST /v1/schedule-drafts/{id}/publish` returns 200 with the `Publication` carrying `operationId`)          |
| Required follow-up never lost | An operation that ends `failed` or `recovery_required` has an `operational_exceptions` row with an `owner_queue`, so the Today workspace shows it (SPK-UX-006, §4.7 invariant 12). The dispatcher already does this for dead-lettered follow-ups.                                                                                                                                                                   | **Verified** for dead letters (`outbox.spec.ts` "dead-letters after max attempts and raises an owned operational exception"); **Proposed** as a rule for every operation producer                        |

## 6. Error contract (§4.10)

### 6.1 Response body

Every error, from any layer, is rendered by `DomainExceptionFilter` as:

| Field           | Type              | Rule                                                                                                                                                                                           | Status                                                                    |
| --------------- | ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `code`          | string            | One of the stable codes in section 6.2 (§4.10 "stable code").                                                                                                                                  | **Verified**                                                              |
| `message`       | string            | Safe for display; never reveals another household's record existence (§4.10).                                                                                                                  | **Verified**                                                              |
| `correlationId` | string            | The request's `X-Correlation-Id` (§4.10 "correlation reference"); on an idempotent replay the stored body is re-stamped with the new id.                                                       | **Verified**                                                              |
| `nextAction`    | string            | The permitted next action (§4.10); defaults per code in section 6.2, overridable per error.                                                                                                    | **Verified**                                                              |
| `details`       | unknown, optional | Structured context: validation issues, `{ expectedRevision, currentRevision }`, `{ machine, from, event }`, scheduling `conflicts[]`. Omitted for `INTERNAL_ERROR` (no internal details leak). | **Verified** (`idempotency.spec.ts` asserts `details` undefined on a 500) |

Source: `packages/contracts/src/errors.ts` (`ErrorResponseBody`, `DomainError.toResponseBody`), `apps/api/src/kernel/http/domain-exception.filter.ts`, `packages/contracts/src/openapi.ts` (`ErrorResponse` component). **Verified** by `auth-and-operations.spec.ts`, `idempotency.spec.ts`, `authorization.spec.ts`.

### 8.3 Dispatcher semantics (outbox)

| Behaviour                                                                                                                                                                                                                                                                                   | Status                                                                                                                                          |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Worker process: `apps/api/src/worker.ts` runs `OutboxDispatcher.start()` (poll every `OUTBOX_POLL_INTERVAL_MS`, default 1000 ms) and `Inbox.runOnce()` on the same interval; several workers may run at once; `WORKER_ID` defaults to hostname and pid.                                     | **Verified** code (`worker.ts`, `config.ts`); the process itself is not under test, the `runOnce` paths are                                     |
| Claim: `FOR UPDATE SKIP LOCKED` over `status = 'pending' and available_at <= now and (locked_until is null or locked_until < now)`, ordered by `available_at, occurred_at`, batch `OUTBOX_BATCH_SIZE` (default 25), lease `OUTBOX_LOCK_LEASE_SECONDS` (default 60).                         | **Verified** (`outbox-dispatcher.ts` `claim`; `core-schema.spec.ts` "outbox claim with FOR UPDATE SKIP LOCKED returns each pending event once") |
| Each registered handler runs in its own transaction together with an `event_consumptions (handler, event_id)` insert; if the row already exists the handler is skipped (`job_attempts.outcome = 'skipped'`). One logical business effect per handler per event, even when delivery repeats. | **Verified** (`outbox.spec.ts` "dispatches each event to every handler exactly once, even when redelivered")                                    |
| A `job_attempts` row is written per handler run with `worker_id`, `attempt_number`, `outcome` (`succeeded`, `failed`, `skipped`) and the error text.                                                                                                                                        | **Verified** (`outbox.spec.ts`)                                                                                                                 |
| Retry: if any handler fails the event stays `pending` with `available_at = now + min(1000 ms * 2^attempt, 10 minutes)` and `attempts` incremented; handlers that already succeeded are not re-run (their consumption row exists).                                                           | **Verified** (`outbox.spec.ts` "retries a failing handler with backoff without re-running handlers that succeeded"; `retryDelayMs`)             |

| Interruption: an expired lease makes the event claimable again, so a worker that stops mid-batch is recovered by any worker (SPK-AT-023 "Worker stops after registration commit").                                                                                                          | **Verified** (`outbox.spec.ts` "reclaims events whose worker died (expired lease)")                                                             |
| Delivery guarantee: at-least-once delivery to each handler; exactly-once business effect per `(handler, event)`; no ordering guarantee between events (retries reorder), so handlers must not assume order.                                                                                 | **Verified** mechanics; the "no ordering" consequence is a **Proposed** consumer rule                                                           |
| Exactly-once network delivery is not assumed (§4.12); a handler that calls a provider must do so outside its transaction and record the outcome as a fact, keeping `unknown` explicit until reconciled.                                                                                     | **Proposed** rule (`CLAUDE.md` "Command pattern" step 4; no provider adapter exists)                                                            |

## 12. Specification ambiguities encountered

1. §4.9 says "A replay with the same key and payload returns the same operation" while the kernel replays the stored HTTP response. For synchronous commands these coincide; for asynchronous commands the `idempotency_keys.operation_id` column must be populated so the replayed 202 names the same operation. Recorded as **Proposed** in section 3.
2. §4.8 lists `POST /v1/registration-quotes` and `POST /v1/registration-checkouts` without an owning module; §4.2 gives quotes and orders to finance and eligibility and capacity to enrollment. This document assigns both commands to finance as the coordinator (§4.11), calling enrollment and catalog ports.
3. §4.10 requires a "permitted next action" but gives no vocabulary. The `nextAction` strings in section 6.2 are the code's defaults; they are a closed, documented set here and **Proposed** as stable client-visible values.
4. §4.12 lists "Operation" as a job field for every job, but a follow-up for a synchronous command (for example `identity.access_grant_revoked`) has no operation. `operationId` is nullable in the envelope; the rule applies when an operation exists.
5. SPK-COMMS-002 "Cancellation" and "Schedule publication or change" overlap with `scheduling.event_changed` (`change = 'canceled'`); the catalogue maps one trigger to several events rather than inventing a duplicate `scheduling.event_canceled` type that would make consumers handle the same fact twice.
6. §4.6 names the machine "Payment attempt" and §4.4 the entity `PaymentAttempt`, while §4.8 names the route `POST /v1/payments/{id}/refunds`. The route is kept as written; `{id}` is the payment attempt id.
7. The workflow assignment for this document stated that only `GET /v1/operations/{id}` and `/v1/health` are Verified. On 2026-10-23 `docs/api/openapi.json` also publishes 27 identity and 31 scheduling operations with tests, including the §4.8 row `POST /v1/schedule-drafts/{id}/publish`; those are marked **Verified** with citations, because marking them Proposed would misstate the repository. `GET /v1/ready` is the reverse case: implemented but neither published nor tested, so it is **Proposed**.
8. The identity README lists communications as the consumer of `identity.access_grant_revoked`; no handler is registered anywhere today (the communications module is a scaffold), so every "Proposed consumers" entry in section 9.2 is a proposal and the dispatcher currently marks these events dispatched with no handler run.
