# API and event schemas

Status legend: **Verified** = implemented and tested in this repository today (file cited). **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval. **Pending decision** = needs an operator answer; the owner is named from specification §6.6. "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23). Repository state inspected 2026-10-24 (`docs/api/openapi.json` with 122 operations).

This is the "API and event schemas" artifact required by §6.7. It covers the versioned, command-oriented API contract (§4.8), command behaviour (§4.9), the error contract (§4.10) and background work: the domain event envelope, the transactional outbox and the provider inbox (§4.12), plus an event catalogue. The exact request and response schemas are generated into `docs/api/openapi.json` (`pnpm build && pnpm openapi`, `CLAUDE.md`); this document explains the conventions those schemas follow and marks what exists. The entities the commands act on are in `docs/architecture/domain-model.md`.

## 2. API conventions (§4.8)

| Convention           | Behaviour today                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Status                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Version prefix       | Every route is served under `/v1` (`API_PREFIX` in `apps/api/src/kernel/app-setup.ts`; `servers: [{ url: '/v1' }]` in `packages/contracts/src/openapi.ts`; OpenAPI `info.version` is `0.1.0`).                                                                                                                                                                                                                                                                                                                                                                                                                             | **Verified** (`auth-and-operations.spec.ts` requests `/v1/health`, `/v1/operations/{id}`)                                                                                                                                                                                                                                                                                                    |
| Versioning rule      | Additive changes (new optional fields, new paths, new error codes) stay in `/v1`. A change that removes or re-types a field, changes a lifecycle or changes an error code's meaning is served under a new prefix, and the old one is kept for the API compatibility window that §4.13 requires the mobile release to define.                                                                                                                                                                                                                                                                                               | **Proposed**; the window, the minimum supported app version and the update behavior are **Pending decision**: Technical lead/operator (no exact §6.6 row), DEC-061 (§4.13, SPK-AT-027); the error code an unsupported client receives is **Pending decision** (DEC-092)                                                                                                                      |

| Authentication       | Bearer token on every route unless the handler is marked `@Public()` (`/v1/health`, `/v1/dev/tokens`, and the catalog discovery reads `GET /v1/offerings`, `GET /v1/offerings/{id}` and `GET /v1/offerings/{id}/sessions`, which return published, child-safe fields only). | Request validation   | Bodies, query strings and path parameters are parsed by zod schemas (`@ZodBody`, `@ZodQuery`, `@ZodParams`); failures are `VALIDATION_FAILED` (400) with `details[]` of `{ path, message, code }`.                                                                                                                                                                                                                                                                                                                                                                                                                         | **Verified** (`apps/api/src/kernel/http/zod-validation.pipe.ts`; `auth-and-operations.spec.ts` "validates path parameters with the error contract")                                                                                                                                                                                                                                          |
| Identifiers          | Every id is an application-generated time-ordered UUID v7 (`newId()`); clients never choose ids.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | **Verified** (`packages/contracts/src/ids.ts`, `ids.spec.ts`)                                                                                                                                                                                                                                                                                                                                |

### 2.1 Headers

| Header                | Direction | Rule                                                                                                                                                                                                                                                                                                                                      | Status                                                                                                                                                 |

| `Authorization`       | request   | `Bearer <token>`; absent on `@Public()` routes gives the anonymous principal.                                                                                                                                                                                                                                                             | **Verified** (`auth.guard.ts`)                                                                                                                         |
| `Idempotency-Key`     | request   | Required on every handler marked `@Idempotent()` (all consequential `POST`, `PATCH`, `DELETE`); 8 to 128 characters (`IdempotencyKey` in `packages/contracts/src/commands.ts`, constant `IDEMPOTENCY_KEY_HEADER = 'idempotency-key'`); missing or malformed is `VALIDATION_FAILED` (400). | `Idempotent-Replayed` | response  | `true` when the response is a stored replay for the same key and payload.                                                                                                                                                                                                                                                                 | **Verified** (`idempotency.spec.ts` "replays the same key + payload without re-executing")                                                             |

## 3. Idempotency semantics (§4.9)

| Rule                                                                                | Mechanism                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Status                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A replay with the same key and payload returns the same operation (§4.9).           | The key is stored with a SHA-256 hash of the canonical JSON of `{ method, path, body }` (key order ignored, `undefined` dropped); the stored status and body are replayed with `Idempotent-Replayed: true` and the handler is not executed again.                                                                                                                                                                                                                                                                                                                          | **Verified** (`idempotency.spec.ts` "replays the same key + payload without re-executing"; `people.spec.ts` "§4.9: POST /v1/people replays ... without creating a second person"; `resources.spec.ts` "idempotent replay creates one resource"; `programs-and-entitlements.spec.ts` "§4.9: creating a program is idempotent; the same key replays without a second row"; `offerings.spec.ts` "§4.9: offering creation replays on the same idempotency key"; `restrictions.spec.ts` "authorization, idempotency and uniqueness: ... replays return the same restriction") |
| The same key with different contents returns a conflict (§4.9).                     | Hash mismatch is `IDEMPOTENCY_CONFLICT` (409, next action `use_new_idempotency_key`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | **Verified** (`idempotency.spec.ts`)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| A key still executing cannot be raced.                                              | The claim is an insert with `on conflict do nothing` inside a transaction; a second request while the first is `in_progress` within its lease (`IDEMPOTENCY_LEASE_SECONDS`) is `IDEMPOTENCY_IN_PROGRESS` (409, `retry_later_with_same_key`). After the lease lapses a retry takes the key over (new `claim_token`) only when nothing committed; the stalled request's commit is then rolled back by the fence, and a claim that committed answers `IDEMPOTENCY_OUTCOME_UNAVAILABLE`.                                                                                       | **Verified** (`idempotency.spec.ts` "a retry while the first request still runs gets IDEMPOTENCY_IN_PROGRESS; a request that committed and then stopped is never run again", "a request that stopped before committing is retried once its lease lapses, and the stalled request can no longer commit"; both pass on PGlite and on PostgreSQL)                                                                                                                                                                                                                           |
| Keys are scoped so one customer cannot replay another's command.                    | Primary key `(organization_id, scope_key, idempotency_key)` where `scope_key` is `account:<accountId>` or `<kind>:<actorLabel>` for principals without an account.                                                                                                                                                                                                                                                                                                                                                                                                         | **Verified** (`idempotency.spec.ts` "keys are scoped per account"; `core-schema.spec.ts` "idempotency keys are unique per organization and scope")                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Domain outcomes are replayed; infrastructure failures are retryable.                | A `DomainError` with status < 500 is stored and replayed (with a fresh `correlationId`). A 5xx or unexpected error releases the key so the client may retry with the same key only when nothing committed during the request; after a commit (recorded on the key by the commit fence inside the business transaction) it is stored and replayed instead, so the command never runs twice.                                                                                                                                                                                 | **Verified** (`idempotency.spec.ts` "stores domain (4xx) failures", "releases the key after an unexpected (5xx) failure", "a 5xx after the command committed is recorded and replayed, not re-executed")                                                                                                                                                                                                                                                                                                                                                                 |
| Keys expire.                                                                        | `expires_at = now + IDEMPOTENCY_TTL_HOURS` (configuration default 24); expired keys are deleted on the next claim and may be reused, and the worker's `IdempotencySweeper` deletes every record past its expiry (every `IDEMPOTENCY_SWEEP_INTERVAL_MS`, default 60 s).                                                                                                                                                                                                                                                                                                     | **Verified** (`idempotency.spec.ts` "expired keys can be reused", "the sweep deletes records past their expiry and keeps live ones"; `apps/api/src/kernel/config.ts`, `apps/api/src/kernel/http/idempotency-sweeper.ts`)                                                                                                                                                                                                                                                                                                                                                 |
| One-time secrets never rest in the idempotency store (§4.14).                       | `@Idempotent({ withhold: [...] })` stores the success body without the named top-level fields; the original response still carries them. A replay of such a command answers `IDEMPOTENCY_SECRET_WITHHELD` (409, `revoke_and_reissue`, `details.resourceId`) instead of re-running it. Applied to `POST /invitations` and `/people/{id}/claims` (`token`), `/team-entries/{id}/invitations` (`token`), `/reports/exports` (`downloadToken`) and `/me/calendar-feeds` (`token`, `path`). Migration `0004_core_idempotency_secret_purge.sql` stripped secrets stored earlier. | **Verified** (`idempotency.spec.ts` "§4.14: one-time secrets never rest in the idempotency store"; one test per endpoint in `invitations.spec.ts`, `claims-and-accounts.spec.ts`, `rosters.spec.ts`, `exports.spec.ts`, `calendar-feeds.spec.ts`)                                                                                                                                                                                                                                                                                                                        |
| A command's key points at its operation so a replay returns the same `operationId`. | `OperationsService.create` links the request's key to the operation through the commit fence, in the same transaction (`idempotency_keys.operation_id`, organization-scoped foreign key since `0005`): the first operation of the request, unless a coordinator passes `primary: true` (the registration checkout does, §4.11 step 4). A 5xx after a commit and `IDEMPOTENCY_OUTCOME_UNAVAILABLE` carry `details.operationId`, in the first response and in every replay, so the client polls `GET /v1/operations/{id}`.                                                   | **Verified** (`idempotency.spec.ts` "§4.9: an idempotency key names the operation its command started"; `checkout.spec.ts` "§4.11: checkout acquires holds ..."; PGlite and PostgreSQL)                                                                                                                                                                                                                                                                                                                                                                                  |
| Replay never re-executes a provider call.                                           | Provider calls happen outside the database transaction and their outcome is recorded as a fact (payment attempt, delivery attempt); a replayed command returns the recorded outcome.                                                                                                                                                                                                                                                                                                                                                                                       | **Proposed** rule (`CLAUDE.md` "Command pattern" step 4); no provider adapter exists (§5.2, **Pending decision**: Technical lead/account owners, DEC-018, DEC-019, DEC-020)                                                                                                                                                                                                                                                                                                                                                                                              |

### 8.3 Dispatcher semantics (outbox)

| Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Status                                                                                                                                                                                                     |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## 12. Specification ambiguities encountered

1. §4.9 says "A replay with the same key and payload returns the same operation" while the kernel replays the stored HTTP response. For synchronous commands these coincide; for asynchronous commands the `idempotency_keys.operation_id` column must be populated so the replayed 202 names the same operation. Recorded as **Proposed** in section 3.
2. §4.8 lists `POST /v1/registration-quotes` and `POST /v1/registration-checkouts` without an owning module; §4.2 gives quotes and orders to finance and eligibility and capacity to enrollment. This document assigns both commands to finance as the coordinator (§4.11), calling enrollment and catalog ports.
3. §4.10 requires a "permitted next action" but gives no vocabulary. The `nextAction` strings in section 6.2 are the code's defaults; they are a closed, documented set here and **Proposed** as stable client-visible values.
4. §4.12 lists "Operation" as a job field for every job, but a follow-up for a synchronous command (for example `identity.access_grant_revoked`) has no operation. `operationId` is nullable in the envelope; the rule applies when an operation exists.
5. SPK-COMMS-002 "Cancellation" and "Schedule publication or change" overlap with `scheduling.event_changed` (`change = 'canceled'`); the catalogue maps one trigger to several events rather than inventing a duplicate `scheduling.event_canceled` type that would make consumers handle the same fact twice.
6. §4.6 names the machine "Payment attempt" and §4.4 the entity `PaymentAttempt`, while §4.8 names the route `POST /v1/payments/{id}/refunds`. The route is kept as written; `{id}` is the payment attempt id.
7. The workflow assignment for this document stated that only `GET /v1/operations/{id}` and `/v1/health` are Verified. On 2026-10-24 `docs/api/openapi.json` publishes 122 operations with tests: 27 identity, 40 catalog, 31 scheduling and 22 facilities beside the two kernel routes, including the §4.8 rows `POST /v1/schedule-drafts/{id}/publish` and `POST /v1/maintenance-restrictions`; those are marked **Verified** with citations, because marking them Proposed would misstate the repository. `GET /v1/ready` is the reverse case: implemented but neither published nor tested, so it is **Proposed**.
8. The identity README lists communications as the consumer of `identity.access_grant_revoked`; no handler for any identity event is registered today (the communications module is a scaffold), so every "Proposed consumers" entry in section 9.2 is a proposal and the dispatcher currently marks those events dispatched with no handler run; the only consumers that exist are the two facilities handlers.
9. §4.8 names `POST /v1/maintenance-restrictions` "Apply an approved operating restriction". The implementation proposes and approves in one request by default (the approval rule is pending, permission matrix C.10) and activates through the scheduling closure port between transactions, so an interruption leaves an `approved` restriction that `POST /v1/maintenance-restrictions/{id}/approve` resumes. The §4.8 wording is read as the outcome (an approved restriction applied to the schedule), not as a requirement that approval precede the request.
10. `docs/api/openapi.json` was regenerated by the module build workflow while this document was being written (60 operations at the first read on 2026-10-23, 122 at the last on 2026-10-24). Sections 2, 7 and 9 are a snapshot of the later state and must be re-derived when further modules land.
