# Metric dictionary

Status legend: **Verified** = implemented and tested in this repository today (file cited); **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval; **Pending decision** = needs an operator answer (owner named from spec §6.6). "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23).

This is the "Metric dictionary" artifact of §6.7. It defines every metric implied by SPK-REPORT-002 to SPK-REPORT-006 and by the §1.2 success measures, each with the SPK-REPORT-001 fields. Companion documents: `permission-matrix.md` (section C.14, the proposed `reporting.*` action identifiers used in the access-scope column), `decision-register.md` (`DEC-###`), `policy-register.md` (`POL-###`), `competitive-proof-plan.md` (how the §1.2 benchmark metrics are measured), `native-acceptance-matrix.md`.

## 1. What this document is

- One record per metric, `MET-001` to `MET-105`, grouped by the report or requirement that implies it (sections 4 to 9).
- Every record carries the SPK-REPORT-001 fields. The specification lists nine bullets, with "Numerator and denominator" as one bullet; this document shows numerator and denominator in separate columns, so each row has ten field columns plus requirement id and status.
- Every metric is **Proposed** as a definition until an operator agrees it. **Verified 2026-10-30 (correction of the 2026-10-24 inspection, which found reporting a scaffold and no 1300 migration):** the reporting module is implemented (`apps/api/src/modules/reporting/README.md`; `packages/db/migrations/1300_reporting_core.sql` with `metric_definitions`, report runs and exports; tests in `apps/api/src/modules/reporting/__tests__/`, among them `metric-definitions.spec.ts`), and its code names 63 of the `MET-###` keys of this dictionary. Every source module is implemented too: kernel, identity, catalog, scheduling, competition, enrollment, finance, workforce, entry, facilities, communications, support and migration (`docs/architecture/domain-model.md` section 3 names each table and its migration). A row that says "sources Verified" cites its table and a test; a row that says only **Proposed** has no source citation yet, which is a gap in this document, not a statement that the source is missing. Thresholds, weightings, allocation methods, cost inputs and period definitions stay **Pending decision**.
- No facility fact appears here: no field name, operating hour, price, tax, vendor, staff count, threshold or target. Where a metric needs a threshold, a weighting, an allocation method, a cost input or a period definition, the record names the pending decision and its §6.6 owner.
- The "original platform specification" (`.docx`, §1.3 item 1) and the "existing local demonstration" (§1.4) are not in this repository. No legacy metric or report of the demonstration is cited.

## 3. Vocabularies used in the metric tables

### 3.1 Time basis codes

| Code     | Meaning                                                                                                                                        |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| T-DAY    | Facility-local operating day of the scheduled start (G4), with as-of instant (G3).                                                             |
| T-WEEK   | Facility-local week (first day of week is an Operations choice under DEC-001; until answered, Monday is used and disclosed).                   |
| T-PERIOD | A viewer-selected facility-local period (day, week, month) with as-of instant. Financial metrics use closed periods only unless marked "live". |
| T-SEASON | The competition season's dates (SPK-COMP-001), with the cohort rules of section 7.1.                                                           |
| T-TERM   | The offering's dates (SPK-CAT-001), with the cohort rules of section 7.1.                                                                      |
| T-EVENT  | The event's scheduled interval and lead time before its scheduled start.                                                                       |
| T-LIVE   | The request instant; the as-of instant is "now" and is still displayed.                                                                        |

| Code    | Meaning                                                                                                       |
| ------- | ------------------------------------------------------------------------------------------------------------- |

### 3.5 Grain vocabulary

Grain names the record one row represents before aggregation: `event` (`events` row), `fixture`, `session`, `enrollment`, `application`, `checkout`, `hold`, `team entry`, `person`, `household`, `obligation`, `payment attempt`, `refund attempt`, `assignment slot`, `notification`, `conflict unit x day`, `resource x day`, `offering`, `task run`. Dimensions are the columns a viewer may group or filter by; every metric also allows `facility`.

## 9. §1.2 success measures

§1.2 requires "measurable improvements" in ten areas and says "feature availability alone does not establish superiority. The product must demonstrate better outcomes through realistic, repeatable tasks." §6.3 names the four task measurements (task completion, errors, time, assistance required). Two kinds of metric therefore apply: benchmark task metrics (9.1), measured in acceptance sessions and in the competitive proof under `competitive-proof-plan.md`, and operating outcome metrics (9.2), measured in production reports. No target value appears anywhere in this document; targets are set after baseline measurement (§6.4, DEC-045).
