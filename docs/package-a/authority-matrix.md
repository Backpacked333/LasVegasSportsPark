# Authority matrix and migration mappings

Status legend: **Verified** = implemented and tested in this repository today (file cited). **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval. **Pending decision** = needs an operator answer; the owner is named from specification §6.6. "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23). Repository last inspected for this revision on 2026-10-24.

This file is the Package A "Authority matrix" deliverable (§6.5) and both halves of the §6.7 handoff artifact "Migration mappings and authority matrix". Sections 1 to 10 are the authority half: they implement §5.6 ("One authority during transition"), feed the cutover runbook of §5.7 and the recovery rules of §5.8, and exist to satisfy integrity invariant §4.7 (11): no duplicated authority during migration. Section 11 is the migration-mappings half: one mapping table per §5.3 category (source element, target table and column, key handling, review rule), the §5.4 batch record and the review queues. Section 11 is a template; every legacy-side cell is empty and **Pending decision** (DEC-014, Migration owner/operator).

Companion documents: [`integration-register.md`](integration-register.md) (entry 4.12, the DaySmart data source), [`decision-register.md`](decision-register.md) (every `DEC-###` cited below), [`facility-inventory.md`](facility-inventory.md) (the physical inventory that row 18 is assigned over), [`role-matrix.md`](role-matrix.md), [`requirement-cross-reference.md`](requirement-cross-reference.md), [`acceptance-fixtures.md`](acceptance-fixtures.md) (SPK-AT-024 reimport fixture), [`../runbooks/cutover.md`](../runbooks/cutover.md) (§5.7, mapped in section 5), [`../runbooks/recovery.md`](../runbooks/recovery.md) (§5.8, mapped in section 6), [`../architecture/domain-model.md`](../architecture/domain-model.md) (sections 3.12 and 5.4, the proposed migration entities).

Every phase assignment in this document is **Proposed** and waits on DEC-014 "Migration scope and writer authority" (required owner: Migration owner/operator; must be resolved before Cutover (Package F)). The legacy system is DaySmart, named in §1.2 as the system to be replaced. Nothing about DaySmart's data model, export format, field names, identifier scheme or behaviour is in this repository and nothing about it is asserted here. The original platform specification (`.docx`, §1.3 item 1) and the existing local demonstration (§1.4) are also **not in this repository**; nothing below is derived from either, and no legacy requirement identifier or demonstration behaviour is cited.

## 2. Definitions

All definitions are **Proposed** readings of §5.3 to §5.8 unless marked otherwise.

| Term                   | Meaning in this document                                                                                                                                                                                                                                                                                                                                   |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Record category        | One of the seventeen §5.3 inventory categories, plus "field reservations" (physical occupancy of pitches and subdivisions). Reservations are separated from "future schedules" because §5.6 makes shared pitches a distinct authority problem: an event's content and the physical space it occupies can have different writers during transition.         |
| Scope                  | The unit at which authority is assigned inside a category: organization, facility, pitch (with its subdivisions), season, offering, team, household, person, order, obligation, payment, document. The matrix names the scope unit for each category.                                                                                                      |
| Effective writer       | The one system whose writes to a record in a given scope and phase are authoritative. Any other representation of that record is a synchronized copy.                                                                                                                                                                                                      |
| Synchronized copy      | A representation produced by import or export from the effective writer. It is read-only in the receiving system. It never accepts a write that is later merged back; "a synchronized copy does not become an independent writer" (§5.6).                                                                                                                  |
| Periodic import        | A copy mechanism with a window between runs. It discovers conflicts after the fact and cannot prevent them (§5.6); see section 7.                                                                                                                                                                                                                          |
| Migrated activity      | An offering, season or team entry inside the approved pilot scope (§6.5 Package F proposes one complete adult-league workflow and one complete youth-program workflow, subject to operator confirmation, DEC-046). Which activities are migrated is part of DEC-014.                                                                                       |
| Non-migrated activity  | Everything the complex continues to run in the legacy system during transition.                                                                                                                                                                                                                                                                            |
| Before cutover         | The phase before any transition step of §5.7 has run. The legacy system is the effective writer of every category and scope; Sportspark holds at most rehearsal imports (Package F "Rehearsed import") that are discarded or reimported.                                                                                                                   |
| During transition      | From the first authority assignment taking effect (typically "Schedule authority" or "Customer activation" of §5.7) until the final cutover reconciliation is accepted. Authority is split by category and scope exactly as the matrix states; every record has one writer.                                                                                |
| After cutover          | From acceptance of the §5.7 reconciliation. Sportspark is the effective writer of every category and scope; the legacy system is frozen as a reference copy for the retention period decided under DEC-084 (see `integration-register.md` entry 4.12 "Exit procedure").                                                                                    |
| Handback               | An explicit reassignment of authority from Sportspark back to the legacy system for a category and scope under §5.8. It is itself an authority assignment record with effective dates; it is never implied by a database restore.                                                                                                                          |
| Authority assignment   | The record that states, for one category and one scope, which system is the effective writer from which instant, who decided it and on what evidence (§4.4 `AuthorityAssignment`; `apps/api/src/modules/migration/README.md` "authority assignments", scaffold). The matrix below is the initial content of that record set; section 8 proposes its shape. |
| External mapping       | The record that links one source identifier, in one source system and one record category, to exactly one Sportspark record (§4.4 `ExternalMapping`; §5.3 "Preserve external identifiers and extraction provenance"). It is the only migration key; names and emails never are (§5.3). Section 11.3 proposes its key.                                      |
| Import batch           | One execution of the repeatable import over one extract, retaining the seven §5.4 fields (source, timestamp, checksum, transformation version, row outcomes, validation errors, review decisions). Section 11.2 proposes its shape.                                                                                                                        |
| Transformation version | The identifier of the exact set of mapping rules (section 11.4) applied by a batch. Any change to a key rule, conversion or review rule of a mapping table produces a new version; every batch records the version it applied (§5.4).                                                                                                                      |

## 7. Why periodic imports cannot prevent conflicting reservations

**Proposed** explanation of §5.6, provided so the runbook and the training material state the same reasoning.

1. At the last import both systems hold the same reservations for pitch X.
2. The legacy system accepts a rental for pitch X from 18:00 to 19:00.
3. Sportspark publishes a fixture on pitch X from 18:30 to 19:30. Its conflict check passes: the rental has not been imported yet, so the exclusion constraint sees no overlap. Both customers have now been told their booking is confirmed.
4. The next import brings the rental into Sportspark. The conflict is discovered after the fact, and one of the two customers must be moved. Shortening the import interval shrinks the window but never closes it, and raising the import frequency does not change step 3.

The only prevention is that one system does not accept bookings for pitch X at all (rule 3 and rule 5). Sportspark's database guarantee of no overlapping exclusive reservation (§4.7 (4)) applies only to writes Sportspark itself accepts; it cannot see a booking that exists only in legacy.

## 10. Maintenance rules

1. A record category enters the migration scope only with a row in section 4 that names its scope unit, owning module and all three phase writers, and a mapping table in section 11.4. A category without both is not migrated and is not written in Sportspark during transition.
2. Phase assignments change only through a decision register entry owned by the Migration owner/operator; this file is updated in the same change with the decision identifier.
3. When the migration module implements `AuthorityAssignment`, section 4 is regenerated from the recorded assignments and this hand-maintained table is retired; until then the table is the source.
4. Every cutover rehearsal (Package F "Rehearsed import") produces a reconciliation report referenced from the affected rows' evidence; a row with no rehearsal evidence cannot move to "After cutover".
5. Keep row 18 consistent with [`facility-inventory.md`](facility-inventory.md): every pitch in its section 4 table (and every subdivision through its parent) has exactly one row-18 assignment per phase. The inventory exists as a template with zero real rows today (its section 1, **Pending decision**, DEC-001, Operations), so no per-pitch assignment can be recorded yet.
6. Keep this file consistent with `integration-register.md` entry 4.12 (data source, extraction, exit), with `role-matrix.md` section 7 item 7 (which staff roles hold the §5.5 approvals), with `../runbooks/cutover.md` (section 5 above) and `../runbooks/recovery.md` (section 6 above).
7. A section 11 target that names a table or column changes in the same change as any migration that alters it. A **Proposed** target becomes **Verified** only when the owning module's migration file and a test that exercises the column are cited.

## 12. Specification ambiguities and consistency notes

1. **§5.3 names no "enrollments" category**, while §5.5 compares "active rosters" and "capacity" and `acceptance-fixtures.md` SPK-AT-024 imports enrollments. This document maps youth-program participation under programs and offerings (table 11.4.5, row 5) and adult team participation under rosters (table 11.4.8, row 8). **Proposed**; **Pending decision** (DEC-014).
2. **§5.3 names no facility or space category**, yet future schedules and reservations cannot be mapped without legacy space identifiers. Table 11.4.19 links them to the inventory that Operations supplies (`facility-inventory.md`). **Proposed**; **Pending decision** (DEC-001, DEC-014).
3. **"Refunds" is a §5.3 category, but a legacy refund cannot be executed again** (§5.4). It is mapped as a historical reconciling fact rather than a `RefundAttempt` (table 11.4.15). **Proposed**; **Pending decision** (DEC-009).
4. **§5.7 is silent on whether the first publication of imported schedules notifies customers**, while §5.4 forbids historical notifications on reimport. **Pending decision** (DEC-012, Operator/privacy owner); also `../runbooks/cutover.md` section 9.
5. **Shape differences with `../architecture/domain-model.md` section 5.4.** That diagram draws `AuthorityAssignment` with `facility_id` as its only scope and `ImportException` with three categories. This document proposes `scope_type` and `scope_id` (section 8, because the scope units of section 4 are finer than a facility) and seven categories (section 11.5). **Proposed** edit to `domain-model.md`; not made here because this revision's write scope is this file.
6. **`../runbooks/cutover.md` section 5 cites "authority matrix section 5, rule 2"**; the rule is section 3 rule 2 of this file. **Proposed** edit to `cutover.md`.
7. **`acceptance-fixtures.md` SPK-AT-024 step 5 cites "section 9, item 1 for the code choice"**; the refusal code is proposed in section 8 and registered as DEC-083 (section 9). **Proposed** edit to `acceptance-fixtures.md`.
8. **Provenance columns differ by module.** `persons.source` and `relationships.source` admit `import`; `roster_memberships.source` does not; `teams` and `communication_preferences` have no provenance column (all **Verified** by reading `0100`, `0400`, `1000`). Whether those modules add an `import` value or flag in their own migration ranges, or rely on `external_mappings` alone, is an engineering choice for the owning modules. **Proposed**; scope **Pending decision** (DEC-014).
9. **`access_grants.source` admits `import`** (`0100_identity_core.sql`) while SPK-IAM-007 forbids importing unverified permissions. This document proposes that no import batch writes `access_grants` (table 11.4.3; check in section 11.6). Whether imported links may exist as `relationships` rows without grants is **Pending decision** (DEC-004).
10. **Owner wording in section 9 now follows `decision-register.md` verbatim** (its rule 10.1(7) and the section 10.3 rows for this file): DEC-083 cites "Technical lead/operator" rather than "Technical lead"; DEC-084 and DEC-046 are cited by identifier. The pilot-scope owner is "Sponsor; Product owner" (DEC-046), not the Migration owner/operator named in earlier revisions of this file.
