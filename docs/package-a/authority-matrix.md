# Authority matrix

Status legend: **Verified** = implemented and tested in this repository today (file cited). **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval. **Pending decision** = needs an operator answer; the owner is named from specification §6.6. "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23).

This is the Package A "Authority matrix" deliverable (§6.5) and the authority half of the "Migration mappings and authority matrix" handoff artifact (§6.7). It implements §5.6 ("One authority during transition") and feeds the cutover runbook of §5.7 and the recovery rules of §5.8. It exists to satisfy integrity invariant §4.7 (11): no duplicated authority during migration. Companion documents: [`integration-register.md`](integration-register.md) (entry 4.12, the DaySmart data source), `decision-register.md` (owners and target dates for every pending decision named below), [`role-matrix.md`](role-matrix.md), [`requirement-cross-reference.md`](requirement-cross-reference.md).

Every phase assignment in this document is **Proposed** and waits on the §6.6 decision "Migration scope and writer authority" (owner: Migration owner/operator; must be resolved before cutover). The legacy system is DaySmart, named in §1.2 as the system to be replaced. Nothing about DaySmart's data model or behaviour is in this repository and nothing about it is asserted here. The original platform specification (`.docx`, §1.3 item 1) and the existing local demonstration (§1.4) are also **not in this repository**; nothing below is derived from either.

## 2. Definitions

All definitions are **Proposed** readings of §5.6 to §5.8 unless marked otherwise.

| Term                  | Meaning in this document                                                                                                                                                                                                                                                                                                                           |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Record category       | One of the seventeen §5.3 inventory categories, plus "field reservations" (physical occupancy of pitches and subdivisions). Reservations are separated from "future schedules" because §5.6 makes shared pitches a distinct authority problem: an event's content and the physical space it occupies can have different writers during transition. |
| Scope                 | The unit at which authority is assigned inside a category: organization, facility, pitch (with its subdivisions), season, offering, team, household, person, order, obligation, payment, document. The matrix names the scope unit for each category.                                                                                              |
| Effective writer      | The one system whose writes to a record in a given scope and phase are authoritative. Any other representation of that record is a synchronized copy.                                                                                                                                                                                              |
| Synchronized copy     | A representation produced by import or export from the effective writer. It is read-only in the receiving system. It never accepts a write that is later merged back; "a synchronized copy does not become an independent writer" (§5.6).                                                                                                          |
| Periodic import       | A copy mechanism with a window between runs. It discovers conflicts after the fact and cannot prevent them (§5.6); see section 7.                                                                                                                                                                                                                  |
| Migrated activity     | An offering, season or team entry inside the approved pilot scope (§6.5 Package F proposes one complete adult-league workflow and one complete youth-program workflow, subject to operator confirmation). Which activities are migrated is part of the pending decision "Migration scope and writer authority".                                    |
| Non-migrated activity | Everything the complex continues to run in the legacy system during transition.                                                                                                                                                                                                                                                                    |
| Before cutover        | The phase before any transition step of §5.7 has run. The legacy system is the effective writer of every category and scope; Sportspark holds at most rehearsal imports (Package F "Rehearsed import") that are discarded or reimported.                                                                                                           |
| During transition     | From the first authority assignment taking effect (typically "Schedule authority" or "Customer activation" of §5.7) until the final cutover reconciliation is accepted. Authority is split by category and scope exactly as the matrix states; every record has one writer.                                                                        |
| After cutover         | From acceptance of the §5.7 reconciliation. Sportspark is the effective writer of every category and scope; the legacy system is frozen as a reference copy for the retention period decided by the migration owner (see `integration-register.md` entry 4.12 "Exit procedure").                                                                   |
| Handback              | An explicit reassignment of authority from Sportspark back to the legacy system for a category and scope under §5.8. It is itself an authority assignment record with effective dates; it is never implied by a database restore.                                                                                                                  |
| Authority assignment  | The record that states, for one category and one scope, which system is the effective writer from which instant, who decided it and on what evidence (§4.4 `AuthorityAssignment`; `apps/api/src/modules/migration/README.md` "authority assignments", scaffold). The matrix below is the initial content of that record set.                       |

### 4.1 Scope notes

- Rows 1, 2 and 17 switch writer at the same instant for one household ("activation"). Activation is a Sportspark command in the identity module that records the assignment for every person in the household; it requires the guardian verification policy to be approved first (**Pending decision**, Operator/privacy owner).
- Rows 6, 8, 9 and 11 switch together per season. A season is never split: there is no state in which legacy writes a season's fixtures while Sportspark writes its results.
- Rows 12 to 15 switch per financial record, not per customer. One household can have a legacy-written order and a Sportspark-written order at the same time; each has one writer.
- Row 18 is assigned per pitch and overrides row 9 for physical occupancy. Closures and maintenance restrictions (SPK-FAC-003, SPK-FAC-005) are reservations for this purpose and follow the pitch's authority.
- Categories not in §5.3 (staff availability and assignments, maintenance assets, support cases, discipline records) are not assigned here. If the migration owner adds any of them to the migration scope, they get a row before the rehearsed import (section 10 rule 1).

## 7. Why periodic imports cannot prevent conflicting reservations

**Proposed** explanation of §5.6, provided so the runbook and the training material state the same reasoning.

1. At the last import both systems hold the same reservations for pitch X.
2. The legacy system accepts a rental for pitch X from 18:00 to 19:00.
3. Sportspark publishes a fixture on pitch X from 18:30 to 19:30. Its conflict check passes: the rental has not been imported yet, so the exclusion constraint sees no overlap. Both customers have now been told their booking is confirmed.
4. The next import brings the rental into Sportspark. The conflict is discovered after the fact, and one of the two customers must be moved. Shortening the import interval shrinks the window but never closes it, and raising the import frequency does not change step 3.

The only prevention is that one system does not accept bookings for pitch X at all (rule 3 and rule 5). Sportspark's database guarantee of no overlapping exclusive reservation (§4.7 (4); SPK-AT-008 "at most one conflicting reservation commits") applies to writes Sportspark accepts; it is **Verified** only that the required extension is installed and usable (`core-schema.spec.ts` "btree_gist exclusion constraints are available for reservation integrity"), while the scheduling module's exclusion constraint on `(organization, conflict unit, occupied interval)` is named in `apps/api/src/modules/scheduling/README.md` as intent and is **Proposed**.

The same reasoning applies to capacity (row 5: a seat sold in both systems) and to obligations (row 13: a payment collected in both), which is why rule 5 applies to every row, not only to pitches.

## 10. Maintenance rules

1. A record category enters the migration scope only with a row in section 4 that names its scope unit, owning module and all three phase writers. A category without a row is not migrated and is not written in Sportspark during transition.
2. Phase assignments change only through a decision register entry owned by the Migration owner/operator; this file is updated in the same change with the decision identifier.
3. When the migration module implements `AuthorityAssignment`, section 4 is regenerated from the recorded assignments and this hand-maintained table is retired; until then the table is the source.
4. Every cutover rehearsal (Package F "Rehearsed import") produces a reconciliation report referenced from the affected rows' evidence; a row with no rehearsal evidence cannot move to "After cutover".
5. Keep row 18 consistent with the Package A "Facility inventory" deliverable (§6.5) once it exists: every pitch in the inventory has exactly one row-18 assignment per phase.
6. Keep this file consistent with `integration-register.md` entry 4.12 (data source, extraction, exit) and with `role-matrix.md` section 7 item 7 (which staff roles hold the §5.5 approvals).
