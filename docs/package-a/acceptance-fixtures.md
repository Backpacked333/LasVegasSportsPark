# Acceptance fixtures

Status legend: **Verified** = implemented and tested in this repository today (file cited); **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval; **Pending decision** = needs an operator answer (owner named from spec §6.6). "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23). Repository tree last inspected 2026-10-24 (the inspection statements of sections 1, 3 and 4, the automation statuses of sections 7 and 8, and every action, event, port and state name of an implemented module were re-derived from the code on that date).

Package A deliverable "Acceptance fixtures" (§6.5). One fixture per end-to-end acceptance journey of §6.1, `SPK-AT-001` to `SPK-AT-028`. Companion documents in this folder: `requirement-cross-reference.md` (requirement-to-test matrix), `decision-register.md` (`DEC-###`), `policy-register.md` (`POL-###`), `permission-matrix.md` (proposed action identifiers), `authority-matrix.md` (writer authority during transition), `integration-register.md` (provider gates).

## 1. What this document is

- For each of the 28 acceptance journeys: the scenario and required outcome (verbatim from §6.1), the preconditions and synthetic fixture data, the step list, the expected observable results (API outcomes, error codes, record states, audit and outbox evidence), the §4.7 integrity invariants exercised, the owning module, the automation status, and a concurrency note where the journey is concurrency-sensitive.
- Every fixture is written so that it can become a test in `apps/api/src/modules/<module>/__tests__/` using `createTestApp()` from `apps/api/src/testing` (**Verified**: `apps/api/src/testing/test-app.ts`), with the test named after the `SPK-AT-###` id (CLAUDE.md "Tests").
- All names, prices, capacities, dates, durations, rule settings and refund behaviour below are synthetic examples, not approved policies (§1.4: "Synthetic names, prices, capacities, refund behavior, and competition settings are examples, not approved policies."). Where a fixture needs a value that only an operator can decide, the fixture names the pending decision and its §6.6 owner and uses an example value marked as such.
- **Verified** by inspection on 2026-10-24: `packages/db/migrations` holds six migrations (`0001_core_schema.sql`, `0100_identity_core.sql`, `0200_catalog_core.sql`, `0300_scheduling_core.sql`, `0400_competition_core.sql`, `0900_facilities_core.sql`); five module directories under `apps/api/src/modules/` are implemented with actions, events, ports, state machines, controllers, services and tests (`identity`, `catalog`, `scheduling`, `competition` part 1, `facilities`); the other nine (`automation`, `communications`, `enrollment`, `entry`, `finance`, `migration`, `reporting`, `support`, `workforce`) are scaffolds (README, `index.ts`, module file) with no actions, events, tables or tests; `docs/api/openapi.json` lists 117 paths under its `/v1` server prefix. Therefore a record shape, action identifier, event type, port or endpoint named in a fixture is **Verified** only when the row cites a kernel, contracts or implemented-module file; everything owned by a scaffold module is **Proposed**. Action identifiers of implemented modules are the ones registered in `<module>.actions.ts` (summarised in `permission-matrix.md` Part B, with the reconciliation of earlier proposed names in B.7); proposed identifiers for scaffold modules follow `permission-matrix.md` Part C; event types of implemented modules are the ones declared in `<module>.events.ts`, and proposed ones follow the `<module>.<past_tense>` convention of CLAUDE.md. Competition part 2 (results, standings, brackets, discipline, disputes, readiness evaluation, fixture generation) and the enrollment module are not in the inspected tree (competition README "Known gaps (part 2 and later)"); nothing from them is cited as implemented.
- The "original platform specification" (`.docx`, §1.3 item 1) and the "existing local demonstration" (§1.4) are **not** in this repository. No legacy requirement identifier and no demo behaviour is cited anywhere in this document. The native customer apps and the staff dashboard are not in this repository either (`docs/architecture/overview.md`, "Not in this repository"); fixtures that need a device (SPK-AT-018, SPK-AT-027) describe the API-observable part and name the native part as Pending.

## 2. How to read a fixture

| Field                          | Meaning                                                                                                                                                                                                     |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Scenario                       | The §6.1 scenario text, verbatim.                                                                                                                                                                           |
| Required outcome               | The §6.1 required outcome text, verbatim. The fixture passes only when every clause of it is observable.                                                                                                    |
| Specification                  | Requirement ids and section numbers the fixture exercises.                                                                                                                                                  |
| Owning module                  | The module whose test suite owns the journey test (first listed), then the modules whose commands it calls. Module ownership per §4.2 and `apps/api/src/modules/*/README.md`.                               |
| §4.7 invariants                | The numbered integrity invariants of §4.7 that the fixture proves, by number.                                                                                                                               |
| Automation status              | **Verified** with the test file and test titles when a passing test already covers part of the journey; otherwise "Pending: to be automated in `<module>` tests".                                           |
| Concurrency note               | Present when the journey depends on true concurrency or on replay. See section 6.                                                                                                                           |
| Pending decisions              | The `DEC-###` records (with §6.6 owner) that must be answered before the fixture's example values can be replaced by approved values and the journey can be operator-accepted.                              |
| Preconditions and fixture data | The synthetic records the test seeds, as shapes (handles, not database rows). Handles are `fx-...`; in a test each handle becomes a UUID v7 from `newId()` (**Verified**: `packages/contracts/src/ids.ts`). |
| Steps                          | What the test does, in order, naming the principal that acts.                                                                                                                                               |
| Expected observable results    | One row per observation: what is observed, where the evidence is (HTTP response, table, state machine), and the status of the statement.                                                                    |

## 6. Concurrency note (shared)

**Verified** (`docs/architecture/overview.md`, "Testing strategy"; `packages/db/src/testing.ts`): PGlite serializes transactions, so in the default `pnpm test` mode two "concurrent" requests run one after the other and a test can only prove that the second one is rejected. The CI job `test-postgres` runs the same suite against a PostgreSQL 18 service with `TEST_DATABASE_URL`, where transactions really interleave. `TestDatabase.concurrent` is `true` in that mode and `false` on PGlite, so a fixture can run its N-way parallel variant only when the database allows it and its sequential variant always.

Rules every concurrency-sensitive fixture follows:

1. The guarantee is a database constraint (unique or partial-unique index, check constraint, exclusion constraint) or a row lock taken before the decision; the application check only gives earlier feedback (§4.7, CLAUDE.md "Data rules").
2. The test has a sequential variant (passes on PGlite and PostgreSQL) and a parallel variant (asserted only when `concurrent` is true), and both assert the same end state.
3. Replay (the same delivery twice) is a separate variant from parallelism and passes in both modes.
4. A fixture marked concurrency-sensitive is not **Verified** until it passes in `test-postgres` (`requirement-cross-reference.md`, section 10).

Concurrency-sensitive fixtures: SPK-AT-004, 005, 006, 007, 008, 018 (replay), 020, 022, 023, 024 (replay), 028 (replay).

## 10. Maintenance rules

1. When a module implements a journey, replace "Pending: to be automated in `<module>` tests" with the test file path and the `it` titles, and change the affected rows from **Proposed** to **Verified** only for what the passing test asserts. A concurrency-sensitive row becomes **Verified** only after the `test-postgres` job has passed with the test present (section 6).
2. When an operator answers a decision, replace the example value with the approved one, cite the `DEC-###` record, and move the row from **Pending decision** to **Verified** (if implemented) or **Proposed** (if not). Never delete the example; mark it superseded.
3. When a fixture's handle is first used in code, keep the handle name in the test (`fx-guardian-alpha`) so that this document and the test read the same way.
4. Action identifiers and event types in this document follow `permission-matrix.md` Part C and CLAUDE.md; when `permission-matrix.generated.md` exists, this document is re-checked against it.
5. If the specification version changes, update the "Last derived from" line and re-derive sections 7 to 9 from §6.1 and §4.7; keep verbatim scenario and outcome text.
6. Nothing in this document may cite the original platform specification or the local demonstration until they are added to the repository (section 1).
