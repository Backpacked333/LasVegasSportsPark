# Screen and journey inventory

Status legend: **Verified** = implemented and tested in this repository today (file cited). **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval. **Pending decision** = needs an operator answer; the owner is named from specification §6.6. "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22).

This is the "Screen and journey inventory" handoff artifact of §6.7. Companion documents: [`journeys.md`](journeys.md) (the step tables this inventory indexes), [`permission-matrix.md`](permission-matrix.md) (the actions behind each screen's permission restriction state), [`decision-register.md`](decision-register.md) (`DEC-###`), [`policy-register.md`](policy-register.md) (`POL-###`).

Not in this repository: the original platform specification (`.docx`, §1.3) and the existing local demonstration (§1.4). §1.4 says the demonstration "provides a useful foundation for customer navigation [and] staff screens", but it cannot be inspected here, so no screen below is described as existing in the demonstration and no demonstration screen name is reused. Every screen in this inventory is **Proposed** and assigned to Package E (§6.5 "Native customer journeys", "Captain workspace", "Family calendar", "Coach and referee workspace", "Arrival and attendance", "Pickup when applicable", "Communications", "Support", "Maintenance"), even where the backend command it calls is delivered earlier (Package B foundation, Package C scheduling and competition, Package D registration and money). The package column names that backend dependency.

Nothing in this inventory is a facility fact: no pitch, program, price, form, staff count or hour is named.
