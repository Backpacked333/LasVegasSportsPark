# Release evidence ledger

Status legend: **Verified** = implemented and tested in this repository today (file cited). **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval. **Pending decision** = needs an operator answer; the owner is named from specification §6.6. "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23).

This is the "Release evidence ledger" handoff artifact of §6.7. It records, per build and environment, the evidence that a capability has reached each stage of the §1.5 lifecycle (specified, implemented, verified, operator accepted, released) and the state of the twelve §6.8 definition-of-done items. It is the place where [`../runbooks/cutover.md`](../runbooks/cutover.md) and [`../runbooks/recovery.md`](../runbooks/recovery.md) file their evidence, and the source for §6.8 item 11 ("Evidence identifies the build and environment") and item 12 ("Release ownership is explicit"). Companion documents: `requirement-cross-reference.md` (requirement-to-test matrix), `acceptance-fixtures.md` (what each acceptance journey must show), `decision-register.md` (the policies §6.8 item 1 refers to), `integration-register.md` (provider evidence classified documented, tested, accepted, live per §5.1).

## 1. Rules (Proposed, consistent with §1.5, §6.7, §6.8)

1. One ledger row per (build identifier, environment, capability). A capability is a deliverable named in §6.5 or a smaller unit the technical lead names; rows never aggregate across builds.
2. A build identifier is a commit hash, read from version control, never a branch name alone. The environment names the runtime that produced the evidence (developer container, continuous integration, staging, production) with versions.
3. Three evidence types only: `test run` (automated tests with their count, files and result), `operator acceptance` (a §6.3 task or §6.1 journey completed by a named operator), `device test` (a §6.2 scenario on a named physical device with a signed build). "A visible screen is not evidence that its underlying workflow is complete" (§1.5); "A web preview or successful bundle export does not satisfy" native acceptance (§6.2).
4. Every row has a named owner. A row whose owner is a role rather than a person is **Pending decision** (DEC-017, Sponsor: "acceptance authority").
5. The ledger records measured facts. A figure that was not measured at the build in the row is not entered; a figure supplied from elsewhere is noted as such (see row L-001 note).
6. Status uses the §1.5 stages. A capability is `released` only when all twelve §6.8 items are met for its scope.
7. Critical defects involving protected data, financial execution, capacity, physical resource conflicts or supervised release block the affected launch scope (§6.8); such a defect is recorded as a row with evidence type `test run` or `operator acceptance` and status `blocked`.

## 6. How to add a row (Proposed)

1. Read the commit hash from version control at the moment the evidence was produced. Do not use a branch name alone.
2. Record the environment with versions: runtime, database engine and version, test runner version, device model and OS for device tests, signed build identifier for native builds.
3. Name the capability using the §6.5 wording or the module README title.
4. List requirement ids from `requirement-cross-reference.md` for that capability; do not list ids the evidence does not cover.
5. Choose exactly one evidence type. A test run states files, counts and result; an operator acceptance states the task, the operator's role, the measures of §6.3; a device test states the §6.2 scenario, the device and the build.
6. Link the evidence. If it lives outside the repository, state where and who holds it; if it is not stored anywhere, the row's status is "evidence link missing".
7. Name the owner. If no person is named, the row is **Pending decision** (DEC-017).
8. Update the definition-of-done instance for the capability (section 4 pattern), then the lifecycle stage in `requirement-cross-reference.md`.
9. Never edit an existing row's evidence after the fact; add a new row that references and supersedes it.
