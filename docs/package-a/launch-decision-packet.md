# Launch decision packet

Status legend: **Verified** = implemented and tested in this repository today (file cited); **Proposed** = engineering proposal awaiting the named owner; **Pending decision** = needs the owner's answer (owner role from spec §6.6). "No answer yet" never becomes "not applicable" (§6.6).

Prepared 2026-11-09 for the Package F pilot (§6.5: "named owners accept the operating evidence and explicitly authorize launch"). It asks, in plain language, the decisions that stand between the verified code and a controlled live pilot, says what each one blocks, gives the engineering proposal where the specification or this repository has one, and says exactly where the answer is recorded so that it takes effect. The full records, with their requirement scope, are in [decision-register.md](decision-register.md); this packet adds no decision and answers none. Nothing here is an operator fact.

How to answer: the named owner writes the answer, their name and the effective date on the record in `decision-register.md` (answer status `answered`, proposal status `approved`, `rejected` or `superseded`), and the engineer applies it where the last column says. Until then each item stays **Pending decision**.

## 3. What engineering can do before any answer

- **Verified**: the production path boots without fakes and without choosing a vendor (`apps/api/src/__tests__/production-boot.spec.ts`); every unanswered provider gate runs as `none` and refuses its work visibly.
- **Proposed** order once answers arrive: identity (DEC-018) first, because every real screen sits behind sign-in; payments (DEC-019) and messaging (DEC-020) next; hosting (DEC-021) as soon as the container host is chosen, then the first restore rehearsal on the real provider.
- Operator answers that are configuration (DEC-001, DEC-002, DEC-003, DEC-006 to DEC-009, DEC-016) need no code change: they are entered on the staff screens as records and approved policy versions, and the acceptance runs of Package C and D use them.
