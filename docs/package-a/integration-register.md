# Integration register

Status legend: **Verified** = implemented and tested in this repository today (file cited). **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval. **Pending decision** = needs an operator answer; the owner is named from specification §6.6. "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23).

This is the Package A "Integration inventory" deliverable (§6.5) and the "Integration capability register" handoff artifact (§6.7). It records, for every provider category the specification depends on, the twelve fields of §5.1 and the evidence classification **Documented → Tested → Accepted → Live**. Companion documents: [`authority-matrix.md`](authority-matrix.md) (migration writer authority), `decision-register.md` (owners and target dates for every pending decision named below), [`role-matrix.md`](role-matrix.md), [`permission-matrix.md`](permission-matrix.md), [`requirement-cross-reference.md`](requirement-cross-reference.md).

Two inputs the specification cites are **not in this repository**: the original platform specification (the `.docx` of §1.3 item 1) and the existing local demonstration (§1.4). Nothing below is derived from either; no legacy requirement identifier and no demonstration behaviour is cited.

### 1.2 Columns

Each entry in section 4 is a table with one row per §5.1 field plus the evidence classification:

- **Requirement the specification places on this integration**: what Sportspark needs from the provider, with the requirement identifier or section. These rows are **Proposed** unless the mechanism already exists in code (**Verified**, file cited) or the answer belongs to an operator (**Pending decision**, owner from §6.6).
- **Provider fact today**: what is known about the facility's actual account and product. Today this is "unknown" for every provider because no provider has been selected, no account has been opened, and no documentation has been reviewed against the facility's account (§5.1: public documentation alone does not prove the facility's account capabilities).
- **Status**: one of the three markers.

"Not selected" in the product and vendor row always carries the decision reference: the §6.6 row "Providers and production accounts" (owner: Technical lead/account owners; must be resolved before integration implementation). The decision register does not exist in this repository at the time of writing and no decision identifier scheme has been defined, so entries are referenced by their §6.6 row name; `decision-register.md` must assign each a stable identifier and this register must then be updated (section 7).

### 1.3 Evidence classification (§5.1)

| Level          | Meaning in this register (**Proposed** criteria)                                                                                                                                                                                                            |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Documented** | The facility's own account documentation (plan, contract, enabled features, limits) states that the capability exists for this account. Public product documentation alone does not reach this level (§5.1).                                                |
| **Tested**     | The capability was exercised against the facility's sandbox or test account by an automated test or a recorded manual test, with the build and environment identified (§6.8 item 11). Tests against the repository's fake adapters do not reach this level. |
| **Accepted**   | The account owner and the responsible §6.6 decision owner reviewed the test evidence and accepted it for the affected workflow (§6.8 item 10).                                                                                                              |
| **Live**       | The capability runs in production for real customers, with monitoring (§5.11), a named failure owner (§4.12) and a tested exit path (§5.12).                                                                                                                |

Today every provider category is at **none** on all four levels (section 5).

### 3.3 Follow-up work: `Outbox` and `OutboxDispatcher`

Outbound provider calls (sending a notice, initiating a payment) will be driven by outbox handlers so that a committed business change always produces its follow-up (§4.7 invariant 12, SPK-AT-023). **Verified** mechanism: `apps/api/src/kernel/outbox/outbox.ts`, `outbox-dispatcher.ts`; tests in `apps/api/src/kernel/__tests__/outbox.spec.ts` ("dispatches each event to every handler exactly once, even when redelivered", "retries a failing handler with backoff without re-running handlers that succeeded", "dead-letters after max attempts and raises an owned operational exception", "reclaims events whose worker died (expired lease)"). The handlers that call providers do not exist yet (**Proposed**).

### 3.4 Error contract for provider failures

`INTEGRATION_UNAVAILABLE` (503, next action `retry_later`), `RATE_LIMITED` (429), `PAYMENT_OUTCOME_UNKNOWN` (409, `await_reconciliation`) and `REFUND_PENDING` (409) exist in `packages/contracts/src/errors.ts` (**Verified**). Their use by adapters is **Proposed**.

### 3.5 What does not exist

No payment, push, email, SMS, storage, accounting, hardware or calendar adapter; no native application project (the Expo apps are Package E, `docs/architecture/overview.md` "Not in this repository"); no hosting configuration beyond `.github/workflows/ci.yml` (continuous integration on GitHub Actions with a PostgreSQL 18 service, **Verified**, which is not a hosting or recovery environment selection); no migration extractor (the migration module is a scaffold, `apps/api/src/modules/migration/README.md`).

## 7. Maintenance rules

1. One entry per provider category; a category with two products (for example separate email and SMS vendors) stays two entries. A new provider category requires a new entry before any adapter code is written.
2. A row moves from "unknown" only with evidence that names its source and date. Public documentation moves nothing past the "Requirement" column; the facility's account documentation moves the entry to **Documented** (section 1.3).
3. **Tested** requires a test whose name carries the requirement identifier (per `CLAUDE.md` "Tests") and that ran against the facility's sandbox account with the build and environment recorded. Tests against `Fake*Provider` adapters keep the Sportspark-side mechanism **Verified** but do not move the provider's evidence level.
4. **Accepted** is recorded with the names of the account owner and the §6.6 decision owner and the date; **Live** additionally cites the monitoring signal (§5.11), the failure owner queue and the exit rehearsal evidence (§5.12).
5. When `decision-register.md` assigns identifiers, replace every "§6.6 row" reference in sections 4 and 6 with the identifier and keep the row name.
6. The implementing engineer never changes a "Product and vendor" row. That row changes only when the technical lead and account owner have recorded the approval in the decision register (§5.2).
7. Regenerate the "Verified boundary in code" section whenever a port, adapter, inbox handler or vendor dependency is added or removed; the dependency check is `grep` over the three `package.json` files for the new package name.
8. Keep this file consistent with `authority-matrix.md` for entry 4.12 and with `role-matrix.md` for every reconciliation owner named here.
