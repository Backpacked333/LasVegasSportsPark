### 1.2 Columns

Each entry in section 4 is a table with one row per §5.1 field plus the evidence classification:

- **Requirement the specification places on this integration**: what Sportspark needs from the provider, with the requirement identifier or section. These rows are **Proposed** unless the mechanism already exists in code (**Verified**, file cited) or the answer belongs to an operator (**Pending decision**, with the `DEC-###` record and the owner from §6.6).
- **Provider fact today**: what is known about the facility's actual account and product. Today this is "unknown" for every provider because no provider has been selected, no account has been opened, and no documentation has been reviewed against the facility's account (§5.1: public documentation alone does not prove the facility's account capabilities). The repository's own adapters (the local identity provider of section 3.1 and the fake messaging providers of section 3.5) are Sportspark test doubles, not provider facts.
- **Status**: one of the three markers.

"Not selected" in the product and vendor row always carries the decision reference as a `DEC-###` identifier from [`decision-register.md`](decision-register.md), followed by the §6.6 row name, the §5.2 gate name or the sub-decision it records. The §6.6 row "Providers and production accounts" is DEC-013 (owner: Technical lead/account owners; must be resolved before integration implementation). The decision register breaks it down into one record per §5.2 gate, DEC-018 "Identity provider", DEC-019 "Payment processor and merchant arrangement", DEC-020 "Messaging providers", DEC-021 "Hosting and recovery environment", DEC-022 "Accounting connection" and DEC-023 "Hardware interfaces", and one record for §5.12 production ownership, DEC-069. Every other decision is cited the same way: identifier, then name, then owner. Every record cited in this register has answer status "unknown" today (`decision-register.md` section 1); an identifier is a reference, not an answer.

### 1.3 Evidence classification (§5.1)

| Level          | Meaning in this register (**Proposed** criteria)                                                                                                                                                                                                            |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Documented** | The facility's own account documentation (plan, contract, enabled features, limits) states that the capability exists for this account. Public product documentation alone does not reach this level (§5.1).                                                |
| **Tested**     | The capability was exercised against the facility's sandbox or test account by an automated test or a recorded manual test, with the build and environment identified (§6.8 item 11). Tests against the repository's fake adapters do not reach this level. |
| **Accepted**   | The account owner and the responsible §6.6 decision owner reviewed the test evidence and accepted it for the affected workflow (§6.8 item 10).                                                                                                              |
| **Live**       | The capability runs in production for real customers, with monitoring (§5.11), a named failure owner (§4.12) and a tested exit path (§5.12).                                                                                                                |

Today every provider category is at **none** on all four levels (section 5).

### 3.3 Follow-up work: `Outbox` and `OutboxDispatcher`

Outbound provider calls (sending a notice, initiating a payment) will be driven by outbox handlers so that a committed business change always produces its follow-up (§4.7 invariant 12, SPK-AT-023). **Verified** mechanism: `apps/api/src/kernel/outbox/outbox.ts`, `outbox-dispatcher.ts`; tests in `apps/api/src/kernel/__tests__/outbox.spec.ts` ("dispatches each event to every handler exactly once, even when redelivered", "retries a failing handler with backoff without re-running handlers that succeeded", "dead-letters after max attempts and raises an owned operational exception", "reclaims events whose worker died (expired lease)"). Messaging is the one implemented provider path, and its provider call is not made inside an outbox handler: the dispatcher runs each handler inside a transaction with its consumption record, so the `communications.delivery_requested` handler does only the transactional half (recipient re-check, attempt rows) and `DeliveryWorker` hands queued attempts to the channel provider outside any transaction (section 3.5; `apps/api/src/modules/communications/README.md` "Kernel notes"; **Verified**, `delivery.spec.ts`). Handlers or workers that call payment, accounting or hardware providers do not exist yet (**Proposed**).

### 3.4 Error contract for provider failures

`INTEGRATION_UNAVAILABLE` (503, next action `retry_later`), `RATE_LIMITED` (429), `PAYMENT_OUTCOME_UNKNOWN` (409, `await_reconciliation`) and `REFUND_PENDING` (409) exist in `packages/contracts/src/errors.ts` (**Verified**). Their use by adapters is **Proposed**.

Its provider boundary is a port with fake adapters only; no messaging vendor is selected (DEC-020, **Pending decision**).

### 3.6 What does not exist

No payment, storage, accounting or hardware adapter, and no fake for any of them; no adapter for a selected identity, push, email or SMS vendor (identity runs on the local provider of section 3.1, messaging on the fakes of section 3.5); no device-token registration for push; no native application project (the Expo apps are Package E, `docs/architecture/overview.md` "Not in this repository"); no hosting configuration beyond `.github/workflows/ci.yml` (continuous integration on GitHub Actions with a PostgreSQL 18 service, **Verified**, which is not a hosting or recovery environment selection); no migration extractor (the migration module is a scaffold, `apps/api/src/modules/migration/README.md`). Private calendar feeds need no adapter: Sportspark produces them itself (entry 4.10).

## 7. Maintenance rules

1. One entry per provider category; a category with two products (for example separate email and SMS vendors) stays two entries. A new provider category requires a new entry before any adapter code is written.
2. A row moves from "unknown" only with evidence that names its source and date. Public documentation moves nothing past the "Requirement" column; the facility's account documentation moves the entry to **Documented** (section 1.3).
3. **Tested** requires a test whose name carries the requirement identifier (per `CLAUDE.md` "Tests") and that ran against the facility's sandbox account with the build and environment recorded. Tests against `Fake*Provider` adapters keep the Sportspark-side mechanism **Verified** but do not move the provider's evidence level.
4. **Accepted** is recorded with the names of the account owner and the §6.6 decision owner and the date; **Live** additionally cites the monitoring signal (§5.11), the failure owner queue and the exit rehearsal evidence (§5.12).
5. Decisions are cited by their `decision-register.md` identifier followed by the §6.6 row name, §5.2 gate name or sub-decision name, and the owner (applied in this revision to sections 1.2, 2, 3, 4, 5 and 6). A decision this register needs that has no record gets one in `decision-register.md` (its section 12) before it is cited here; identifiers are never reused or renumbered (`decision-register.md` section 10.1).
6. The implementing engineer never changes a "Product and vendor" row. That row changes only when the technical lead and account owner have recorded the approval in the decision register (§5.2).
7. Regenerate the "Verified boundary in code" section whenever a port, adapter, fake, inbox handler, webhook endpoint or vendor dependency is added or removed, or a module that owns an integration changes from scaffold to implemented; the dependency check is `grep` over the three `package.json` files for the new package name.
8. Keep this file consistent with `authority-matrix.md` and `docs/runbooks/cutover.md` for entry 4.12 and with `role-matrix.md` for every reconciliation owner named here. At this revision `authority-matrix.md` (preamble) and `cutover.md` (section 1) still state that the legacy system is DaySmart as a fact; both must adopt the wording of entry 4.12 (a working assumption based on §1.2; the source system is **Pending decision**, DEC-014).
