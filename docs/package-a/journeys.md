## 2. How to read a journey

Each journey is a table with one row per step. Columns:

| Column                       | Meaning                                                                                                                                                                                                                         |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Step                         | Journey identifier and sequence number, cited by the screen inventory.                                                                                                                                                          |
| Phase (§1.1)                 | Which of the nine journey phases the step belongs to.                                                                                                                                                                           |
| Customer action              | What the person does in the customer app (§2.2) or in person.                                                                                                                                                                   |
| Corresponding staff workflow | The staff workflow §1.1 requires for that action: who acts, on which dashboard area (§2.3) or workspace (§2.4), using which command. Where the correct response is "no staff action required", the row says what staff can see. |
| Records touched (§4.4)       | Entities created, transitioned or read, using the §4.4 names. Module ownership follows §4.2 and the module READMEs.                                                                                                             |
| Requirement ids              | `SPK-*` ids, `SPK-AT-*` acceptance journeys, and §4.8 interfaces. §4.8 interfaces are "representative"; only `GET /v1/operations/{id}` exists today.                                                                            |
| Visible status               | The customer-visible and staff-visible status vocabulary from section 3, showing which states the step may leave the person in.                                                                                                 |
| Status                       | **Proposed** for every row. Verified foundations are listed under each journey separately so a row never claims more than the repository proves.                                                                                |

A step marked "customer" may be performed by front desk on the customer's behalf through assisted registration; SPK-REG-009 then records the staff actor separately from the participant, payer and form signer, and staff never sign a guardian acknowledgment.

Rules that apply to every label (all **Proposed**, derived from §2.2 and §2.5):

1. A label names the participant and the offering, team or program it belongs to (SPK-UX-003).
2. A label that is not terminal shows the time or actor it is waiting on, in facility local time derived from the facility timezone (SPK-SCHED-008).
3. A failure label carries the `nextAction` from the error contract (**Verified** `packages/contracts/src/errors.ts`), never a bare "error".
4. Staff labels use the machine state names verbatim so that app, dashboard and audit agree (SPK-UX-010).
