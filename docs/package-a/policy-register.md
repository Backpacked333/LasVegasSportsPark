# Policy register

Status legend: **Verified** = implemented and tested in this repository today (file and test cited); **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval; **Pending decision** = needs an operator answer (owner named from spec §6.6). "No answer yet" never becomes "not applicable" (§6.6). Code that exists but that no test asserts is described as "implemented, not asserted by a test" and is never marked **Verified**.

Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23). Repository inspection date for every **Verified** statement: 2026-10-24.

Package A deliverable "Policy register" (§6.5) and the policy half of the "Policy and decision register" (§6.7). The decision half, which this document cites by `DEC-###`, is `docs/package-a/decision-register.md`.

## 1. What this document is

- One row per policy the system must version and enforce: a rule that a command evaluates, that a record cites as its basis, or that a customer acknowledges. 47 policies, `POL-001` to `POL-047` (section 4).
- For each: what it governs, the requirement ids that depend on it, where the specification's entities and interfaces reference it (§4.4 `PolicyVersion`, `Acknowledgment`, `Approval` and the records that carry a policy basis) and, where they exist, the implemented tables, its status with the §6.6 owner, the specification's proposed default where one exists, and the decision records that answer it.
- A mapping from every `POL` id to the implemented policy store (section 3.2) and the approval roles the code applies to each catalog policy kind (section 3.3).
- A lookup by owner (section 5), so each §6.6 owner can see every policy waiting on them.

**Verified**: the §4.4 "Policies" entities are implemented by the catalog module. `policy_versions`, `approvals` and `acknowledgments` are created by `packages/db/migrations/0200_catalog_core.sql`; their database guards are proven in `apps/api/src/modules/catalog/__tests__/catalog-schema.spec.ts` and their commands in `apps/api/src/modules/catalog/__tests__/policies-and-acknowledgments.spec.ts` (section 3.1). The migrations present are `0001_core_schema.sql`, `0100_identity_core.sql`, `0200_catalog_core.sql`, `0300_scheduling_core.sql`, `0400_competition_core.sql`, `0900_facilities_core.sql` and `1000_communications_core.sql`.

**Verified** (by inspection): no policy has an operator-approved version. The only approved `policy_versions` rows are written by the test fixture `createPolicyVersionFixture` (`apps/api/src/modules/catalog/testing/catalog-fixtures.ts`) into the per-file test databases that `createTestApp()` creates; no migration, seed or script writes `policy_versions` (search of `apps/` and `packages/`), and no file under `docs/` records an operator-approved policy. Every row in section 4 is therefore **Pending decision**. The "Specification's proposed default" column is the only source of values, and everything in it is **Proposed**.

The "original platform specification" (`.docx`, §1.3) and the "existing local demonstration" (§1.4) are not in this repository. The demonstration's "refund behavior, and competition settings are examples, not approved policies" (§1.4) and are not reproduced here; no legacy policy identifier is cited.

## 2. Verified context

What exists in the repository today that a policy plugs into. Each item names the file and, where it is tested, the test.

1. **Commands can cite policies and reasons.** `CommandMetaSchema` in `packages/contracts/src/commands.ts` accepts `policyReferences` (up to 20 strings of 1 to 200 characters) and `reason` on every consequential command (§4.9 "Policy references", "Reason for overrides or corrections"). **Verified** for `reason`: `audit_records.reason` is written and read in `apps/api/src/kernel/__tests__/unit-of-work.spec.ts`. **Verified** for `policyReferences` as an accepted command field: `apps/api/src/modules/catalog/__tests__/pricing.spec.ts` "SPK-PAY-003: finance defines discounts; codes are unique; revisions and lifecycle are enforced" creates a discount with `policyReferences: ['POL-011']` and the command succeeds. `apps/api/src/modules/catalog/services/discounts.service.ts`, `services/price-rules.service.ts` and `apps/api/src/modules/competition/services/competitions.service.ts` (rule-set versions) copy the array into `audit_records.details.policyReferences`; that persistence is implemented, not asserted by a test. The kernel does not persist `policyReferences`, and no service validates the strings or resolves them to a stored policy version. The format is proposed in section 3.4, item 4.
2. **The error contract already names policy outcomes.** `packages/contracts/src/errors.ts` defines `ELIGIBILITY_FAILED`, `MISSING_ACKNOWLEDGMENT`, `CAPACITY_UNAVAILABLE`, `DUPLICATE_ENTITLEMENT`, `QUOTE_EXPIRED`, `REFUND_PENDING` and `PAYMENT_OUTCOME_UNKNOWN` with a permitted next action each (§4.10). **Verified** as a contract: `apps/api/src/kernel/__tests__/auth-and-operations.spec.ts` "rejects missing, malformed, expired and unknown tokens with the error contract" proves the `{ code, message, correlationId, nextAction }` shape through `DomainExceptionFilter`. **Verified** (by inspection): no command in `apps/api/src` raises `ELIGIBILITY_FAILED` or `MISSING_ACKNOWLEDGMENT` yet.
3. **Lifecycles carry no policy values.** The §4.6 machines in `packages/contracts/src/state-machines.ts` (tested in `state-machines.spec.ts`) define allowed transitions only. A hold has one terminal outcome but no duration; a result can be published but no authority rule is encoded; a refund can be `unknown` but no amount rule exists. The policy-version lifecycle is `PolicyVersionMachine` in `apps/api/src/modules/catalog/catalog.state-machines.ts`: draft, approved, retired, **Verified** by `catalog.state-machines.spec.ts` "§4.4 PolicyVersion: draft → approved → retired, nothing else". The values are the rows below.
4. **Action-specific grants exist.** `GrantPermissions` (`view`, `register`, `pay`, `receive_messages`, `complete_forms`, `collect`) in `apps/api/src/kernel/authorization/actions.ts`; **Verified** by `apps/api/src/kernel/__tests__/authorization.spec.ts` "one permission never implies another: view does not allow collect". The pickup policy (POL-019) decides how `collect` is granted and verified, not whether it is separate. The `complete_forms` grant is what lets a guardian sign an acknowledgment for a child (POL-037, section 3.2).
5. **Append-only records exist for corrections.** The `forbid_mutation` trigger in `packages/db/migrations/0001_core_schema.sql` is applied to `audit_records` (**Verified** by `packages/db/src/core-schema.spec.ts` "audit records are append-only"), to `approvals` and `discount_redemption_entries` in `0200_catalog_core.sql` (**Verified** by `catalog-schema.spec.ts` "§4.4 Approval: approvals are append-only facts" and "§4.7 invariant 5: one redeem and one release per reference; the ledger is append-only"), and to competition `rule_sets` in `0400_competition_core.sql` (**Verified** by `apps/api/src/modules/competition/__tests__/competition-schema.spec.ts` "SPK-COMP-002: a rule-set version is immutable (append-only), and versions chain by name"). Policy versions do not use `forbid_mutation`, because retirement must stay possible; they use the dedicated trigger `policy_versions_guard` (section 3.1).
6. **Money mechanics exist; the rounding rule is not approved.** `packages/contracts/src/money.ts` rounds basis-point percentages half away from zero and allocates by largest remainder; **Verified** by `money.spec.ts`. Discount definitions carry their own rounding mode (`half_up` by default, `half_even`, `down`, `up`) and allocation method (`proportional` by default, `largest_first`, `first_line`, `even`) in `discount_definitions`; **Verified** by `apps/api/src/modules/catalog/pricing/discount-evaluator.spec.ts` "rounds a percentage under each mode" and the "allocation across lines (SPK-PAY-003)" tests. These are engineering defaults that POL-011 and POL-012 may confirm or replace (DEC-007).
7. **The catalog module owns the policy store.** **Verified**: `apps/api/src/modules/catalog/README.md` lists "policy versions, approvals, acknowledgments" among its owned records with status "implemented"; the tables are in `0200_catalog_core.sql` and the tests are those cited in section 3.1. Other modules read policy versions only through `POLICY_PORT` and `OFFERING_LOOKUP_PORT` (catalog README, "Ports"); **Verified** (by inspection): no module outside catalog calls `POLICY_PORT` yet.
8. **Configuration values that look like policies are not.** `AUTH_TOKEN_TTL_SECONDS` (8 hours), `IDEMPOTENCY_TTL_HOURS` (24) and `OUTBOX_LOCK_LEASE_SECONDS` (60) in `apps/api/src/kernel/config.ts`, and `outbox_events.max_attempts` (10) in `0001_core_schema.sql`, are engineering defaults (code) and appear in no row below. The catalog's `POLICY_APPROVAL_ACTION` and staffing formula (`apps/api/src/modules/catalog/catalog.policy.ts`) are engineering defaults for mechanisms that rows here govern; section 3.3 records them as **Proposed** values, and `decision-register.md` section 3, item 9 lists them as placeholders.

### 3.2 Mapping from `POL` ids to the implemented store

Column key. **Catalog kind**: the `policy_versions.kind` that holds the approved rule; "none" means no kind holds it today. **Proposed key**: the `key` convention of section 3.4, item 1 (**Proposed** on every row). **Implemented store**: tables, triggers and constraints that hold or enforce the policy today. **Approving action today**: "participation" is `catalog.approve_participation_policy` (`program_manager`, `league_manager`); "financial" is `catalog.approve_financial_policy` (`finance_operator`); see section 3.3. **Status**: the status of the store, then of the values; owners are from §6.6 as in section 4.

Notes used in the table:

- **N1. No store yet.** No catalog kind or other table holds this policy. **Proposed**: when the owning module is built, its approved rule is stored either as a new `policy_versions` kind, added by a new catalog migration in the 0200s range (applied migrations are immutable, and the `kind` check lists exactly ten values, **Verified** by `catalog-schema.spec.ts` "§4.4: one policy version number per (kind, key); kinds are the ten policy kinds"), or in a versioned table owned by that module; in both cases the approval is recorded as an `approvals` row, which for a module table needs a new `approvals.subject_type` value (a catalog migration). The choice is made when the owning module is built and is recorded on this row.
- **N2. Competition rule set.** The values are fields of competition `rule_sets.content` (section 3.1). **Verified** store; the field defaults in `proposedRuleSetContent` (`apps/api/src/modules/competition/competition.policy.ts`) are engineering defaults a league manager starts from (competition README), **Proposed**. Rule-set versions are created through `competition.manage_competitions` (`league_manager`, `general_manager`, `system_administrator`, per the competition README) and record no `approvals` row. **Proposed**: record an approval fact for each rule-set version before a season in registration may use it, and cite the policy in `policyReferences` (already copied into the audit record by `competitions.service.ts`, not asserted by a test).

### 3.4 Remaining proposal (**Proposed**)

This subsection replaces the earlier, unimplemented proposal with one reconciled to section 3.1. Each item is **Proposed** unless it cites a test.

1. **Identity.** A `POL-###` id names a policy subject in this register. A stored version is identified by `(organization_id, kind, key, version)` and its uuid (**Verified**, section 3.1). **Proposed** key convention: the `key` begins with the lowercased `POL` id (`pol-001`), with a suffix for each variant (`pol-001-youth`), which the `key` check accepts; the mapping in section 3.2 then reads directly off the stored rows. Per-offering, per-competition or per-facility variants are separate keys bound by the referencing record's foreign key; the earlier proposal of a scope field is withdrawn because the implemented table has none.
2. **Versions are immutable.** Implemented by `policy_versions_guard` (**Verified**). **Proposed** additions: (a) refuse moving an approved version's `effective_to` later, as `price_rules_guard` does for price rules, through a new catalog migration; (b) because the table has no fixture marker, any non-production seed carries `"synthetic": true` in `content`, and production data never receives fixture rows (fixtures today write only into per-file test databases, section 1).
3. **Approval.** One `approvals` row per approval (**Verified**, section 3.1). `ApprovePolicyVersionBody` carries `reason`, `expectedRevision` and `policyReferences`; the service writes `reason` and `details` `{ kind, key, version }` but not `policyReferences` (inspection of `policies.service.ts`). **Proposed**: the approving staff member writes the answered `DEC-###` id, the §6.6 owner's name and the evidence reference in `reason`, and the decision register's record is answered in the same change. Where §6.6 names an owner with no approval path (section 3.3, "Difference"), the approving staff member records that owner's documented decision; whether the system must require the owner's own approval is part of the cited `DEC` records.
4. **Commands cite policies.** The `POL-###@<version>` format of the earlier proposal is withdrawn: versions are numbered per `(kind, key)`, and one `POL` id may own several keys. **Proposed** format for `policyReferences` entries: `POL-###` cites a register policy as a whole (the form `pricing.spec.ts` sends today); `<kind>/<key>@<version>`, for example `eligibility/pol-001-youth@2`, cites one stored version. A service that receives a version reference resolves it to an approved version effective at the command's reference date (SPK-REG-002 "configured reference date") and refuses an unknown, draft or retired one with `VALIDATION_FAILED`. No such resolution exists today; the contract checks only length and count (section 2, item 1).
5. **Records keep their basis by foreign key.** **Verified** for offerings (eligibility, cancellation, required forms), acknowledgments and seasons (rule-set version), section 3.1. **Proposed** for `Quote`, `OrderLine`, `Enrollment`, `Hold`, `WaitlistEntry`, `RefundAttempt`, `Credit`, `Suspension`, `ResultRevision` and `ReleaseRecord`, whose modules have no table in this repository: each stores the `policy_versions.id` (or rule-set id) it was evaluated under, so "Historical purchases retain their price and policy basis" (SPK-PAY-002) and later versions never rewrite history (§4.7 invariant 9).
6. **Acknowledgments** are implemented with the signer recorded separately from the staff actor (SPK-REG-009, **Verified**, section 3.1). **Proposed**: a command that requires an acknowledgment of a version the participant has no active acknowledgment for fails with `MISSING_ACKNOWLEDGMENT`, using `POLICY_PORT.hasAcknowledgment` (**Verified** port behaviour in "an adult acknowledges for themselves; a guardian holding complete_forms acknowledges for a child"); no command raises the code yet.
7. **Release gate.** A capability is complete only when "Its applicable policies are approved" (§6.8 item 1). **Proposed** check: every `POL` row the capability depends on has an approved, non-fixture `policy_versions` row (or rule-set version with an approval fact, N2) whose key follows item 1 and whose `approvals` row cites an answered `DEC` record. The rows in section 4 name the capability packages that each policy blocks through their owners' "Must be resolved before" entries (section 5).

## 7. How this register is maintained (**Proposed**)

1. **Ids are permanent.** `POL-###` is never reused or renumbered. A policy the operator declares not applicable keeps its row with Status "**Pending decision** resolved: not applicable (owner, date, evidence)"; an "unknown" is never rewritten as "not applicable" without those three fields (§6.6).
2. **Status changes only through the decision register.** A row leaves **Pending decision** when every `DEC` record in its "Decision records" column is answered and an approved, non-fixture version exists in the store section 3.2 names for it (a `policy_versions` row whose key follows section 3.4, item 1, or a rule-set version with an approval fact); the same pull request updates both documents and the cross-reference's Status column for the requirement ids listed.
3. **A new policy** is added when a requirement, a command or a record needs a versioned rule that no row covers. The row cites the requirement ids and the `DEC` record that owns the answer; if no `DEC` record exists, one is added first. The same change adds its row to section 3.2.
4. **Proposed defaults are quoted, not paraphrased into values.** The "Specification's proposed default" column holds only what the specification proposes; an engineering default (section 2, items 6 and 8; section 3.3) is named as such and never promoted into that column.
5. **Code placeholders** for an unapproved policy are marked synthetic and cite the `POL` id (section 3.4, item 2), so a test fixture or seed is never mistaken for an approved version. The implemented table has no marker today; fixtures are confined to test databases.
6. **Review trigger.** Every pull request that adds a `policyReferences` value, an eligibility or pricing evaluation, a `policy_versions` kind, an `approvals.subject_type`, a change to `POLICY_APPROVAL_ACTION` or `catalog.actions.ts` approval roles, or a table named in section 3 updates the affected rows of sections 3.2, 3.3 and 4.
7. **Regeneration check**: `grep -oE 'POL-[0-9]{3}' docs/package-a/policy-register.md | sort -u | wc -l` must equal the row count in section 4 (47); section 3.2 must have one row per `POL` id (47); and every `DEC-###` cited here must exist in `docs/package-a/decision-register.md` (`grep -oE 'DEC-[0-9]{3}' docs/package-a/policy-register.md | sort -u` against the same pattern on the decision register).

## 8. Specification ambiguities encountered

Each item is **Proposed** handling unless it says **Pending decision**.

1. **Cancellation policy has two owners.** §6.6 gives "Refunds, credits, transfers, cash" to Finance and "Waitlist, holds, approvals, basket behavior" to Product and operations, but names no owner for an offering's cancellation terms (SPK-CAT-001). POL-007 lists both; the catalog approves `cancellation` versions by the finance operator only (section 3.3).
2. **Quote validity has no §6.6 row.** POL-013 is placed with Finance (prices) and Product and operations (registration acceptance).
3. **Eligibility spans two owners.** Adult competition eligibility (SPK-COMP-002) sits with the League manager and youth eligibility (SPK-YOUTH-001) with the Program manager; POL-001 is one policy with per-scope keys (section 3.4, item 1) rather than two policies, because SPK-REG-002 evaluates one "eligibility" per registration. The adult competition fields also appear in competition rule sets (section 3.2, POL-001 and N2); which store an adult league's eligibility check reads first is for the enrollment module to state when it is built.
4. **"Pickup" has two meanings** (supervised pickup, POL-019; pickup sessions, POL-045), as in the decision register (ambiguity 2) and the cross-reference (item 2).
5. **Participation consequences of balances** (POL-017) could belong to "Team liability, installments, overpayments" or to "Waitlist, holds, approvals, basket behavior"; the row follows SPK-PAY-006's placement in §3.15 and assigns Finance and league manager.
6. **Visitor categories and arrival guidance** (POL-046) have no §6.6 row; Operations is the closest fit.
7. **Policy-version mechanics beyond §4.4 and §4.9.** The specification names `PolicyVersion`, `Acknowledgment` and `Approval` (§4.4) and "Policy references" (§4.9) without fields. The implemented fields (section 3.1) are the catalog module's choice; section 3.4 is this document's proposal for the rest, so that the §6.8 item 1 gate ("Its applicable policies are approved") becomes checkable.
8. **The ten catalog kinds are an engineering choice.** §4.4 lists no kinds. Eleven `POL` rows map to a kind, six to competition rule sets, two to catalog configuration tables, and the rest have no store (section 3.2, N1). Adding a kind requires a new catalog migration because the `kind` check is part of the applied migration `0200_catalog_core.sql`.
9. **§6.6 owners are not staff roles.** "Product and operations", "Finance and league manager", "Operator/privacy owner" and "Product owner" have no `StaffRole`; the catalog approves participation kinds through the program and league managers and financial kinds through the finance operator (section 3.3). The approving staff member records the owner's documented decision (section 3.4, item 3); whether the system must also capture the owner's own approval is part of DEC-006, DEC-008 and DEC-009, and the exclusion of `general_manager` and `system_administrator` from approval is DEC-087.
10. **Whether the drafter of a version may approve it.** The specification is silent; the code allows it (section 3.3, **Verified**). **Pending decision** (owner: the §6.6 owner of each kind, section 3.3). No `DEC` record covers it yet; under rule 7.3 one must be added to `docs/package-a/decision-register.md` before it can be answered, which is outside this document's scope.
11. **Prices and discounts are policy values without approval facts.** §6.6 "Prices, taxes, discounts, rounding" makes them Finance decisions, but `price_rules` and `discount_definitions` are written by finance roles without an `approvals` row (section 3.2, POL-011 and POL-012). The handling proposed there is to cite the answered decision in `reason` and `policyReferences`, which both services already copy into the audit record.
12. **Competition rule sets carry policy values outside the policy store.** POL-026 to POL-030 and POL-032 values live in `rule_sets.content`, which is immutable but has no approval status (section 3.1). The handling proposed in N2 is an approval fact per rule-set version before a season in registration uses it.
