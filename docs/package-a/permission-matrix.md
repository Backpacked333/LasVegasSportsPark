# Permission matrix

Status legend: **Verified** = implemented and tested in this repository today (file cited). **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval. **Pending decision** = needs an operator answer; the owner is named from specification §6.6. "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22).

This is the Package A "Permission matrix" (§6.7) and the input to the "Authority matrix" (§6.5). It has three parts:

- **Part A** describes the authorization model as implemented in the kernel and in the identity and competition modules (**Verified**).
- **Part B** lists the 77 actions registered in code today (**Verified**): 3 in the kernel, 24 in identity, 16 in catalog, 18 in competition, 8 in scheduling and 8 in facilities, each declared with `defineActions` and evaluated through `AuthorizationService`.
- **Part C** is the proposed action-level matrix for everything the specification requires that is not registered yet (**Proposed** in its entirety), and Part B.7 reconciles the earlier Part C rows for identity, catalog, competition, scheduling and facilities with the registry.

Part B was derived by hand from the five `apps/api/src/modules/<module>/<module>.actions.ts` files and from the two kernel services that call `defineActions`, in the order `actionRegistry.list()` returns (alphabetical by id). The generated file `docs/package-a/permission-matrix.generated.md` and a `pnpm permissions` script do not exist: the root `package.json` defines `openapi` but no `permissions` script, and `apps/api/scripts/` contains only `emit-openapi.ts` (**Verified** absence). The generator stays **Proposed** (last section). Modules without a `<module>.actions.ts` today: automation, communications, enrollment, entry, finance, migration, reporting, support and workforce (each is a scaffold; see its `README.md`). The competition registry (part 1) landed while this revision was being written and its part 2 is under construction, so Part B is a dated snapshot (Ambiguities item 12). Companion documents: [`role-matrix.md`](role-matrix.md), `authority-matrix.md`, `decision-register.md`, `requirement-cross-reference.md`.

The original platform specification (`.docx`, §1.3) and the existing local demonstration (§1.4) are not in this repository; no permission below is derived from either.

### A.2 Action definition fields

| Field               | Type                                                                                        | Meaning                                                                                                                                                                                           |
| ------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                | `<module>.<verb>`                                                                           | Unique action identifier; the module prefix matches §4.2 ownership                                                                                                                                |
| `description`       | text                                                                                        | Human-readable purpose                                                                                                                                                                            |
| `staffRoles`        | `StaffRole[]`                                                                               | Staff roles permitted within their organization and facility scope; may be empty (customer-only actions such as `identity.accept_invitation`)                                                     |
| `allowSelf`         | boolean, optional                                                                           | A principal may act when every subject person is themselves (subject to the relationship port when the action also names a `subjectPermission`, A.4 step 6b)                                      |
| `subjectPermission` | one of `view`, `register`, `pay`, `receive_messages`, `complete_forms`, `collect`, optional | A principal may act when they hold this grant over every subject person (SPK-IAM-003)                                                                                                             |
| `teamRole`          | one of `captain`, `co_captain`, `member`, optional                                          | A principal may act when they hold this role on the target's `teamEntryId`; used by the competition registry (`captain`, `member`) and evaluated as a downward hierarchy by the port (A.4 step 8) |
| `requirements`      | string[], optional                                                                          | Specification requirement ids the action implements (documentation; every one of the 77 registered actions sets it)                                                                               |

| Field              | Meaning                                                                                             |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| `type`, `id`       | Record type and id (id may be null for collection-level actions)                                    |

### A.4 Decision order

`AuthorizationService.decide` (`apps/api/src/kernel/authorization/authorization.service.ts`) returns the first matching outcome:

| Step | Condition                                                                                                                                                                                                                                                                                                                                                                         | Outcome                                                                                                                                               | Test (in `apps/api/src/kernel/__tests__/authorization.spec.ts` unless another file is named)                                                                                                                                                                                                                                                                                                                          |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | Action id not in the registry                                                                                                                                                                                                                                                                                                                                                     | deny (`unknown action`)                                                                                                                               | (no dedicated test)                                                                                                                                                                                                                                                                                                                                                                                                   |
| 2    | `principal.kind === 'anonymous'`                                                                                                                                                                                                                                                                                                                                                  | deny (`authentication required`)                                                                                                                      | "denies anonymous principals"                                                                                                                                                                                                                                                                                                                                                                                         |
| 3    | `principal.organizationId !== target.organizationId`                                                                                                                                                                                                                                                                                                                              | deny (`organization scope mismatch`)                                                                                                                  | "never crosses organization scope, even for staff and system actions"                                                                                                                                                                                                                                                                                                                                                 |
| 4    | `principal.kind === 'system'`                                                                                                                                                                                                                                                                                                                                                     | allow (`system`)                                                                                                                                      | "system principals are allowed within their organization only"                                                                                                                                                                                                                                                                                                                                                        |
| 5    | staff: a listed role is held and the facility scope matches                                                                                                                                                                                                                                                                                                                       | allow (`staff role`)                                                                                                                                  | "allows staff by role and enforces facility scope"                                                                                                                                                                                                                                                                                                                                                                    |
| 5a   | staff: a listed role is held, facility scope does not match                                                                                                                                                                                                                                                                                                                       | deny (`facility scope mismatch`), evaluation stops                                                                                                    | same test                                                                                                                                                                                                                                                                                                                                                                                                             |
| 5b   | staff: no listed role is held                                                                                                                                                                                                                                                                                                                                                     | continue to step 6 with the staff member's own `personId`                                                                                             | "a coach who is also a parent: staff authority only via staff membership, guardian authority only via grants" (`apps/api/src/modules/identity/__tests__/relationships.spec.ts`)                                                                                                                                                                                                                                       |
| 6    | `principal.personId` is null (an account without a person)                                                                                                                                                                                                                                                                                                                        | skip steps 6a to 8 and deny at step 9                                                                                                                 | "an unlinked account authenticates but has no person and no authorities" (`apps/api/src/modules/identity/__tests__/principal-resolver.spec.ts`)                                                                                                                                                                                                                                                                       |
| 6a   | `allowSelf`, the target names at least one subject, every subject equals `principal.personId`, and the action has no `subjectPermission`                                                                                                                                                                                                                                          | allow (`self`) without consulting any port                                                                                                            | "§4.5: household membership never grants authority; customers manage households they belong to" (`identity.create_household`, `staff-memberships.spec.ts`); "acceptance by the wrong person is denied as not-found; a wrong token is not-found" (`identity.accept_invitation`, `invitations.spec.ts`)                                                                                                                 |
| 6b   | as 6a, but the action names a `subjectPermission`                                                                                                                                                                                                                                                                                                                                 | ask `RelationshipAuthorityPort.hasPermission(org, personId, personId, permission)`; allow (`self`) when it answers true, otherwise continue to step 7 | "allows self when the action permits it and the relationship authority agrees"; "never lets a child principal pay or collect for themselves, even on an allowSelf action"; identity implementation: "self authority: an adult always, a child never for pay or collect" (`relationships.spec.ts`)                                                                                                                     |
| 7    | `subjectPermission` and the target names at least one subject: `hasPermission(org, personId, subject, permission)` answers true for every subject, evaluated one subject at a time and stopping at the first false. A subject equal to the principal is answered by the port exactly as in 6b; the kernel no longer treats "the subject is the principal" as satisfied on its own | allow (`relationship:<permission>`)                                                                                                                   | "one permission never implies another: view does not allow collect"; "requires authority over every subject in a multi-participant target"; through the identity port: "SPK-IAM-003: a guardian holding only collect cannot read the child (no implied view)" (`people.spec.ts`) and "SPK-IAM-003: view does not imply collect, through the port and through the kernel authorization path" (`relationships.spec.ts`) |
| 8    | `teamRole`, target has `teamEntryId`, `hasTeamRole` is true (the competition port answers `member` for any effective role, `co_captain` for captains and co-captains, and `captain` for a co-captain only under the rule set's `roster.coCaptainMayActAsCaptain`)                                                                                                                 | allow (`team_role:<role>`)                                                                                                                            | "grants team-role actions only to the role holder on that team entry"; competition implementation: "TEAM_AUTHORITY_IMPL: downward hierarchy, co-captain policy from the rule set, ended roles, and the kernel authorization path" (`apps/api/src/modules/competition/__tests__/team-entries.spec.ts`)                                                                                                                 |
| 9    | otherwise                                                                                                                                                                                                                                                                                                                                                                         | deny (`no applicable authority`)                                                                                                                      | "reports protected denials as not-found and unprotected denials as access denied"                                                                                                                                                                                                                                                                                                                                     |

Facility scope (step 5): allowed when the target has no `facilityId`, or the principal's `facilityIds` is empty, or it contains the target's facility.

Steps 6b and 7 call the port on every decision without caching, so a revocation or a review restriction is visible on the next request ("SPK-IAM-006: revocation denies on the very next check and enqueues identity.access_grant_revoked" and "SPK-IAM-003: grants outside their effective window do not confer authority", `relationships.spec.ts`). Earlier revisions of this document described step 6 as an unconditional self allow; that was the kernel before it consulted the port for self decisions. The identity module's `README.md` ("Kernel limitations worked around here") still describes that older behaviour; see Ambiguities item 9.

### A.5 Outcomes of `require`

| Decision                                                            | Error thrown (`packages/contracts/src/errors.ts`)     | HTTP | `nextAction`                        |
| ------------------------------------------------------------------- | ----------------------------------------------------- | ---- | ----------------------------------- |
| allowed                                                             | none                                                  |      |                                     |
| denied and `target.protected`                                       | `NOT_FOUND` (`errors.protectedNotFound(target.type)`) | 404  | `verify_reference`                  |
| denied, anonymous principal                                         | `AUTHENTICATION_REQUIRED`                             | 401  | `authenticate`                      |
| denied with `no applicable authority` and the target named subjects | `PARTICIPANT_AUTHORITY_REQUIRED`                      | 403  | `request_participant_authority`     |
| any other denial                                                    | `ACCESS_DENIED` with `details.action`                 | 403  | `contact_support_or_request_access` |

The protected check precedes the anonymous check in `require`, so an anonymous request against a protected target is answered with `NOT_FOUND` (code reading; the anonymous test uses an unprotected target).

### A.6 Where authorization is called

- Kernel pattern: inside `unitOfWork.run` after loading the real record, before the state-machine and revision checks, and before `audit.record` and `outbox.enqueue` (`CLAUDE.md`, "Command pattern"). Example: `OperationalExceptions.transition` requires `exceptions.manage` with the record's organization and facility, then checks `expectedRevision`, then audits (`operational-exceptions.service.ts`; test "exceptions deduplicate while open, transition with authorization and revision checks, and are audited" in `unit-of-work.spec.ts`).
- `OperationsService.find` first checks organization, then `decide(operations.read)` with `protected: true`, then allows the requester by comparing `requested_by.accountId` with `principal.accountId`. The requester rule is a service rule, not a registry field (`operations.service.ts`; test "shows an operation to its requester and to staff, and hides it across accounts and organizations" in `auth-and-operations.spec.ts`).
- Identity and competition commands follow the kernel pattern. The authority ports read through the kernel's transaction context (A.1), so a `require` inside `unitOfWork.run` sees the command's own writes; `TeamAuthority.hasTeamRole` relies on this when a role assigned earlier in the same command must count. The identity `README.md` ("Kernel limitations worked around here") still describes the earlier module-local workaround; see Ambiguities item 9.
- Catalog acknowledgments (`apps/api/src/modules/catalog/services/acknowledgments.service.ts`): `require(catalog.record_acknowledgment)` runs before the transaction. Staff: a role check plus the rule that a staff actor is never the signer (`ACCESS_DENIED`). Customers: `subjectPersonIds: [subject]` with `protected: true`. The signer is then re-checked inside the transaction through the identity `AUTHORITY_LOOKUP_PORT` with the transaction handle (catalog `README.md`). This is a documented deviation from "authorize inside `unitOfWork.run`" that predates the kernel's transaction context; see Ambiguities item 13.
- Catalog public reads (`offerings.service.ts`, `loadVisible` and `listPublic`): an anonymous principal skips the registry; any other principal is evaluated with `decide(catalog.read_catalog)` and gets the staff view when allowed, otherwise the child-safe `PublicOffering` view of published states only, or `NOT_FOUND` (§4.14; test "SPK-CAT-001: a draft offering is created with its definition and is visible to staff only" in `offerings.spec.ts`).
- `identity.accept_claim` is registered with `staffRoles: []` and no customer flag, so `decide` would deny every non-system principal; the service never calls `require` with it. Acceptance is authorized by the claim token and the verified account (service rule), and the action id is used as the audit label (`claims.service.ts`; test "SPK-IAM-002: self-claim validation" in `claims-and-accounts.spec.ts`). See Ambiguities item 11.
- `GET /v1/me` has no action: any authenticated principal reads their own principal, person, memberships and current authorities (`people.controller.ts`; test "GET /v1/me reports the principal, person, memberships and current authorities" in `principal-resolver.spec.ts`).
- Public routes (`@Public()`) skip the registry entirely; the six that exist are listed in C.16.

## Part B. Actions registered in code today

**Verified** in its entirety. Rows are in `actionRegistry.list()` order (alphabetical by id) within each module.

## Part C. Proposed action matrix

**Proposed** in its entirety: nothing in Part C is registered in code. Rows marked **Pending decision** are additionally gated on an operator answer; the owner is from §6.6. The identity, catalog, competition, scheduling and facilities rows that are registered today have moved to Part B; what remains of those modules here is only what the registry does not cover, and Part B.7 records how each earlier row was reconciled.

How the rows were derived:

- One row per "must be able to", "must support", command or interface in §3 and §4.8, named `<module>.<verb>` with the module from §4.2 and the module `README.md` files.
- Staff roles follow the §2.1 responsibilities with least privilege (§4.14). `general_manager` and `system_administrator` do not inherit other roles' writes in Part C (see `role-matrix.md` §7); the registry already departs from this for catalog, competition and scheduling writes (B.7), which is a live review item for the Sponsor (pending-decisions table).
- The customer authority column uses the kernel vocabulary only: `self`, a grant name from SPK-IAM-003 (`view`, `register`, `pay`, `receive_messages`, `complete_forms`, `collect`), or a team role (`captain`, `co_captain`, `member`). A grant name alone already includes self when the relationship port agrees (Part A steps 6b and 7). `none` means staff only.
- Marks: ✓ allowed within organization and facility scope; ◐ allowed only for the actor's own assignment (module-level target check, **Proposed**; the kernel has no assignment scope today); blank = not allowed.
- Facility or vendor facts (which fields, hours, prices, taxes, providers) are never assumed; where a default comes from the specification it is reproduced as **Proposed**.

Module index: C.1 core and administration, C.2 identity (remaining rows), C.3 catalog (remaining rows), C.4 enrollment, C.5 competition (remaining rows), C.6 scheduling (remaining rows), C.7 finance, C.8 workforce, C.9 entry, C.10 facilities (remaining rows), C.11 communications, C.12 support, C.13 migration, C.14 reporting, C.15 automation, C.16 public routes, C.17 composite checks.

## Ambiguities for the kernel and the specification

1. **Assignment scope (◐).** The kernel has no notion of "my assignment". The registries already list `coach` and `official` on `scheduling.read_inventory`, `scheduling.read_schedule`, `scheduling.read_event`, `facilities.report_issue` and `operations.read`, and `coach` on `catalog.read_catalog`, `catalog.read_acknowledgments` and `catalog.evaluate_discounts`, each for the whole facility scope (**Verified**). Either each module performs the target narrowing before `require`, or `AuthorizationTargetInput` gains an `assignedPersonIds` field evaluated like `subjectPersonIds`. **Proposed**: the kernel field, so that the generated matrix can show it.
2. **Facility mismatch blocks the customer paths.** A staff principal with a listed role at another facility is denied before self, grant and team checks run (Part A step 5a). **Verified** behaviour, **Proposed** change to fall through; see `role-matrix.md` §8 item 2.
3. **One `teamRole` and one `subjectPermission` per action.** Captain-or-co-captain and register-or-pay combinations need either two actions, two `require` calls (C.17), or array-valued fields. For team roles the competition port resolves captain-or-co-captain with a hierarchy (A.7), so a single `teamRole` suffices and the open question is the co-captain policy value, **Pending decision** (League manager). For grants: engineering choice (**Proposed**: two `require` calls, which keeps the registry honest about what each check means). The registry already follows the two-actions pattern where two meanings exist (`identity.create_relationship` and `identity.create_relationship_self_service`; `catalog.approve_participation_policy` and `catalog.approve_financial_policy`).
4. **No grant for RSVP, profile edits, or delegating grants.** SPK-IAM-003 lists six permissions. The registry's engineering defaults: profile edits and contact points under `register` (`identity.update_person`, `identity.add_contact_point`); delegation through `identity.create_invitation` under `view` plus "only what you hold" (service rule); RSVP is still mapped to `register` in C.5. All three stay **Pending decision** (Operator/privacy owner; Product and operations).
5. **System principals bypass the registry.** Correct for workers, but any recipient or authority recheck in a handler must call the ports directly (C.17). **Proposed**: a lint rule or test that no outbox handler calls `authorization.require` with a system principal and expects a denial.
6. **Service rules are invisible to the registry.** **Verified** examples: the `operations.read` requester rule; `identity.accept_claim` authorized by token; the creator-guardian rule of `identity.revoke_access`; the "delegate only what you hold" rule of `identity.create_invitation`; "a staff actor is never the signer" of `catalog.record_acknowledgment`; the staff-versus-public branch of the catalog reads; `GET /v1/me` with no action. A generator reading only `actionRegistry.list()` would render none of them. **Proposed**: an optional `notes` field on `ActionDefinition` rendered into the generated file, and a `serviceAuthorized: true` marker for actions such as `identity.accept_claim` so they are not rendered as "nobody".
7. **`general_manager` and `system_administrator` breadth.** Least privilege is assumed throughout Part C; the registry grants both roles the catalog and scheduling writes listed in the pending-decisions table. No §6.6 row owns this. **Pending decision** (fallback owner: Sponsor).
8. **Public reads are invisible to the registry.** `@Public()` routes bypass `AuthorizationService`. `docs/api/openapi.json` lists five operations with `security: []` (C.16) but not `GET /v1/ready`, which is `@Public()` in `health.controller.ts` and has no contract. A generator that reads OpenAPI alone would miss it. **Proposed**: emit the public-route table from the Nest route metadata (`IS_PUBLIC_KEY`) and fail CI when a public route has no OpenAPI entry, so that a protected read is never accidentally public and no public route is undocumented.
9. **The identity README describes an older kernel.** `apps/api/src/modules/identity/README.md` ("Kernel limitations worked around here") says the kernel's self short-circuit lets a child principal act on themselves for `pay` and `collect` before consulting the port, and that the kernel calls the relationship port without a transaction handle. Both are outdated: `authorization.service.ts` asks the port for every self decision that names a `subjectPermission` (kernel test "never lets a child principal pay or collect for themselves, even on an allowSelf action"), and `kernel/database/transaction-context.ts` carries the transaction in async context (the identity alias file says so itself). The README paragraphs need removing (not this document's file to change).
10. **The team-role hierarchy lives in the port, not the registry.** `competition.read_team_entry` declares `teamRole: 'member'` and is satisfied by captains and co-captains; `competition.manage_roster` declares `captain` and is satisfied by a co-captain only under the rule set's `roster.coCaptainMayActAsCaptain` (A.1). A generator reading `actionRegistry.list()` would render the literal role only. **Proposed**: render a fixed hierarchy note under every competition table, and keep the co-captain flag in the policy register (**Pending decision**, League manager).
11. **`identity.accept_claim` cannot pass `decide`.** It is registered with `staffRoles: []` and neither `allowSelf` nor `subjectPermission`, so the registry renders it as an action nobody may perform; in fact the service authorizes it by token (A.6). **Proposed**: the `serviceAuthorized` marker of item 6, or a `notes` entry, so the generated matrix is not misleading.
12. **Counting the registry, and its drift.** The repair assignment that triggered this revision counted 25 identity actions and 57 module actions; the files hold 24 identity actions and, without competition, 56 module actions. While this revision was being written the competition module (part 1) landed with 18 more, so Part B now lists 77 actions including the three kernel ones, and competition part 2 is under construction. Part B is therefore a dated snapshot; a generator would settle the count mechanically on every build.
13. **Leftovers of the earlier port limitation.** The kernel now carries the transaction in async context (`kernel/database/transaction-context.ts`), so the authority ports already see the command's transaction. Two workarounds from before that change remain: `acknowledgments.service.ts` calls `require` before `unitOfWork.run` (A.6), and `identity.transaction-context.ts` survives as an alias. **Proposed**: move the acknowledgment check inside the transaction and delete the alias; neither changes any permission.
14. **Scheduling and facilities tests do not load the identity port.** They run with `FakePrincipalResolver` and the deny-all relationship fallback, so the guardian `view` path of `scheduling.read_event` is verified only at the kernel level, not end to end. **Proposed**: one scheduling test created with `principalResolver: 'module'` and `IdentityModule` imported, as the catalog and competition tests already do.

## How `permission-matrix.generated.md` will replace Part B and Part C

1. Each module declares its actions once in `apps/api/src/modules/<module>/<module>.actions.ts` with `defineActions({...})`, giving every action `id`, `description`, `staffRoles`, the optional `allowSelf`, `subjectPermission`, `teamRole`, and `requirements` naming the SPK ids (`CLAUDE.md`, "Command pattern"). **Verified** for identity, catalog, competition (part 1), scheduling and facilities; **Proposed** for the nine remaining modules and for competition part 2.
2. A script (proposed `apps/api/scripts/emit-permission-matrix.ts`, wired as `pnpm permissions` next to the existing `pnpm openapi` in `package.json`) imports every module so registrations run, calls `actionRegistry.list()`, and renders the Part B columns (one table per module prefix, the same role abbreviations, customer authority from `allowSelf`, `subjectPermission`, `teamRole`, the `notes` of Ambiguities item 6) into `docs/package-a/permission-matrix.generated.md`, together with the public routes read from the route metadata and cross-checked against `docs/api/openapi.json` (Ambiguities item 8). **Proposed**; neither the script nor the file exists.
3. A CI check compares the generated file with the committed one (as `pnpm openapi` does for `docs/api/openapi.json`) and fails when an action has empty `requirements`. **Proposed**.
4. Review rule for the diff between Part C and the generated file: a generated action without a Part C row was added without a specification derivation and needs one; a Part C row without a generated action is not yet implemented and stays **Proposed**; a role difference is a review item for the owner named in the pending-decisions table. **Proposed**; applied by hand once in B.7.
5. Until the generated file exists, Part B is hand-derived from the registries and is the only **Verified** content; Part C is the contract that the builders of the nine remaining modules implement. Part B must be re-derived whenever a `<module>.actions.ts` changes, which is the maintenance cost the generator removes.
