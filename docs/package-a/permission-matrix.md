# Permission matrix

Status legend: **Verified** = implemented and tested in this repository today (file cited). **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval. **Pending decision** = needs an operator answer; the owner is named from specification §6.6. "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22).

This is the Package A "Permission matrix" (§6.7) and the input to the "Authority matrix" (§6.5). It has three parts:

- **Part A** describes the authorization model as implemented in the kernel (**Verified**).
- **Part B** lists the actions registered in code today (**Verified**): three, all in the kernel.
- **Part C** is the proposed action-level matrix derived from every "must be able to" and command in §3 and from the API table in §4.8 (**Proposed** in its entirety).

Part C will be replaced by `docs/package-a/permission-matrix.generated.md`, generated from the code's action registry (`actionRegistry.list()` in `apps/api/src/kernel/authorization/actions.ts`). That file and its generator do not exist yet, and no domain module has registered actions: there is no `apps/api/src/modules/*/<module>.actions.ts` in the repository today (every module is a scaffold; see each module's `README.md`). Companion documents: [`role-matrix.md`](role-matrix.md), `decision-register.md`, `requirement-cross-reference.md`.

The original platform specification (`.docx`, §1.3) and the existing local demonstration (§1.4) are not in this repository; no permission below is derived from either.

### A.2 Action definition fields

| Field               | Type                                                                                        | Meaning                                                                                               |
| ------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `id`                | `<module>.<verb>`                                                                           | Unique action identifier; the module prefix matches §4.2 ownership                                    |
| `description`       | text                                                                                        | Human-readable purpose                                                                                |
| `staffRoles`        | `StaffRole[]`                                                                               | Staff roles permitted within their organization and facility scope                                    |
| `allowSelf`         | boolean, optional                                                                           | A principal may act when every subject person is themselves                                           |
| `subjectPermission` | one of `view`, `register`, `pay`, `receive_messages`, `complete_forms`, `collect`, optional | A principal may act when they hold this grant over every subject person (SPK-IAM-003)                 |
| `teamRole`          | one of `captain`, `co_captain`, `member`, optional                                          | A principal may act when they hold this role on the target's `teamEntryId`                            |
| `requirements`      | string[], optional                                                                          | Specification requirement ids the action implements (documentation; rendered by the future generator) |

### A.3 Target fields

| Field              | Meaning                                                                                             |
| ------------------ | --------------------------------------------------------------------------------------------------- |
| `type`, `id`       | Record type and id (id may be null for collection-level actions)                                    |
| `organizationId`   | Must equal the principal's organization                                                             |
| `facilityId`       | Optional; when present, the staff facility scope is enforced                                        |
| `subjectPersonIds` | Persons whose private data the target concerns (participants, payers); drives self and grant checks |
| `protected`        | Customer-private record: a denial is reported as `NOT_FOUND`                                        |
| `teamEntryId`      | Season team entry for team-role checks (`AuthorizationTargetInput`)                                 |

### A.4 Decision order

`AuthorizationService.decide` returns the first matching outcome:

| Step | Condition                                                                                           | Outcome                                                   | Test in `apps/api/src/kernel/__tests__/authorization.spec.ts`                                                                              |
| ---- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 1    | Action id not in the registry                                                                       | deny (`unknown action`)                                   | (no dedicated test)                                                                                                                        |
| 2    | `principal.kind === 'anonymous'`                                                                    | deny (`authentication required`)                          | "denies anonymous principals"                                                                                                              |
| 3    | `principal.organizationId !== target.organizationId`                                                | deny (`organization scope mismatch`)                      | "never crosses organization scope, even for staff and system actions"                                                                      |
| 4    | `principal.kind === 'system'`                                                                       | allow (`system`)                                          | "system principals are allowed within their organization only"                                                                             |
| 5    | staff: a listed role is held and the facility scope matches                                         | allow (`staff role`)                                      | "allows staff by role and enforces facility scope"                                                                                         |
| 5a   | staff: a listed role is held, facility scope does not match                                         | deny (`facility scope mismatch`), evaluation stops        | same test                                                                                                                                  |
| 5b   | staff: no listed role is held                                                                       | continue to step 6 with the staff member's own `personId` | (no dedicated test; see `role-matrix.md` §8 item 9)                                                                                        |
| 6    | `allowSelf` and every subject equals `principal.personId`                                           | allow (`self`)                                            | "allows self when the action permits it"                                                                                                   |
| 7    | `subjectPermission` and, for every subject, the subject is the principal or `hasPermission` is true | allow (`relationship:<permission>`)                       | "one permission never implies another: view does not allow collect"; "requires authority over every subject in a multi-participant target" |
| 8    | `teamRole`, target has `teamEntryId`, `hasTeamRole` is true                                         | allow (`team_role:<role>`)                                | "grants team-role actions only to the role holder on that team entry"                                                                      |
| 9    | otherwise                                                                                           | deny (`no applicable authority`)                          | "reports protected denials as not-found and unprotected denials as access denied"                                                          |

Facility scope (step 5): allowed when the target has no `facilityId`, or the principal's `facilityIds` is empty, or it contains the target's facility.

### A.5 Outcomes of `require`

| Decision                                                            | Error thrown (`packages/contracts/src/errors.ts`)     | HTTP | `nextAction`                        |
| ------------------------------------------------------------------- | ----------------------------------------------------- | ---- | ----------------------------------- |
| allowed                                                             | none                                                  |      |                                     |
| denied and `target.protected`                                       | `NOT_FOUND` (`errors.protectedNotFound(target.type)`) | 404  | `verify_reference`                  |
| denied, anonymous principal                                         | `AUTHENTICATION_REQUIRED`                             | 401  | `authenticate`                      |
| denied with `no applicable authority` and the target named subjects | `PARTICIPANT_AUTHORITY_REQUIRED`                      | 403  | `request_participant_authority`     |
| any other denial                                                    | `ACCESS_DENIED` with `details.action`                 | 403  | `contact_support_or_request_access` |

The protected check precedes the anonymous check in `require`, so an anonymous request against a protected target is answered with `NOT_FOUND` (code reading; the anonymous test uses an unprotected target).

### A.6 Where authorization is called

- Inside `unitOfWork.run` after loading the real record, before the state-machine and revision checks, and before `audit.record` and `outbox.enqueue` (`CLAUDE.md`, "Command pattern"). Example: `OperationalExceptions.transition` requires `exceptions.manage` with the record's organization and facility, then checks `expectedRevision`, then audits (`operational-exceptions.service.ts`; test "exceptions deduplicate while open, transition with authorization and revision checks, and are audited" in `unit-of-work.spec.ts`).
- `OperationsService.find` first checks organization, then `decide(operations.read)` with `protected: true`, then allows the requester by comparing `requested_by.accountId` with `principal.accountId`. The requester rule is a service rule, not a registry field (`operations.service.ts`; test "shows an operation to its requester and to staff, and hides it across accounts and organizations" in `auth-and-operations.spec.ts`).
- Public routes (`@Public()`) skip the registry; today only `GET /v1/health` (`health.controller.ts`; test "serves health publicly and echoes correlation ids").

## Part C. Proposed action matrix

**Proposed** in its entirety. Nothing in Part C is implemented. Rows marked **Pending decision** are additionally gated on an operator answer; the owner is from §6.6.

How the rows were derived:

- One row per "must be able to", "must support", command or interface in §3 and §4.8, named `<module>.<verb>` with the module from §4.2 and the module `README.md` files.
- Staff roles follow the §2.1 responsibilities with least privilege (§4.14). `general_manager` and `system_administrator` do not inherit other roles' writes (see `role-matrix.md` §7).
- The customer authority column uses the kernel vocabulary only: `self`, a grant name from SPK-IAM-003 (`view`, `register`, `pay`, `receive_messages`, `complete_forms`, `collect`), or a team role (`captain`, `co_captain`, `member`). A grant name alone already includes self (Part A step 7). `none` means staff only.
- Marks: ✓ allowed within organization and facility scope; ◐ allowed only for the actor's own assignment (module-level target check, **Proposed**; the kernel has no assignment scope today); blank = not allowed.
- Facility or vendor facts (which fields, hours, prices, taxes, providers) are never assumed; where a default comes from the specification it is reproduced as **Proposed**.

Module index: C.1 core and administration, C.2 identity, C.3 catalog, C.4 enrollment, C.5 competition, C.6 scheduling, C.7 finance, C.8 workforce, C.9 entry, C.10 facilities, C.11 communications, C.12 support, C.13 migration, C.14 reporting, C.15 automation, C.16 public routes, C.17 composite checks.

## Ambiguities for the kernel and the specification

1. **Assignment scope (◐).** The kernel has no notion of "my assignment". Either each module performs the target narrowing before `require`, or `AuthorizationTargetInput` gains an `assignedPersonIds` field evaluated like `subjectPersonIds`. **Proposed**: the kernel field, so that the generated matrix can show it.
2. **Facility mismatch blocks the customer paths.** A staff principal with a listed role at another facility is denied before self, grant and team checks run (Part A step 5a). **Verified** behaviour, **Proposed** change to fall through; see `role-matrix.md` §8 item 2.
3. **One `teamRole` and one `subjectPermission` per action.** Captain-or-co-captain and register-or-pay combinations need either two actions, two `require` calls (C.17), or array-valued fields. **Pending decision** (League manager) for team roles; engineering choice for grants (**Proposed**: two `require` calls, which keeps the registry honest about what each check means).
4. **No grant for RSVP, profile edits, or delegating grants.** SPK-IAM-003 lists six permissions; Part C maps RSVP to `register` and leaves child profile edits and grant delegation pending (Operator/privacy owner; Product and operations).
5. **System principals bypass the registry.** Correct for workers, but any recipient or authority recheck in a handler must call the ports directly (C.17). **Proposed**: a lint rule or test that no outbox handler calls `authorization.require` with a system principal and expects a denial.
6. **`operations.read` requester rule lives in the service.** The generated matrix will not show it unless the generator reads a documented exception list. **Proposed**: an optional `notes` field on `ActionDefinition` rendered into the generated file.
7. **`general_manager` and `system_administrator` breadth.** Least privilege is assumed throughout Part C; no §6.6 row owns this. **Pending decision** (fallback owner: Sponsor).
8. **Public reads are invisible to the registry.** `@Public()` routes bypass `AuthorizationService`; the generated matrix should list them from the OpenAPI document (`security: []`, as `GET /health` is registered in `packages/contracts/src/api/operations.ts`) so that a protected read is never accidentally public.

## How `permission-matrix.generated.md` will replace Part C

All **Proposed**:

1. Each module declares its actions once in `apps/api/src/modules/<module>/<module>.actions.ts` with `defineActions({...})`, giving every action `id`, `description`, `staffRoles`, the optional `allowSelf`, `subjectPermission`, `teamRole`, and `requirements` naming the SPK ids from the "Covers" column above (`CLAUDE.md`, "Command pattern").
2. A script (proposed `apps/api/scripts/emit-permission-matrix.ts`, wired as `pnpm permissions` next to the existing `pnpm openapi` in `package.json`) imports every module so registrations run, calls `actionRegistry.list()`, and renders the Part B and Part C columns (one table per module prefix, the same role abbreviations, customer authority from `allowSelf`, `subjectPermission`, `teamRole`) into `docs/package-a/permission-matrix.generated.md`, together with the public routes read from `docs/api/openapi.json`.
3. A CI check compares the generated file with the committed one (as `pnpm openapi` does for `docs/api/openapi.json`) and fails when an action has empty `requirements`.
4. Review rule for the diff between Part C and the generated file: a generated action without a Part C row was added without a specification derivation and needs one; a Part C row without a generated action is not yet implemented and stays **Proposed**; a role difference is a review item for the owner named in the pending-decisions table.
5. Until the generated file exists, Part C is the contract that module builders implement, and Part B is the only **Verified** content.
