# Decision register

Status legend: **Verified** = implemented and tested in this repository today (file cited); **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval; **Pending decision** = needs an operator answer (owner named from spec §6.6). "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23). Repository last inspected for this revision on 2026-10-24.

Package A deliverable: the decision half of the "Policy and decision register" (§6.7) and the evidence for the Package A gate, "unresolved decisions are owned and their affected workflows identified" (§6.5). The policy half is `docs/package-a/policy-register.md`; it references the `DEC-###` identifiers defined here.

## 1. What this document is

- One record per row of the §6.6 "Operator decisions" table (17 records, section 4).
- One record per provider-selection gate of §5.2 (6 records, section 5), separated from the §6.6 "Providers and production accounts" row because each gate blocks a different package.
- One record per explicit "Proposed default", "Proposed", "subject to operator confirmation" or "pending ... approval" statement anywhere in the specification (23 records, section 6), found with the search in section 10.2.
- One record per explicit "approved ..." or "configured ..." sub-decision that the specification attaches to a §6.6 row without resolving it (25 records, section 7).
- One record per conditional capability of §1.6, because "Conditional capability applicability" (§6.6) is one row for ten capabilities with different affected workflows (11 records, section 8).
- One record per decision that a companion Package A or architecture document raised without a `DEC` record, as `policy-register.md` rule 3 (section 7 of that document) and `authority-matrix.md` section 9 require (11 records, section 12; placed after the maintenance rules so that the rule numbers cited by companion documents, "rule 10.1(n)", stay stable).
- Total: 93 records, `DEC-001` to `DEC-093`.

**Verified** (by inspection of the repository on 2026-10-24): no file under `docs/` records an operator answer, an approval, an effective date or a questionnaire response. `docs/runbooks/` holds three runbooks (`cutover.md`, `outage-and-offline.md`, `recovery.md`); each marks every owner, duration and procedure value as **Proposed** or **Pending decision**, cites this register for the owner (for example `cutover.md` section 13, "The named owner is **Pending decision** (DEC-068)"), and therefore contains no answer. Every record below has answer status "unknown", a blank named owner, a blank effective date and a blank target date. Nothing in this register is an operator fact. The specification is the only source of the proposed values, and it is itself titled "proposed master specification" (DEC-024). Engineering placeholders that exist in code are listed in section 3, item 9, and are marked "proposed (engineering placeholder only)" on the record that owns them; none of them is an answer.

## 3. Verified context: the code boundary these decisions gate

The repository enforces the provider gates and keeps policy values out of code. Each statement cites its file; "tested" names the passing test. Inspection date for this section: 2026-10-24; statements contradicted by later code are corrected in place and marked **Verified 2026-10-29 (correction)**.

1. **Local identity provider refuses production.** **Verified**: `apps/api/src/kernel/config.ts` defines `AUTH_MODE` as `local` or `oidc` (default `local`) and rejects `AUTH_MODE=local` with `NODE_ENV=production` with the message "AUTH_MODE=local is a development/test identity provider and cannot run in production; select a managed identity provider (decision register: providers)". Tested by `apps/api/src/kernel/__tests__/config.spec.ts` "refuses the local identity provider in production". The same test file proves "requires DATABASE_URL in production" (PGlite is development and test only) and "requires a long local secret".
2. **No managed identity adapter exists.** `apps/api/src/kernel/kernel.module.ts` builds `LocalJwtIdentityProvider` only when `AUTH_MODE === 'local'`; for any other mode the `IDENTITY_PROVIDER` factory throws "AUTH_MODE=oidc: a managed identity provider has not been selected (specification §5.2). This throw is implemented but no test names it (search of `apps/api/src/kernel/__tests__` on 2026-10-24), so it is not marked Verified. Consequence of items 1 and 2 together: no configuration boots the API in production today; production start requires DEC-018 answered and an adapter behind the port.
3. **Ports, not vendors.** **Verified**: `IdentityProviderPort` (`apps/api/src/kernel/auth/identity-provider.port.ts`), `PrincipalResolverPort` (`apps/api/src/kernel/auth/principal-resolver.port.ts`), `RelationshipAuthorityPort` and `TeamAuthorityPort` (`apps/api/src/kernel/authorization/authorization.port.ts`), with injection tokens in `apps/api/src/kernel/tokens.ts` and deny-all fallbacks when no module has registered an implementation (`kernel.module.ts`). ## 10. How this register is maintained

### 10.1 Rules (**Proposed**, consistent with §6.6 and §6.7)

1. **Ids are permanent.** `DEC-###` is never reused or renumbered. A superseded or rejected record keeps its row with proposal status "superseded" or "rejected" and a note naming the replacement.
2. **Answering a record** means writing all of: answer status "answered" or "not applicable", the named owner (a person holding the required owner role), the effective date, and evidence (the questionnaire response, meeting record or signed document, cited by file or link; for a policy value, the `approvals` row and the approved `policy_versions` row in `packages/db/migrations/0200_catalog_core.sql`, by identifier). An answer without all four is not an answer.
3. **"Not applicable" is an answer**, with the same four fields plus the reason. "Unknown" is never rewritten as "not applicable" (§6.6).
4. **Proposal status** moves from "proposed" to "approved", "rejected" or "superseded" only together with an answer. "none" becomes "proposed" when engineering proposes a default; the proposing change is cited in supporting evidence, and a value that exists in code only so that a mechanism can run is written as "proposed (engineering placeholder only)" and listed in section 3, item 9. A proposal is never marked "approved" by the engineer who made it.
5. **Target dates** are set by the sponsor (DEC-017) when a package is scheduled, for every record whose "Must be resolved before" falls inside that package. **Gate reading (Proposed, confirmation recorded under DEC-017):** this document reads the Package A gate (§6.5, "unresolved decisions are owned and their affected workflows identified") as met when every record carries a required owner role from §6.6 and an affected scope naming requirement ids, acceptance journeys or §6.3 tasks; it does not require answers or named persons. "Named owner" is blank on all 93 records today. Whether role-level ownership satisfies "owned" is itself a Sponsor decision, so the gate is not called met until DEC-017 records that confirmation or the persons are named.
6. **Code that needs an unanswered value** uses a placeholder marked as such and cites the `DEC` id, the way `apps/api/src/kernel/config.ts` cites "decision register: providers" and `scheduling.policy.ts`, `facilities.policy.ts`, `catalog.policy.ts` and `identity.shared.ts` cite the §6.6 row. A placeholder is never promoted to a default in documentation; the register row stays "unknown" until answered.
7. **Cross-document consistency.** The cross-reference's Status column cites the §6.6 owner, which must match the required owner here. The policy register's Status column cites `DEC` ids; answering a `DEC` record updates every `POL` row that cites it in the same pull request. Every companion document that names a `DEC` record uses this register's "Required owner" wording for it, verbatim; a discrepancy is corrected in the companion document, never by changing the record here (section 10.3).
8. **Review trigger.** A pull request that implements a requirement listed in a record's affected scope cites the record in its description and, if it introduces or changes a proposed value, updates the record.
