# Decision register

Status legend: **Verified** = implemented and tested in this repository today (file cited); **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval; **Pending decision** = needs an operator answer (owner named from spec §6.6). "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23).

Package A deliverable: the decision half of the "Policy and decision register" (§6.7) and the evidence for the Package A gate, "unresolved decisions are owned and their affected workflows identified" (§6.5). The policy half is `docs/package-a/policy-register.md`; it references the `DEC-###` identifiers defined here.

## 1. What this document is

- One record per row of the §6.6 "Operator decisions" table (17 records, section 4).
- One record per provider-selection gate of §5.2 (6 records, section 5), separated from the §6.6 "Providers and production accounts" row because each gate blocks a different package.
- One record per explicit "Proposed default", "Proposed", "subject to operator confirmation" or "pending ... approval" statement anywhere in the specification (23 records, section 6), found with the search in section 10.2.
- One record per explicit "approved ..." or "configured ..." sub-decision that the specification attaches to a §6.6 row without resolving it (25 records, section 7).
- One record per conditional capability of §1.6, because "Conditional capability applicability" (§6.6) is one row for ten capabilities with different affected workflows (11 records, section 8).
- Total: 82 records, `DEC-001` to `DEC-082`.

**Verified** (by inspection of the repository on 2026-10-23): no file under `docs/` records an operator answer, an approval, an effective date or a questionnaire response, and `docs/runbooks/` is empty. Every record below therefore has answer status "unknown", a blank named owner, a blank effective date and a blank target date. Nothing in this register is an operator fact. The specification is the only source of the proposed values, and it is itself titled "proposed master specification" (DEC-024).

## 3. Verified context: the code boundary these decisions gate

The repository enforces the provider gates and keeps policy values out of code. Each statement cites its file; "tested" names the passing test.

1. **Local identity provider refuses production.** **Verified**: `apps/api/src/kernel/config.ts` defines `AUTH_MODE` as `local` or `oidc` (default `local`) and rejects `AUTH_MODE=local` with `NODE_ENV=production` with the message "AUTH_MODE=local is a development/test identity provider and cannot run in production; select a managed identity provider (decision register: providers)". Tested by `apps/api/src/kernel/__tests__/config.spec.ts` "refuses the local identity provider in production". The same test file proves "requires DATABASE_URL in production" (PGlite is development and test only) and "requires a long local secret".
2. **No managed identity adapter exists.** `apps/api/src/kernel/kernel.module.ts` builds `LocalJwtIdentityProvider` only when `AUTH_MODE === 'local'`; for any other mode the `IDENTITY_PROVIDER` factory throws "AUTH_MODE=oidc: a managed identity provider has not been selected (specification §5.2). Record the decision in docs/package-a/decision-register.md and implement the adapter behind IdentityProviderPort." This throw is implemented but no test names it, so it is not marked Verified. Consequence of items 1 and 2 together: no configuration boots the API in production today; production start requires DEC-018 answered and an adapter behind the port.
3. **Ports, not vendors.** **Verified**: `IdentityProviderPort` (`apps/api/src/kernel/auth/identity-provider.port.ts`), `PrincipalResolverPort` (`apps/api/src/kernel/auth/principal-resolver.port.ts`), `RelationshipAuthorityPort` and `TeamAuthorityPort` (`apps/api/src/kernel/authorization/authorization.port.ts`), with injection tokens in `apps/api/src/kernel/tokens.ts` and deny-all fallbacks when no module has registered an implementation (`kernel.module.ts`). Tested by `apps/api/src/kernel/__tests__/authorization.spec.ts` ("denies anonymous principals", "never crosses organization scope, even for staff and system actions", "allows staff by role and enforces facility scope", "one permission never implies another: view does not allow collect", "reports protected denials as not-found and unprotected denials as access denied") and `apps/api/src/kernel/__tests__/auth-and-operations.spec.ts` ("rejects missing, malformed, expired and unknown tokens with the error contract").
4. **Fakes that exist.** **Verified**: `FakePrincipalResolver` in `apps/api/src/testing/test-app.ts` is the default principal directory for every API test. `apps/api/src/kernel/__tests__/inbox.spec.ts` registers a handler for a provider named `fake-payments` against the generic `Inbox` and proves "records duplicates once and processes each event once" and "retries failed events and dead-letters with an exception after repeated failure"; the duplicate guard is the `unique (provider, provider_event_id)` constraint on `inbox_events` in `packages/db/migrations/0001_core_schema.sql`. Webhook idempotency therefore does not depend on the processor chosen in DEC-019.
5. **Fakes that do not exist yet.** **Verified** by search on 2026-10-23: no `PaymentProviderPort`, messaging port, accounting port, hardware port or `Fake*Provider` adapter for them exists under `apps/` or `packages/`. The finance module README's "Provider adapters behind PaymentProviderPort with a deterministic fake" and the `CLAUDE.md` rule "code against a port interface with a deterministic fake adapter (`Fake*Provider`) ... Do not add a vendor SDK or create accounts" are the required practice and are **Proposed** until those modules land. The same rule is why DEC-018 to DEC-023 block only the adapter, not the domain work (§5.2: "Unrelated domain work may proceed against tested adapters and synthetic fixtures").
6. **Organization scope is structural.** **Verified**: every core table carries `organization_id` (`packages/db/migrations/0001_core_schema.sql`); the principal's organization comes from the resolver, never the request (`apps/api/src/kernel/auth/auth.guard.ts`, `PrincipalSchema` in `packages/contracts/src/principal.ts`); cross-organization access is denied even for staff and system principals (`authorization.spec.ts`). Relevant to DEC-070.
7. **Lifecycles carry no policy values.** **Verified**: `packages/contracts/src/state-machines.ts` defines the §4.6 machines, tested in `packages/contracts/src/state-machines.spec.ts` ("holds have exactly one terminal outcome (SPK-REG-006)", "unknown payment outcomes resolve only to authoritative terminal states (SPK-PAY-007)", "checkout keeps provider success with local failure visible as recovery_required (§4.11)", "results never go backwards from official (SPK-RESULT-001)"). None of them contains a duration, an approval rule, a refund amount or a publication authority; those values are the records in this register.
8. **Override reasons and policy references have a place to go.** `CommandMetaSchema` in `packages/contracts/src/commands.ts` accepts `reason` and `policyReferences` (§4.9). **Verified** for `reason`: `audit_records.reason` is written in `apps/api/src/kernel/__tests__/unit-of-work.spec.ts`. `policyReferences` is accepted by the schema but no test exercises it, so it is implemented, not Verified. No `PolicyVersion`, `Acknowledgment` or `Approval` table exists (§4.4 "Policies"); see the policy register, section 2.
9. **Engineering defaults that are not operator policies.** **Verified** as code, and flagged so no reader mistakes them for answers: half-away-from-zero rounding and largest-remainder allocation in `packages/contracts/src/money.ts` (tested in `money.spec.ts`; DEC-007); `AUTH_TOKEN_TTL_SECONDS` default 8 hours, `IDEMPOTENCY_TTL_HOURS` 24, `OUTBOX_LOCK_LEASE_SECONDS` 60 in `apps/api/src/kernel/config.ts`; `outbox_events.max_attempts` default 10 in `0001_core_schema.sql`. None of these is cited as a proposed value below.

## 10. How this register is maintained

### 10.1 Rules (**Proposed**, consistent with §6.6 and §6.7)

1. **Ids are permanent.** `DEC-###` is never reused or renumbered. A superseded or rejected record keeps its row with proposal status "superseded" or "rejected" and a note naming the replacement.
2. **Answering a record** means writing all of: answer status "answered" or "not applicable", the named owner (a person holding the required owner role), the effective date, and evidence (the questionnaire response, meeting record or signed document, cited by file or link; once the §4.4 `Approval` entity exists, its identifier). An answer without all four is not an answer.
3. **"Not applicable" is an answer**, with the same four fields plus the reason. "Unknown" is never rewritten as "not applicable" (§6.6).
4. **Proposal status** moves from "proposed" to "approved", "rejected" or "superseded" only together with an answer. "none" becomes "proposed" when engineering proposes a default; the proposing pull request is cited in supporting evidence. A proposal is never marked "approved" by the engineer who made it.
5. **Target dates** are set by the sponsor (DEC-017) when a package is scheduled, for every record whose "Must be resolved before" falls inside that package. The Package A gate (§6.5) is met when every record has a required owner and an affected scope, which is the state of this version; it does not require answers.
6. **Code that needs an unanswered value** uses a placeholder marked as such and cites the `DEC` id, the way `apps/api/src/kernel/config.ts` cites "decision register: providers". A placeholder is never promoted to a default in documentation; the register row stays "unknown" until answered.
7. **Cross-document consistency.** The cross-reference's Status column cites the §6.6 owner, which must match the required owner here. The policy register's Status column cites `DEC` ids; answering a `DEC` record updates every `POL` row that cites it in the same pull request.
8. **Review trigger.** A pull request that implements a requirement listed in a record's affected scope cites the record in its description and, if it introduces or changes a proposed value, updates the record.

### 10.2 Regeneration procedure (**Proposed**; the commands are the ones used to build this version)

```
# 1. Rows of §6.6 (must equal section 4)
awk '/^### 6.6 Operator decisions/,/^Each decision record/' docs/spec/master-specification.md | grep '^| [A-Z]' | tail -n +2 | wc -l

# 2. Candidate statements for sections 6 and 7 (every hit must map to a record or to a listed exclusion)
grep -n -i -E 'proposed|pending|approved|approval|operator|subject to|confirmation|if enabled|where permitted|separately configured' docs/spec/master-specification.md

# 3. Provider gates of §5.2 (must equal section 5)
awk '/^### 5.2 Provider-selection gates/,/^### 5.3/' docs/spec/master-specification.md | grep '^- '

# 4. Conditional capabilities of §1.6 (must equal section 8, less the pickup-sessions record)
grep -n 'Conditional capabilities include' docs/spec/master-specification.md
```

Hits from step 2 that are not records: role names ("Finance operator", "Facilities operator", "Support operator", §2.1); state names ("Proposed" assignment state, "Pending disputes", "Refund pending" error, §3.10, §3.9, §4.10); record fields ("Application approval", "Approval" as a deliverable or entity, §3.3, §4.4, §6.5); and descriptive uses of "approved" that name an authorization step already covered by a record (for example "commit the approved revision", SPK-SCHED-006, covered by the scheduling command contract rather than a decision).

## 11. Specification ambiguities encountered

Each item is **Proposed** handling; the operator may re-map an owner.

1. **§6.6 has no row for** architecture (DEC-025), mobile release definitions (DEC-061), the tentative RSVP state (DEC-064) or visitor categories (DEC-071). The closest-fit owners are this document's proposal and are marked "(no exact §6.6 row)" in the record.
2. **"Pickup" has two meanings.** Package E "Pickup when applicable" is read as supervised pickup (DEC-075); Package G "Pickup" and §2.2 Discover are read as pickup sessions (DEC-082). The cross-reference makes the same reading (its item 2).
3. **SPK-SCHED-003's "ten-minute turnover requirement" is an example**, not a proposed default ("A game ending at 19:00 with a ten-minute turnover requirement does not make its space available at 19:00"). It is not recorded as a proposal; buffers are part of DEC-001.
4. **The §1.3 product decisions are stated as already made**, but the document that states them is titled "proposed master specification" and no approval exists in the repository. They are recorded under DEC-024 with answer status "unknown", so adoption is explicit rather than assumed.
5. **§5.5 names "program and league owners"**, which is not a §6.6 label; DEC-067 maps them to Program manager and League manager.
6. **SPK-REG-007 "Approval does not promise capacity unless the approved policy explicitly reserves it"** is read as a proposed default of "no reservation by approval" (DEC-029), since the sentence states what happens absent a contrary policy.
7. **The hold duration (DEC-027) depends on a different owner's gate**: "payment-method testing" cannot happen before the payment processor is selected (DEC-019). The record names both.
8. **"Operating approval" and "operator" are used for several §6.6 roles.** §4.15 "pending operating approval" is mapped to Operations (the "Pickup and outage procedure" row); §4.14 "responsible operator and advisers" is mapped to Operator/privacy owner.
9. **§6.6 "Providers and production accounts" is one row for six gates** that block five different packages; section 5 splits it so each gate has its own "Must be resolved before".
10. **The cross-reference marks SPK-PAY-003 rounding as a verified kernel slice**; this register records that the value is an unapproved engineering default (DEC-007, section 3 item 9). Both statements are true: the mechanism is tested, the policy is not decided.
11. **§6.5 Package B names "Managed identity integration" as a deliverable** while DEC-018 is unanswered; the record places the gate before that deliverable, and section 3 records that no production boot path exists until then.
