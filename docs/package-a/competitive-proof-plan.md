# Competitive proof plan

Status legend: **Verified** = implemented and tested in this repository today (file cited); **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval; **Pending decision** = needs an operator answer (owner named from spec §6.6). "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23).

This document is the plan for the §6.4 "Competitive proof": the eight benchmark workflows, the comparable inputs each needs, what is measured, how setup and scope differences are disclosed, and the rules that govern targets and competitor claims. It contains no measured value, no target and no percentage. Companion documents: `metric-dictionary.md` (MET-091 to MET-094 define the four task measurements; MET-095 to MET-105 the operating outcome metrics per §1.2 success measure), `journeys.md` (journeys A, B, C, D, E), `acceptance-fixtures.md` (`SPK-AT-###` fixtures reused as benchmark inputs), `native-acceptance-matrix.md` (device evidence for customer workflows), `decision-register.md` (DEC-045 targets, DEC-017 acceptance authority).

## 1. What this document is

- §1.2 names the ambition ("replace DaySmart for the complex's agreed operating scope and deliver a substantially better experience"), the ten areas in which improvement must be measurable, and three rules: feature availability alone does not establish superiority; outcomes must be demonstrated through realistic, repeatable tasks; the comparison program must use current, verified competitor workflows, and unsupported claims about competitor limitations must not enter product requirements or marketing.
- §6.4 names the eight workflows, requires comparable inputs with disclosed differences in setup or scope, and says: "Proposed improvement targets must be set after baseline measurement. Do not invent percentage improvements in advance and report them as achieved."
- Every statement here is **Proposed** except where it cites a repository mechanism (**Verified**) or an operator decision (**Pending decision**). **Verified** by inspection on 2026-10-23: no benchmark, baseline, competitor verification record or measurement result exists in this repository; `docs/runbooks/` is empty; the native apps and the staff dashboard that the workflows run on are not in the repository (`docs/architecture/overview.md`). Nothing in this document describes how the competitor product behaves. The competitor's name appears only because §1.2 names it.
- The "original platform specification" (`.docx`, §1.3 item 1) and the "existing local demonstration" (§1.4) are not in this repository; neither is used as a baseline or as a source of competitor behaviour.
- No number appears in this document: no participant count, run count, duration, price, capacity, team count, improvement target or threshold. Where a workflow needs a quantity to be fixed (how many children, how many teams), the plan says it must be fixed in the measurement plan before baseline and recorded with the run, and names the owner.

## 2. Rules of the proof

| Id  | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Source            | Status                                                                                                |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- | ----------------------------------------------------------------------------------------------------- |
| P1  | Targets follow baselines. No improvement target exists for any workflow until (a) the competitor baseline and (b) the platform baseline have both been measured under this plan and recorded. Targets are then proposed by the measurement owner and approved by the sponsor (DEC-045). A target set before a baseline is invalid and must not be cited.                                                                                                                                                                          | §6.4              | **Proposed** rule; targets: **Pending decision** (Sponsor, DEC-045)                                   |
| P2  | No invented improvements. No percentage, multiple or "faster by" statement about the platform relative to the competitor may appear in any requirement, ticket, release note, gate review or marketing material unless it is the arithmetic result of two recorded baselines measured under the same measurement plan version, cited by run identifiers. A statement without that citation is removed.                                                                                                                            | §6.4, §1.2        | **Proposed**                                                                                          |
| P3  | Competitor claims come from current verified workflows only. Memory, marketing material, third-party reviews, sales conversations and older experience are not verification. Claims expire when the competitor changes or at the review date in the record, whichever is first. | §1.2              | **Proposed**                                                                                          |
| P4  | Feature availability is not superiority. A workflow is compared on outcomes (task completion, errors, time, assistance), never on a feature checklist. A feature the competitor lacks is recorded as a scope difference (section 6), not as a win.                                                                                                                                                                                                                                                                                | §1.2              | **Proposed**                                                                                          |

Competitor runs use the complex's own legitimate access to the competitor product under its terms; no credential sharing, scraping or probing outside normal use; competitor data used in runs is synthetic or the complex's own. ## 3. What is measured

The four measurements of §6.3 apply to every run of every workflow, as defined in `metric-dictionary.md`:

| Measurement     | Metric  | Definition used in every run                                                                                                                                                                                                                                                      | Captured by                                                                                               |
| --------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Task completion | MET-091 | The run reached the workflow's end state (section 4, column "End state and required outcome") with every required outcome observable. Partial completion is a non-completion with the stage reached recorded.                                                                     | Observer checklist against the end-state definition; platform-side evidence where available (section 5.3) |
| Errors          | MET-092 | Each error event: a validation failure, a wrong or unexpected outcome, a dead end requiring back-navigation, a recovery the participant had to perform, classed as product-caused or participant-caused by the observer using the written error taxonomy of the measurement plan. | Observer log with timestamps; platform error log where available                                          |
| Time            | MET-093 | Elapsed time from the start signal to the end state; waiting on an external provider (payment, messaging) is timed separately and disclosed.                                                                                                                                      | Observer clock; platform timestamps where available                                                       |
| Assistance      | MET-094 | Each assistance event: a question the facilitator answered, a hint, an intervention by a staff member, a document consulted. The pre-run briefing is not assistance.                                                                                                              | Observer log                                                                                              |

Results are reported per run, then summarised per workflow, platform and participant role. The summary method (which central and spread statistics) is fixed in the measurement plan before baseline and is the same for both platforms (P7). No summary is reported without its runs.

## 4. The eight benchmark workflows

Each workflow is defined by: the §1.2 success measures it evidences; the roles who perform it; the start signal and the end state with its required outcome; the comparable inputs that must be fixed before baseline (P5); the journeys and acceptance fixtures it reuses; the policy decisions that must be approved before a valid run (P9); and the scope notes that are likely to need disclosure (section 6).

## 7. Competitor verification record

A claim about the competitor is admissible only with a record in this form (P3). The records live with the measurement plan, not in this document; this document holds no competitor behaviour.

| Field       | Content                                                                                            |
| ----------- | -------------------------------------------------------------------------------------------------- |
| Record id   | Stable identifier                                                                                  |
| Workflow    | One of the eight, or the specific behaviour verified                                               |
| Claim       | The single, specific statement verified (what the product did when the named steps were performed) |
| Verified by | Named person and their role (they/them); the account owner for the access used                     |
| Verified on | Date; the product version or release identifier visible in the product, if any                     |
| Access used | The complex's own subscription or a trial, and the terms it was used under (P12)                   |
| Evidence    | Recording or screenshots, stored with the measurement plan; no customer or child data              |
| Scope       | What was not verified (features not tried, configurations not available to the complex)            |
| Review date | When the record expires and must be re-verified; immediately on a known competitor release         |
| Status      | current, expired, superseded                                                                       |

Any sentence about the competitor in a requirement, ticket, gate review or marketing text must cite a current record id; one that cannot is removed (P2, P3).
