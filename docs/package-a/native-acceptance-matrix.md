# Native acceptance matrix

Status legend: **Verified** = implemented and tested in this repository today (file cited); **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval; **Pending decision** = needs an operator answer (owner named from spec §6.6). "No answer yet" never becomes "not applicable" (§6.6).

Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23).

This is the "Native acceptance matrix" artifact of §6.7. It lists every native scenario that §6.2 requires, the accessibility requirements of SPK-UX-009, the capabilities of SPK-UX-001 and the release definitions of §4.13, each with the evidence that must exist on a physical iOS device and a physical Android device before the Package E gate ("representative customers and operators complete connected tasks on actual devices", §6.5) can pass. Companion documents: `screen-and-journey-inventory.md` (screen ids `SCR-C-##` referenced below, section 7.4), `journeys.md`, `acceptance-fixtures.md` (SPK-AT-018, SPK-AT-027), `decision-register.md` (`DEC-###`), `integration-register.md` (app store, push and staging entries).

## 1. What this document is

- Rows: the fifteen required scenarios of §6.2 (section 4), the accessibility requirements of SPK-UX-009 (section 5), the SPK-UX-001 capabilities not already covered by a §6.2 scenario (section 6), and the nine §4.13 release definitions plus the two §4.13 engineering requirements (section 7).
- Columns: iOS physical device, Android physical device, evidence required, status. Each row also names its source, the acceptance criterion, the screens involved and the pending decisions that gate it.
- Every row is **Pending** and belongs to Package E. **Verified** by inspection on 2026-10-23: the native customer apps are not in this repository (`docs/architecture/overview.md`, "Not in this repository: Native customer apps (Expo) and the React staff dashboard, Package E"); no Expo project, no app store configuration and no device test evidence exists under `apps/`. No row can be Verified until signed builds exist and have been tested on physical devices. Where the API-side half of a scenario is already implemented and tested, the row says so and cites the file; that never makes the row Verified.
- **A web preview or successful bundle export does not satisfy these requirements** (§6.2, verbatim). SPK-UX-001: "An Expo web build may remain available for development. It is not a substitute for native acceptance." Evidence from a simulator, an emulator, a web preview, a development client, a storybook, a bundle export log or a CI build log is recorded as supporting material only and never as a pass. The status of a row changes from Pending only on evidence captured on a physical device running a signed build.
- The "original platform specification" (`.docx`, §1.3 item 1) and the "existing local demonstration" (§1.4) are not in this repository. The demonstration's customer navigation cannot be inspected and is not cited; the specification says native iOS and Android replace the original mobile-web-first direction (§1.3).
- No device model, OS version number, app version number, session duration, link domain or store account is named here. Each of those is a release definition (§4.13) and is **Pending decision** (DEC-061, Technical lead/operator; privacy declarations with the Operator/privacy owner).

## 3. Status vocabulary for the device columns

| Value                       | Meaning                                                                                                                       |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Pending (Package E)         | No signed build exists; no evidence exists. The value every row holds today.                                                  |
| Pending: blocked by DEC-### | As above, and the scenario cannot even be specified fully until the named decision is answered.                               |
| Evidence captured           | Evidence per section 2 exists for this build and device; awaiting review.                                                     |
| Accepted                    | Reviewed by the acceptance authority (DEC-017) and recorded in the release evidence ledger for a named build and environment. |
| Failed                      | Evidence shows a criterion not met; defect reference required.                                                                |

The matrix never uses "not applicable" for a platform column: a scenario that genuinely has no platform counterpart (none in this document) would still carry an owner and a decision.
