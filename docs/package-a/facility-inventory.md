Status legend: **Verified** = implemented and tested in this repository today (file cited). **Proposed** = engineering proposal from the specification or from this document, awaiting operator approval. **Pending decision** = needs an operator answer; the owner is named from specification §6.6. Last derived from specification v2.0 (2026-10-22). Source: `docs/spec/master-specification.md` (repository copy supplied 2026-10-23).

Decision record: DEC-001 in `decision-register.md`. ## 7. Closures

One row per known closure: public holidays, planned maintenance, events that take the whole facility. Intervals are facility-local here and stored as UTC ranges (**Verified** `closures.during`). A closure's impact on games, programs, rentals, staff and customers is computed by the scheduling module (SPK-SCHED-009; **Verified** `closures.spec.ts` "the preview names every affected game, program and rental"); for each event a closure cancels, scheduling emits `scheduling.event_changed` naming the closure (**Verified** `closures.spec.ts` "SPK-AT-009: applying a facility closure with cancel_affected cancels every affected event with a notice naming the closure"), and the communications module composes change and cancellation notices from that event (**Verified** `apps/api/src/modules/communications/README.md`; `communications/services/schedule-notices.spec.ts`). The effect on financial obligations is resolved by finance (**Proposed**; the finance module is a scaffold, `apps/api/src/modules/finance/README.md`).

| [ ]                                  | [ ]                               | [ ]            | [ ]          | [ ]               | [ ]                                         | [ ]                         | unknown       | Operations  | [ ]            |
| EXAMPLE (synthetic): Example Complex | (whole facility)                  | [unknown]      | [unknown]    | Illustration only | `holiday`                                   | [unknown]                   | synthetic     | none        | none           |

Recurring closures are not modelled as a rule in the `closures` table (**Verified** `0300_scheduling_core.sql`). Recurring maintenance is held by the facilities module: a `preventive_schedules` row stores a recurrence (`frequency`, `interval`, `byWeekday`, `startDate`, `until` or `count`), a facility-local start time, a duration, the facility timezone, one affected space (`resource_id`, not null) and an optional asset; generation materializes each occurrence's maintenance task and restriction exactly once, and the restriction creates a `maintenance` closure through the scheduling authority (SPK-FAC-005; **Verified** `0900_facilities_core.sql`; `facilities/__tests__/preventive-schedules.spec.ts` "SPK-FAC-005: generation materializes tasks and future restrictions through the scheduling authority, exactly once per occurrence"; `facilities/__tests__/schema-invariants.spec.ts` "SPK-FAC-005: a preventive schedule materializes each occurrence at most once"). Because a preventive schedule names one space, a recurring whole-facility closure is not one schedule. For a recurring maintenance closure, state the rule in those terms (frequency, interval, weekdays, start date, end date or count, local start time, duration) so it can be loaded as a preventive schedule; load recurring closures that are not maintenance (holidays, whole-facility events) as individual `closures` rows. Both loading routes are **Proposed**.

## 9. Required equipment

SPK-SCHED-001 "Required equipment" and SPK-FAC-001 maintainable assets ("Turf areas", "Goals", "Nets", "Boards", "Dividers", "Lighting", "Scoreboards", "Relevant equipment"). Three stores exist today:

- `resources.required_equipment` is a descriptive JSON array on the space that needs the equipment (**Verified** `0300_scheduling_core.sql`; `resources.spec.ts` "SPK-SCHED-001/002: creates a pitch, its subdivisions and the unit mapping that makes the whole conflict with every half").
- Each physical item is a facilities `assets` row. `kind` is one of `turf`, `goal`, `net`, `boards`, `divider`, `lighting`, `scoreboard`, `equipment`, `other` (the SPK-FAC-001 list plus `other`); `identifier` (tag or serial) names at most one non-retired asset per facility; optional `resource_id` names the space the item belongs to; `status` is one of `in_service`, `restricted`, `out_of_service`, `retired` (**Verified** `0900_facilities_core.sql`; `AssetKind` in `packages/contracts/src/api/facilities.ts`; `facilities/__tests__/maintenance-tasks.spec.ts` "SPK-FAC-001: assets are registered, edited, retired and scoped to their organization"; `facilities/__tests__/schema-invariants.spec.ts` "SPK-FAC-001: an identifier names at most one non-retired asset per facility").
- Equipment conflicts are `equipment` party commitments on events (**Verified** `event_commitments.party_type` in `0300_scheduling_core.sql`; the overlap exclusion constraint covers every party type, and its tests exercise team and official commitments, not equipment).

The three are not linked today: `required_equipment` names no asset, and `event_commitments.party_id` carries no foreign key to `assets` (scheduling README "Known gaps"). Committing a specific asset to an event and deriving a space's required equipment from its assets is **Proposed**. `assets` has no maintenance owner column; the owner is recorded per maintenance task (`maintenance_tasks.assigned_owner_person_id`) or per preventive schedule task template (**Verified** `0900_facilities_core.sql`), so the "Owner for maintenance" column below would become the default owner on those records (**Proposed**).

Fill one row per equipment type a resource or format needs, with the asset kind each item would be registered under. A quantity of N would be loaded as N `assets` rows, each with its own identifier where the item carries one (**Proposed**). Movable items that cannot be in two places at once must be listed so they can become commitments.
