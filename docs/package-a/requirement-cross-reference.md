"No answer yet" never becomes "not applicable" (§6.6).

## 1. What this document is

- One row for every requirement identifier in the specification: 139 `SPK-<DOMAIN>-###` requirements, the 12 numbered integrity invariants of §4.7, and the 28 `SPK-AT-###` acceptance journeys of §6.1. Total: 179 rows. (**Verified**: counted with `grep -oE 'SPK-[A-Z]+-[0-9]{3}' docs/spec/master-specification.md | sort -u` on the repository copy, 167 distinct ids; the §4.7 list was counted by hand.)
- For each row: the owning module, the lifecycle stage reached today, the evidence for that stage, the delivery package, the decision status, and the legacy identifier column required by §1.5.

## 2. How to read the columns

**Id** and **Spec §**: exactly as the specification numbers them. The §4.7 invariants have no `SPK` identifier; they are referenced as "§4.7 (n)".

**Title / short statement**: a compression of the requirement text. The specification remains the authoritative wording.

**Owning module** (§4.2 and `apps/api/src/modules/<module>/README.md`):

- Where a module README names the section or identifier, the owner is as written in that README (**Verified** as a statement of what the README says). Five modules are implemented today (identity, catalog, scheduling, competition part 1, facilities); the other nine are scaffolds (section 3).
- Where no README names it, the owner is marked "(proposed)" and is this document's **Proposed** assignment.
- Customer app and staff dashboard surfaces (§2) have no module owner in §4.2; they are Package E surfaces that do not exist in this repository.

**Lifecycle stage** (§1.5: Specified, Implemented, Verified, Operator accepted, Released). Values used today:

| Value                       | Meaning                                                                                                                                                                                                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Specified                   | The requirement exists only in the specification. No module code in this repository implements any of it.                                                                                                                                                                |
| Implemented (kernel slice)  | A shared-kernel or shared-package artefact implements one named clause of the requirement and is exercised only by a generic test (not a test named after the requirement). The clause is named in the evidence column. Everything else in the requirement is Specified. |
| Implemented (module slice)  | A module implements one named clause and cites the id in its source (regeneration step 3, section 10.2), but no passing test is named after the id; the evidence names the source file and any generic test that exercises the clause. Everything else is Specified.     |
| Verified (kernel slice)     | A test in `apps/api/src/kernel`, `packages/contracts` or `packages/db` that names the requirement id, or tests its exact clause, passes today. The test file is cited. Everything else in the requirement is Specified.                                                  |
| Verified (module slice)     | A test in the owning module named after the requirement id passes today and covers the clauses it names; the evidence column names the clauses that remain Specified (usually because they belong to a scaffold module).                                                 |
| Verified (module)           | Tests in the owning module named after the requirement id pass today and, together with any kernel or contracts test, cover every clause of the requirement as the specification words it. No clause remains Specified. The requirement has not been operator accepted.  |
| Operator accepted, Released | No row has reached these stages.                                                                                                                                                                                                                                         |

**Evidence**: the test file(s) and test title(s) that justify the stage. "none yet" means no code or test exists for the row. Test titles are quoted verbatim from the files.

**Package** (§6.5, A to G): the package whose deliverable list names the capability. Where §6.5 does not name the capability, the cell carries `*` and the assignment is this document's **Proposed** reading; section 9 lists each such case. The delivery sequence as a whole is the specification's proposal.

**Status**: **Verified** where the evidence column cites a passing test (the marker applies to the slice the lifecycle column names; for "Verified (module)" it applies to the whole requirement). **Proposed** where a row or a remaining clause depends on no open operator decision. **Pending decision (owner)** where the row's behaviour depends on a §6.6 decision; the owner is the "Required owner" from the §6.6 table, and the `DEC-###` identifier, where cited, is the record in `docs/package-a/decision-register.md`.

**Legacy id**: "pending: original specification not in repository" on every row (section 8).

## 10. How this matrix is maintained

### 10.1 Rules

1. **One row per requirement id, forever.** The row inventory is the set of ids in `docs/spec/master-specification.md` plus the numbered §4.7 list plus the §6.1 table. Rows are never deleted or renumbered (§1.5). A requirement withdrawn by a later specification version keeps its row with lifecycle "Specified" and a note naming the version that withdrew it. (**Proposed** rule; consistent with §1.5.)
2. **Tests are named after requirement ids** (CLAUDE.md, "Tests": "Every requirement you implement gets a test named after it; every integrity invariant gets a test that proves the database rejects the violation, not only the service."). The practice in force today (**Verified**): the id appears in the `describe` or `it` title, usually as a leading prefix, for example `it('SPK-FAC-005: generation materializes tasks and future restrictions through the scheduling authority, exactly once per occurrence')` in `apps/api/src/modules/facilities/__tests__/preventive-schedules.spec.ts`, `it('§4.7 (3): division capacity is enforced by the database on placement')` in `apps/api/src/modules/competition/__tests__/competition-schema.spec.ts`, and `describe('transactional outbox and durable dispatch (§4.12, SPK-AT-023)')` in `apps/api/src/kernel/__tests__/outbox.spec.ts`. Several titles name two ids separated by a slash ("SPK-AT-003 / SPK-CAP-005: ..."); both rows cite the test.
3. **File placement** (**Verified** practice, **Proposed** as a rule): module tests live in `apps/api/src/modules/<module>/__tests__/<topic>.spec.ts` (API tests with `createTestApp()`) and next to the code for pure rules (`<module>.state-machines.spec.ts`, `time/recurrence.spec.ts`, `pricing/discount-evaluator.spec.ts`); each module has a schema-invariant file (`identity-schema.spec.ts`, `catalog-schema.spec.ts`, `competition-schema.spec.ts`, scheduling and facilities `schema-invariants.spec.ts`) whose tests show the database rejecting the violation (`isUniqueViolation`, `isExclusionViolation`, or a check-constraint or trigger error from `@sportspark/db`). Acceptance journeys are proven today inside the owning module's `__tests__` (section 9, item 13); a dedicated `apps/api/src/__tests__/journeys/spk-at-###-<slug>.spec.ts` directory for journeys that span more than two modules is **Proposed** and does not exist.
4. **Evidence must be a passing test, cited by file and title.** A screen, a README, a comment or a type alone never moves a row past Specified (§1.5: "A visible screen is not evidence that its underlying workflow is complete"). A source citation of the id without a test named after it moves a row to "Implemented" at most (regeneration step 3).
5. **Stage transitions** (**Proposed**):
   - Specified to Implemented: code merged under the owning module with the id cited in comments and the commit message (CLAUDE.md), but no test named after the id yet, or only generic tests.
   - Implemented to Verified (slice): a test named after the id passes in `pnpm test`; the evidence column names the clauses it covers and the clauses that remain Specified.
   - Verified (slice) to Verified (module): tests named after the id cover every clause of the requirement as worded; for concurrency-sensitive rows, the `test-postgres` CI job has run and its result is recorded in the release evidence ledger.
   - Verified to Operator accepted: the §6.3 or §6.2 acceptance task is completed by the named operator and recorded in the release evidence ledger (§6.7) with build and environment (§6.8 item 11).
   - Operator accepted to Released: the release owner (§6.8 item 12) records the release in the ledger.
   - "Slice" qualifiers are removed only when the whole requirement, not a clause, meets the stage.
6. **Status column discipline**: a row stays **Pending decision** until the decision register records the answer as "answered" with an owner and effective date (§6.6); "unknown" is never rewritten as "not applicable". A **Verified** marker never removes a **Pending decision** marker on the same row: a mechanism can be proven while its operator values are unknown (SPK-FAC-001, SPK-SCHED-001, SPK-PAY-003).
7. **Package column** changes only when the sponsor approves a change to the §6.5 sequence; the `*` marker is removed when §6.5 itself names the capability.
8. **Legacy column** is filled only from the original specification once it is in the repository (section 8).
9. **Review trigger**: every pull request that cites an `SPK` id or a `§4.7` invariant (CLAUDE.md requires the citation) updates the affected rows in the same pull request. A pull request that lands a module (a new migration range in use, a README moving from "scaffold" to "implemented") also updates section 3, section 6 and the counts in section 7.

### 10.2 Regeneration procedure (**Proposed**, commands are the ones used to build this version on 2026-10-24)

```
# 1. Ids the specification defines (must equal the rows in section 4, plus §4.7 (1)..(12))
grep -oE 'SPK-[A-Z]+-[0-9]{3}' docs/spec/master-specification.md | sort -u

# 2. Ids and sections that tests name (must equal the evidence column and section 6);
#    run from the repository root so that .claude/worktrees and node_modules are not scanned
grep -rnoE 'SPK-[A-Z]+-[0-9]{3}|§4\.7 \([0-9]+\)|§4\.7 invariant [0-9]+|§[0-9]+(\.[0-9]+)?' \
  --include='*.spec.ts' --exclude-dir=node_modules --exclude-dir=dist apps packages

# 2b. Test titles verbatim, one line per describe/it, with the per-file count
for f in $(find apps packages -name '*.spec.ts' -not -path '*/node_modules/*' | sort); do
  echo "== $f ($(grep -cE '^\s*(it|test)\(' "$f") tests)"; grep -nE "^\s*(describe|it|test)\(" "$f"; done

# 3. Ids that source code cites but no test names (candidates for "Implemented", never "Verified")
grep -rnoE 'SPK-[A-Z]+-[0-9]{3}' --include='*.ts' --exclude='*.spec.ts' \
  --exclude-dir=node_modules --exclude-dir=dist apps packages

# 4. Which modules are implemented (README status) and which migrations exist
grep -m1 -nE 'Status' apps/api/src/modules/*/README.md; ls packages/db/migrations

# 5. Confirm the evidence still passes before publishing an update
pnpm test
```

Differences between step 1 and section 4 mean a specification change: add rows. Differences between step 2 and the evidence column mean a stale matrix: fix the rows, never the tests. Any test in step 2 that names an id but fails removes "Verified" from that row until it passes again. The `.claude/worktrees` directory, when present, holds other working copies and must not be scanned: run the commands on `apps` and `packages` only, as written.
