# Team screens (SCR-C-21 to SCR-C-29)

Customer app screens for teams and captains (spec §2.2, §3.4, §3.5, §3.11, §3.15, §3.16; journeys
A and B in `docs/package-a/journeys.md`; rows SCR-C-21 to SCR-C-29 in
`docs/package-a/screen-and-journey-inventory.md`).

Status legend (§6.7): **Verified** = implemented and asserted by a jest test here, against a mocked
API. **Proposed** = engineering proposal awaiting approval. **Pending decision** = waits on an
operator answer (owners in `docs/package-a/decision-register.md`). Nothing here has passed native
acceptance on signed builds and devices (§6.2), including VoiceOver, TalkBack and large text.

screen of SCR-C-17 (`/invitations/<id>?type=team`). Shared pieces live in `src/features/teams/`.

## API operations used

| Operation                                                                            | Where                                                                    |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| `GET /v1/me/team-entries` (CMP-02)                                                   | SCR-C-21 team list; refreshed after creating or renewing an entry        |
| `GET /v1/me/team-invitations`, `POST /v1/team-invitations/{id}/decline` (CMP-03)     | SCR-C-21 open invitations, decline with the revision read                |
| `GET /v1/person-names` (ID-02)                                                       | SCR-C-21 given names of family members on a team                         |
| `GET /v1/team-entries/{id}` `viewer` (`actingAsCaptain`, `availableActions`, CMP-02) | Every team screen: which tools are offered                               |
| `POST /v1/me/support-requests` (SUP-01)                                              | SCR-C-22 the captain contacts the operating team about the team          |
| `POST /v1/team-entries/{id}/roles/handover` (CMP-13)                                 | SCR-C-23 hand over the captain or co-captain role                        |
| `GET /v1/fixtures/{id}` `responses`, `venue` (CMP-04)                                | SCR-C-24 answers the person may give (with revisions), facility zone     |
| `GET`, `POST /v1/fixtures/{id}/availability-requests` (CMP-14)                       | SCR-C-24 the captain asks players without an answer, earlier requests    |
| `POST /v1/disputes/{id}/withdraw` (CMP-12)                                           | SCR-C-28, SCR-C-29 withdraw an open dispute with a reason and revision   |
| `GET /v1/pools/{id}`, `GET /v1/pools/{id}/standings` (CMP-15)                        | SCR-C-28 a tournament pool's table                                       |
| `GET /v1/me/permissions` capabilities (K-12)                                         | SCR-C-28 tournament pools shown only where `tournaments` is on (DEC-078) |

## Not available from the API (rendered as "not available" or not offered)

- Which tournament pool a team plays in: there is no pool list for a division or an entry, and no
  pool id on the workspace or the team list, so `PoolStandingsScreen` is reachable only by its
  route; Standings says so where tournaments are on (SCR-C-28).
- A captain's list of the disputes they filed across a season: `GET /v1/disputes` is for league
  staff only, so disputes are read per game (`GET /v1/fixtures/{id}/disputes`, SCR-C-29).
- The workspace's upcoming games carry no venue, so their times use the device's zone (named);
  the game itself (`GET /v1/fixtures/{id}`) and the team list carry the facility's zone.
