# Team screens (SCR-C-21 to SCR-C-29)

Customer app screens for teams and captains (spec §2.2, §3.4, §3.5, §3.11, §3.15, §3.16; journeys
A and B in `docs/package-a/journeys.md`; rows SCR-C-21 to SCR-C-29 in
`docs/package-a/screen-and-journey-inventory.md`).

Status legend (§6.7): **Verified** = implemented and asserted by a jest test here, against a mocked
API. **Proposed** = engineering proposal awaiting approval. **Pending decision** = waits on an
operator answer (owners in `docs/package-a/decision-register.md`). Nothing here has passed native
acceptance on signed builds and devices (§6.2), including VoiceOver, TalkBack and large text.

test is in `__tests__/team-routes.test.tsx`.

## Not available from the API (rendered as "not available" or not offered)

- Which tournament pool a team plays in: there is no pool list for a division or an entry, and no
  pool id on the workspace or the team list, so `PoolStandingsScreen` is reachable only by its
  route; Standings says so where tournaments are on (SCR-C-28).
- A captain's list of the disputes they filed across a season: `GET /v1/disputes` is for league
  staff only, so disputes are read per game (`GET /v1/fixtures/{id}/disputes`, SCR-C-29).
- The workspace payload (`GET /v1/team-entries/{id}`) carries no venue for its upcoming games, so
  each game's zone is read from `GET /v1/fixtures/{id}` (the read Availability makes for the same
  games); this is an extra read per game, not a missing value.

## SCR-C-20 and SCR-C-24: answering for a child

Both screens record answers with `POST /v1/fixtures/{id}/availability`, and the API decides who may
answer for whom. Which permission lets a guardian answer for a child is DEC-090 (**Pending
decision**; the register proposes `register`). SCR-C-24 renders the answers the API lists for the
viewer in the game's `responses` (CMP-04), which the API fills by its proposed `register` rule, so
the screen offers a child's answer only when the API does and holds no default of its own; if the
decision lands elsewhere, the API's list changes and the screen follows. SCR-C-20's RSVP control
(`features/today/RsvpControl.tsx`, another area) answers for the signed-in person only and does not
read `responses`, so it offers no child answer until DEC-090 is decided. The difference is which
read each screen renders, not a different rule; aligning SCR-C-20 is for that area.
