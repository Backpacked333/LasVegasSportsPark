# Programs, registrations and finance screens

Staff dashboard screens SCR-S-14, SCR-S-15 (Programs and camps), SCR-S-24 to SCR-S-27
(Registrations and waitlists) and SCR-S-35 to SCR-S-38 (Finance) from
`docs/package-a/screen-and-journey-inventory.md` section 5, against the stage-3 API
(`docs/api/openapi.json`).

Status legend (§6.7): **Verified** = implemented and asserted by a jsdom test in this app.
**Proposed** = engineering handling awaiting operator approval. **Pending decision** = needs an
operator answer (owners in `docs/package-a/decision-register.md`); the screen shows the pending
state and never invents the value. jsdom tests are not staff acceptance on real devices (§6.3).

## Layout

- Routes: `routes.tsx` (`registrationFinanceRoutes()`, registered once in `src/App.tsx` ahead of
  the area placeholders, so they win for `/programs`, `/registrations` and `/finance`: React
  Router ranks equal routes by order). The three areas are also marked `ownRoutes` in
  `src/navigation/areas.ts` for the shell's area filter. Route parameters and search parameters are
  opaque ids or view names only (§4.14). `/finance/orders/:orderId` (SCR-S-35) is new.
- Screens: `src/screens/programs/`, `src/screens/registrations/`, `src/screens/finance/`, tests in
  each `__tests__/`. Shared pieces here: `CommandError` (the §4.10 error presentation), `fields`
  (labelled controls), `format` (minor units, facility-local time), `labels` (machine state names
  as staff labels), `pending` (DEC references), `names` (participant, offering and team names
  read from their owning APIs), `facilities` (the facility directory), `OfferingPicker`,
  `Eligibility`, `RefundView`, `ObligationFigures`, `offline`, and, new in stage 4:
  `consequence` (ENR-03 accepted consequence), `PackageEntitlements` (session packages and
  redemption reversal), `MembershipSuspensions`, `PaymentAttempts` (`GET /payments` list),
  `RefundList` (`GET /refunds` list), `LiveAttempt` (FIN-01 payment on its way), `PersonSearch`
  (`GET /people`, names only, paged; `PersonReferenceField` puts it next to every person reference
  these screens ask for, and Enter in it searches, never submitting the enclosing command form),
  `CapabilityNotice` (the switch as a notice above records and commands the API never turns off;
  unlike `CapabilityGate` it never hides them while `GET /me/permissions` loads or fails).
- Lists are the API's keyset pages through `useApiPages` and `LoadMore` (`src/api`, `src/ui`):
  "Load more <label>", a failed page keeps what is loaded, nothing is silently cut off (§4.5). This
  covers the offering picker (programs and a program's offerings), the person search and the
  finance exception queue; a list is shown in the API's order and never re-sorted on a partial
  set.

## What stays open, and why

- Review deadlines on applications (SCR-S-24) and offer expiry (SCR-S-26): **Pending decision**
  DEC-028 and DEC-006 (stage 3 deliberately added none). The API names no resolver per
  application; the decision permissions shown are the principal's role view. Who may override
  eligibility is **Pending decision** DEC-066, and whether approval reserves a place DEC-028 and
  DEC-029.
- Oldest-first review queue (SCR-S-24): `GET /applications` pages newest first only, so the queue
  is shown newest first and says older applications follow under "Load more". An oldest-first
  order is reported as an API issue rather than re-sorting a partial set.
- Staff read of a membership's suspensions (SCR-S-27): the API offers only the customer's
  `GET /me/memberships`, so suspensions made before the page was opened are not listed and cannot
  be ended from here (ending needs the suspension's revision). Reported as an API issue.
- Provider events per payment attempt (SCR-S-36): `GET /provider-events` has no attempt or provider
  reference filter, so the attempt links to the events of its provider.
- Card payment at the desk (DEC-019), installment plans (DEC-073), partial basket fulfillment
  (DEC-026), cash procedures (DEC-009), refund and credit rules (DEC-009, DEC-058), team liability
  (DEC-008), accounting export (DEC-022): **Pending decision**, shown as such.
- Money records carry no facility, so order periods and attempt times are shown in UTC and labelled
  (stage 3: "facility zone on money records" not built).

## Proposed handling

- Every person a registration or finance screen asks for has the person search beside its
  reference field (and the staff directory picker for a responsible manager), and the reference
  stays editable, so a person the viewer may not search for can still be entered (**Proposed**).
- The OpenAPI document marks some components nullable (`PaymentAttempt`, `FinancialConsequence`,
  `Receipt`, `Person`, ...) and encodes nullable references as `allOf` with a null type, which the
  generated types read as non-nullable; screens guard both at runtime.
