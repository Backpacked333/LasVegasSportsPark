# Today, People and families, support cases (staff)

SCR-S-01, SCR-S-02, SCR-S-20 to SCR-S-23, SCR-S-49 and SCR-S-50 of
`docs/package-a/screen-and-journey-inventory.md`. Screens live in `src/screens/today/`,
`src/screens/people/` and `src/screens/support/`; the pieces they share live here
(`src/features/people/`) and in `src/screens/today/` (`AffectedRecordState.tsx`, `AuditHistory.tsx`,
`useFacilityDirectory.ts`). Tests are in `src/screens/{today,people,support}/__tests__/`.

Status legend (§6.7): **Verified** = implemented and asserted by a jsdom test in this app against
the mocked API client; **Proposed** = engineering choice awaiting operator approval; **Pending
decision** = needs an operator answer (owners in `docs/package-a/decision-register.md`). Staff
acceptance on the actual workstations (§6.3) has not happened for any of these screens.

Routes: `/today`, `/today/exceptions/:exceptionId`, `/people`, `/people/:personId`,
`/people/:personId/relationships`, `/people/invitations`, `/people/access-reviews` (`/new`,
`/:reviewId`), `/people/duplicates`, `/people/duplicates/:candidateId`, `/admin/cases` (`/new`,
`/:caseId`).

## Still open

- Per-participant arrival issues (MET-005) are evaluated at check-in by the entry module and are
  not part of the expected-arrivals report; the Today feed itself carries no arrivals or activity
  list (stage 3 did not add them), so both come from their owning reads.
- Exceptions and cases carry no state of the affected record (stage 3 did not add it); the client
  reads each record from its owner, and record types without a single-record read
  (`delivery_attempt`, `installment`, `case_action`, `person_merge`, `offline_sync_batch`,
  `release_record`, `package_entitlement`, `access_device`, `visit`, `attendance` and others) say
  their state is kept by the owning module.
- A household's members are not listed for staff (the authority read gives the name and member
  count); `GET /v1/me/households` is the customer's own view.
